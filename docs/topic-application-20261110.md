# 话题判断与申请流程（2026-11-10 本轮）

> 状态：**第一轮实现完成；同日第二轮完成五项 P1 修复（见 §7）。完整验收结果以最终交付报告为准**。
> 共享契约：`docs/topic-application-contract-20261110.md`。源代码位置以实际仓库为准。
> 本轮不改数据库 schema；话题申请复用既有审批记录的持久化、有效期与单次消费能力。

## 1. 普通用户会看到什么

以前，QIO 自己（相似度预测）可能先判断“这段话像另一个话题”，然后弹出「转到这里？」的提示；是否该换话题有多个入口，标准也不一致。

现在改为：**先由本轮主模型结合上下文作唯一判断，QIO 不在后台替你换话题**。

- 你继续追问、纠正、补充、让 QIO 重做或推进当前事情时，QIO 会留在当前话题继续回答，不会打断你确认。
- 当 QIO 认为你提出了一个**确实独立、超出当前话题范围的新目标**时，它会提出一次话题申请：
  - 已有合适的旧话题：弹窗问你是否「转到并回答」；
  - 需要新建话题：弹窗问你是否「新建并回答」，新话题名可以直接在弹窗里改。
- 弹窗里只显示：当前话题、目标话题或新名称、简短原因，**不会展示你的原问题或摘要**。
- 你可以选「在当前话题回答」：QIO 不换话题，直接在当前话题回答原问题；同一段讨论里不会再反复问你。
- 右上角关闭只是**收起**弹窗，不代表批准或拒绝；你可以从输入区入口重新打开，已经改过的新名称也会保留。
- 点「转到并回答 / 新建并回答」后，QIO 会先把这次提问真正归到目标话题，再基于目标话题的上下文回答；**不会把同一问答在两个话题里各存一份**。
- 等待你选择期间：你可以继续打字写草稿，但这一个对话的发送按钮和发送快捷键暂时不可用；其他对话/页面不受影响。处理完后，草稿仍在输入框，之后由你主动发送到确认后的话题（不会自动发送）。
- 如果申请过期、执行失败或目标话题已经不在了，弹窗/提示会说明真实原因，原问题和草稿不会丢，也不会重复执行。

## 2. 判断口径（统一语义）

**唯一语义判断位置是本轮主循环模型**（第二轮 P1-01 定稿）：用户原话完整进入主循环，程序在
进入主循环之前**不做**任何关键词/正则/包含匹配式的「这是不是在要求切换/新建」识别，也不在
模型调用前直接改变对话位置。模型需要换题时调用**原有** `switch_topic` / `create_topic`，
并在参数里声明来源：`intent="user_request"`（用户本轮明确要求，直接执行、不重复普通确认）
或 `intent="suggestion"`（QIO 主动建议，进入话题申请）；缺省/无法确定一律按 `suggestion`。
这个声明是本轮真实工具调用的一部分，客户端字段、历史布尔值与其它轮次都不能复用它。

判断顺序：

1. 是否在纠正、补充、追问、重做或推进当前事项？→ 优先延续。
2. 是否出现可独立处理的新目标？
3. 新目标是否超出当前话题和用户已认可的讨论范围？
4. 是否仍属于用户已经选择“保留在这里”的同一段讨论？

这些规则（含否定、引用、解释、条件、改口、指代等反例）单源维护在
`backend/src/agent/prompts.py` 的 `TOPIC_SEMANTIC_POLICY`；`services/topic_decision.py` 只注入证据。
「是否主动要求」是**主模型的语义判断**，不再交回关键词、正则、固定否定词表、相似度阈值或新增轻量模型；
程序只负责结构化事实（工具/轮次/会话绑定、目标存在性、参数有效性、查重、位置版本、有效期、单次消费、幂等）。

四种结果：

| 结果 | 程序行为 |
| --- | --- |
| 延续当前话题 | 直接在当前话题回答，不申请、不打断 |
| 建议切换已有话题 | 调用既有 `switch_topic` → 程序建立话题申请 → 等你选择 |
| 建议创建新话题 | 调用既有 `create_topic` → 程序建立话题申请（名称可改）→ 等你选择 |
| 暂时无法判断 | 留在当前话题正常回答，不强制询问 |

相似度只用于**筛选可能相关的已有话题、作为证据**：高相似不代表一定延续，低相似也不等于应该新建；不能只因交付形式变化（查论文 → 写邮件）就拆话题，也不能把每个新词都拆成新话题。程序里没有“经过若干轮/若干分钟再提示”的计时规则，判断来自本轮主模型结合真实上下文。

## 3. 申请生命周期

```
本轮用户消息
   │
   ├─ 主模型正常回答（延续 / 无法判断）─────────────────────────────→ 回答写入当前话题
   │
   └─ 主模型调用 switch_topic / create_topic
          │
          ├─ 程序拦截：本次调用**尚未执行**
          │     ├─ 模型声明 intent="user_request" → 校验参数后直接执行原工具（不重复确认）
          │     └─ 否则（suggestion / 无法确定）建立话题申请（复用审批身份/有效期/单次消费/持久化）
          │
          ├─ 弹窗等待用户选择（期间：不执行工具、不泄露正式回答；可写草稿，发送暂不可用）
          │     ├─ 批准 → 校验参数（新名称/目标是否存在/位置是否被新导航改变）
          │     │        → 执行原工具 → 本轮提问/绑定搬到目标话题 → 重装目标话题上下文
          │     │        → 继续生成正式回答（只存一份，归属目标话题）
          │     ├─ 拒绝 / 取消申请 → 不执行工具 → 在当前话题回答原问题（整轮不算“用户停止”）
          │     └─ 收起（关闭弹窗）→ 申请仍待处理，不发决定；可从入口重新打开
          │
          └─ 过期 / 后端重启 / 用户已手动导航 → 按失效处理：不执行、不重复、保留原问题与草稿，在原话题回答
```

### 3.1 申请身份与权威记录

- 一条申请只有一个权威记录：后端 `ApprovalService.request()` 产生的审批行（`approval_id` + 有效期 + 单次消费 + 持久化）。前端不写话题、不另走导航旁路，也不保留第二条可独立提交的旧确认路径。
- 申请种类：`topic_switch`（目标已有话题）/ `topic_create`（新名称可编辑）。载荷只含展示与执行所需字段，不含原问题。
- 决定沿用统一确认弹窗的既有审批提交路径：批准 / 拒绝；「停止整轮」仍是原来的停止语义，与「取消话题申请」分开。
- 执行前重校验：目标是否仍存在、新名称是否为空、本轮绑定/当前锚点是否仍是申请时的原话题。任何一条不成立都按失效处理并如实说明，不产生“假成功”。

### 3.2 正式回答之前落实归属与上下文

这是本轮的核心改造：旧实现主要在**收尾**时把整轮搬到模型自己切的话题。现在把绑定与上下文衔接**提前到正式回答之前**：

1. 原工具真实成功后，程序把本轮用户消息与轮次绑定迁到目标话题（只移动本轮这一条；其它历史/已排队消息不动）；
2. 重新装配目标话题需要的上下文（话题范围、短期记忆、检索、实体卡、焦点位置），**不**把原话题全部历史复制进新话题；替换本轮 system 上下文后继续生成；
3. 提问、正式回答、关联轮次记录归属一致；不产生重复的用户消息；工具失败与回答失败分别记录，已成功创建的话题不因回答失败回滚。

### 3.3 前后端交互（摘要）

| 层 | 行为 |
| --- | --- |
| 事件 | 申请使用既有 `APPROVAL_REQUIRED` / `APPROVAL_RESULT`；旧的 `TOPIC_SWITCH_SUGGESTED` 可执行建议退役，不再发布 |
| 弹窗 | 复用既有中央统一确认弹窗与互斥/排队规则；话题申请自动展开（不抢占正在处理的弹窗），关闭=收起 |
| 决定 | 沿用工具审批既有决定路径 `POST /api/approvals/{id}/respond`，新增可选 `edits.name`（新建名称）；空名称/目标消失/失效返回可处理错误，申请不被误消费 |
| 等待状态 | 显示「正在等待你选择话题」，不伪装成模型生成中 |
| 发送限制 | 仅对应对话的发送按钮与快捷发送暂不可用，草稿可写；处理后恢复原有发送/排队规则 |
| 草稿 | 确认后跟随到确认后的话题且不自动发送；拒绝保留在原话题；目标话题已有草稿保留可恢复能力 |
| 新话题入口 | 输入区的旧「话题切换建议」入口改为打开同一话题申请，不再有独立提交路径 |

## 4. 边界与已知限制

- **原生工具模式与兼容文本模式**都要覆盖：兼容档下工具调用从文本解析，程序同样在工具执行前拦截申请；如某档位无法保证「先申请后回答」，会如实记录并禁用该档位的自动申请（不伪装）。
- **真实模型准确率**不在本轮证明范围：所有流程测试使用 fake/mock 模型；测试只能证明程序接线、状态传递、证据来源与拒绝范围处理，不能声称真实模型在所有自然语言场景判断准确。
- **后端重启**：未处理申请不会续期；重启后按既有审批恢复可见，若已无等待中的本轮，按失效处理（不执行、不重复、保留原问题），可从原话题重新发送或重新申请。
- 用户等待期间手动导航：旧申请不得覆盖新选择；按失效处理并在当前话题回答原问题。
- 申请记录沿用既有审批表（无 schema 变更）；第二轮 P1-04 追加了一张**只存单调导航版本**的单行表
  `navigation_version`（新迁移，不改历史迁移）。

- `ApprovalResult.edits` 只在带 `edits` 时以关键字传入 `respond`，旧调用方/测试桩签名不变；无等待者的 topic 申请返回 409 `topic_application_stale`，非 topic 旧行保持原 409 口径。
- **（第二轮 P1-02 修订）** 旧的「先发布 answer delta、发现话题工具后再用同一 delta_id 改判为过程说明」
  的路径已**删除**：它仍然让正式正文先到达用户。现在改为后端话题阶段门 —— 决策/等待/执行/上下文
  准备期间整段缓冲，不发布任何 `interim=false` 正文；含话题工具调用的响应正文整段丢弃，
  只有进入 `answerable` 之后才发布正式回答（事件顺序：`TOPIC_PHASE(answerable)` 先于正文）。
- 后端重启后未处理申请不续期；无等待者时决定 409 stale，不执行、不假成功，原问题/草稿保留。
- 真实模型自然语言判断准确率不在本轮证明范围：流程测试均用 fake/mock 模型，只证明程序接线、状态传递、证据来源与拒绝范围处理。
- 本轮未新增数据库 schema；申请记录沿用 `pending_approvals`。第二轮只追加 `navigation_version` 单行表

## 7. 第二轮：五项 P1 修复（2026-11-10 同日后半轮）

1. **P1-01 移除错误的程序授权识别与轮前直切**：删除 `detect_explicit_navigation` /
   `detect_explicit_topic_creation` 及 `begin()` 里的轮前 `enter_topic` 与 `explicit_*` 生产依赖；
   语义判断唯一交回主循环模型（工具参数 `intent`）；`prompts.TOPIC_SEMANTIC_POLICY` 集中维护规则
   （含否定/引用/解释/条件/改口/指代反例）。手动 UI 导航入口不变。
2. **P1-02 后端正式回答发布边界**：新增 `TopicPhase` 阶段门与 `TOPIC_PHASE` 事件；
   `decision_open / awaiting_confirmation / executing / context_preparing` 期间零正式正文；
   `answerable` 后归属固定，迟到导航请求不再改变归属；之后恢复流式。
3. **P1-03 上下文准备失败可恢复**：`TopicStages` 分步事实；异常/超时/空结果不再回落到旧上下文，
   不清空待重建记录；发可恢复错误 + `POST /api/recovery/records/{id}/retry-answer` 只重做未完成步骤，
   不重跑 create/switch、不新增用户消息；回答失败单独恢复。
4. **P1-04 申请绑定真实导航位置与版本**：`navigation_version` 单调版本 + 申请快照
   （`operation_id / base_nav_version / param_version / from_fragment_id` 等）；确认前复核 +
   写入前 CAS 条件更新（版本不符整体回滚）；失效 ≠ 拒绝，禁用原确认但保留恢复入口。
5. **P1-05 稳定操作身份**：`operation_id` 衔接改名/查重/重试；名称/目标是带版本参数；
   同 operation + 同参数版本的合法重试可进入既有冲突确认流程；双击/重复确认/回调/超时/刷新幂等；
   操作 ID 稳定不延长有效期。
