# R9-H8 共同根因记录

基线 r9h7/main 89397527（代码 ca47d07d）。本轮先追踪 H5-H7 变更，再修六项。

## 1. 反复回归的共同根因

| 观察 | 证据 |
| --- | --- |
| 共享数据含义被局部修复改变 | H7 在限制匹配函数过滤 program_name 后把空 objects 的返回值从 True 改成 False。原语义 objects 为空表示限制全部对应操作；改为 False 后整体限制静默失效（问题一）。 |
| A/B 状态混用 | H7 把“明确存在程序禁止但对象未绑定”返回 APPROVE，并让 operations 接受 program_name code 完成具体批准；普通批准因此能执行已确定禁止的同一解释器（问题二）。这是 A（明确禁止待绑定）被混入 B（限制内容未知）。 |
| 修一个约束删另一个 | H7 为“确认前不读取”直接省略内部维护 base 内容摘要，只保留身份；身份不变的内容编辑被旧方案覆盖（问题三）。 |
| 同一规则多处实现 | 工具读取探测、recheck_before_execute、审批恢复各自实现读取顺序；H7 只在部分入口检查，删除批量禁读在循环内整体 return（问题四、五）。 |
| 同名字段不同事实 | script_sha256 在 cmd 工具里是 argv 参数文件集合的合成摘要，在 launch facts 里是单一脚本来源摘要；审批恢复比较同名字段，未变化脚本被判失效（问题六）。 |
| 测试只覆盖局部阶段 | 大量测试只断言 pending/最终拒绝，未验证批准后实际执行、拒绝前读取次数、未变化成功、批量子项结果。 |

## 2. 统一后的共享规则

1. 限制条目：operations 空=全部操作，objects 空=全部对象；objects 非空按结构化 kind/对象匹配；program_name 是未解决来源，不能直接决定允许/拒绝。
2. 状态 A/B：A（明确禁止但对象未绑定）必须恢复/澄清，直接 DENY，普通批准不能解除；B（限制未知）按 unresolved/known limits 契约处理。
3. 读取顺序：读取权限/要求状态 -> 真实内容读取 -> 身份/摘要/前置状态 -> 操作授权/确认；工具、直接执行、模型等待、审批恢复、重启恢复一致。
4. 内部维护：确认前只允许元数据（身份/size/mtime/目录枚举）；确认后仍核对元数据/最新限制，不静默采集新基准。
5. 目录：目录是一个子项但其子对象影响必须保留；内部目录维护确认前不读正文。
6. 程序：入口、解析目标、脚本来源、参数文件集合、spec_digest 分开表达；同一事实同一生产方式。
7. 批量：共同条件失败终止整批；子项条件只失效对应项，结果逐项保留。

## 3. 六项修复对应

1. 空 objects 恢复 True；program_name 仅作来源匹配，不直接命中冲突。
2. program_name 按平台程序解析和真实对象 identity/realpath 绑定；同一对象换入口仍拒绝；未绑定明确禁止直接 DENY，普通批准不能覆盖。
3. 内部写确认前只绑 identity/size/mtime；执行前核对元数据；变化 invalidated。
4. 删除逐项读取检查改为写入 denied 子项并继续；审批只包含有效项。
5. 内部目录确认前 metadata-only；执行前 metadata-only 比较；不读正文。
6. cmd execution facts 的 script_sha256 改为真实脚本来源摘要；参数文件集合由 argument_files/spec_digest 表达，恢复不再误比。

## 4. 旧测试冲突处理

- H4/H6/H7 中 program_name 由 DENY 改为 APPROVE/ALLOW 的预期改回 DENY：依据是问题二要求普通批准不能覆盖明确禁止，A 状态必须先恢复对象。
- H6 程序名称测试的输入保持真实入口 python/绝对路径，不替换成解析目标；新增 H8 回归保留原案例。
- H6 未变化脚本审批测试新增绑定要求，证明批准后实际执行，而不是只验证 pending。
