## 3. review.py（语义化授权审查）

### 3.1 输入组装（后端负责，模型不能选择性提交）

`build_review_payload` 现在包含：
- `requirement`：`requirement_id / version / text / provenance / parent_id / status / limits`（原话不经模型改写）；
- `corrections / user_limits / user_constraints`：用户原话里的补充与限制；
- `requirement_resolution: {status, limits[]}`：该要求来自哪次模型解析；解析失败时 `status="unavailable"`（契约 §3）；
- `operation`：动作、对象（后端核实 identity/file_origin）、程序/argv/cwd/脚本摘要、`spec_digest/content_digest/precondition_digest/delete_mode/conditions`、网络接收方、用途摘要；
- `related_grants / prior_decisions / approvals`：只作背景；
- `untrusted_material`：文件/网页/工具结果内容**单独标注**，不混入 requirement。

### 3.2 validate_outcome（只做事实核对，不做语义/措辞判断）

1. 结构合法：`ReviewOutcome / decision / 字段类型`；
2. 来源一致：`outcome.requirement_id == request.requirement.requirement_id`（严格要求，父要求 id 也不能冒充当前依据）；要求 active 且 `version` 为有效整数；
3. 只在 restricted 模式、合法操作类型上生效；
4. objects / allowed_operations ⊆ 请求集合；身份/来源以请求（后端核实）为准，模型不得补造；
5. ALLOW 必须覆盖全部目标对象、allowed_operations 只含本次操作类型、必须给出 limits 与 purpose，并且用户原话/补充非空（来源完整性）；
6. reason 非空；
7. 请求结构校验包括：`requirement_resolution_status` 合法、`resolution_limits` 为对象数组、操作绑定字段类型/`delete_mode` 合法、`conditions` 为对象数组。
任何不通过 → `ReviewUnavailable`（调用方不得当 ALLOW）。

### 3.3 审计

`ReviewAuditLedger` 新增 `requirement_version` 列写入（迁移 57）；调用方未给时从台账读取当前版本；仍只落摘要/结果/模型/提示词版本/耗时/错误，不落推理与材料原文。

## 4. resolution.py（模型要求解析）

### 4.1 API

```python
class RequirementRelation(str, Enum): NEW="new"; AMEND="amend"; WITHDRAW="withdraw"

@dataclass(frozen=True)
class ResolutionOutcome:
    relation: RequirementRelation
    target_requirement_id: str | None
    corrections: tuple[str, ...]
    limits: tuple[dict, ...]          # {"operations": [...], "objects": [{"kind","value"}], "reason": str}
    reason: str
    model: str
    prompt_version: str
    target_version: int | None = None # 契约 §3 版本核对所需（dataclass 清单未列，见 §10）

class RequirementResolutionUnavailable(Exception): ...

class RequirementResolver(Protocol):
    async def resolve(self, *, message, message_id, turn_id, candidates) -> ResolutionOutcome: ...

class ModelRequirementResolver:
    def __init__(self, *, adapter_factory, model_call=None, timeout_seconds=20,
                 context_provider=None, allowed_objects_provider=None)
    async def resolve(self, *, message, message_id, turn_id, candidates) -> ResolutionOutcome

def validate_resolution(outcome, *, candidates, allowed_objects=()) -> ResolutionOutcome
```

- 单次 `adapter.complete(messages, tools=[])`；不新建 Agent、不暴露工具/文件/设置；不写库。
- 提示词单一来源 `agent/prompts.py`；版本 `r9g-req-resolution-v2`。
- 超时/异常/非法输出/校验失败 → `RequirementResolutionUnavailable`；调用方按"新要求"继续并标 unresolved，**不做关键词/句式兜底**。

### 4.2 validate_resolution

- relation 合法；reason 非空；
- NEW 不得带 target/target_version；
- AMEND/WITHDRAW：target 必须是候选里的 id，候选状态 active，`target_version` 必须等于候选版本（防止模型基于过期候选修改）；
- limits：structure 合法；operations 必须是稳定操作名白名单；objects 的 kind 必须合法；当调用方提供 `allowed_objects` 或候选自带 objects 时，limit 对象必须命中（同一后端对象允许 path/directory 等类别措辞差异，按规范化值匹配）；没有对象清单时只做结构校验（限制只收紧、不产生授权，执行前仍会核对真实对象）；
- 不落推理全文。

## 5. requirements.py（版本绑定与落实）

### 5.1 API 增补

```python
@dataclass(frozen=True) class RequirementBinding: requirement_id: str; version: int

@dataclass(frozen=True) class AppliedResolution:
    resolution_id: str; relation: str; requirement: UserRequirement | None
    target_requirement_id: str | None; superseded_requirement_id: str | None
    limits: tuple[dict, ...]; corrections: tuple[str, ...]; reason: str

class RequirementLedger:
    def binding_for(self, requirement_id) -> RequirementBinding | None     # 仅 active
    def validate_binding(self, binding) -> bool
    def candidates(self, *, limit=12) -> list[dict]                        # id/version/原话摘录/时间/状态/topic
    def apply_resolution(self, resolution, *, message_id=None, turn_id=None,
                         topic_id=None, message=None, latency_ms=None) -> AppliedResolution
    def record_resolution_failure(self, *, error, message_id=None, turn_id=None, ...) -> str
    def resolutions_for(self, *, target_requirement_id=None, limit=50) -> list[dict]
    # 既有：record_user_message / add_correction / withdraw / supersede / by_id / chain / corrections_for
```

### 5.2 语义

- `record_user_message`：新的 active 要求，`version=1`；原话原样保存。
- `add_correction`：子要求 `version=parent.version+1`；父要求 superseded；父链授权记录撤销；历史行保留；limits 继承并追加修正原话/额外限制文本。
- `apply_resolution`：
  - new → 新建 version=1 要求（`text` 优先用调用方传入的真实用户消息，保证"用户原话不被模型改写"）；
  - amend → 以 target 为父 add_correction（版本+1；父要求 superseded）；
  - withdraw → target 及后代 withdrawn（历史保留）；
  - 目标不存在/非 active/版本不符 → 抛错且写 `rejected` 审计，**不静默新建**；
  - 成功写 `applied` 审计（relation/target/outcome/reason/model/prompt_version/latency）。
- 结构化 limits 展平为可读文本写入 `user_requirements.limits`（持久化/重启后可见）；完整结构化 limits 通过 `AppliedResolution` 返回给 turn 上下文（见 §12 限制）。
- `current()` 保留只读兼容，docstring 明确"不得再作为授权依据"。

### 5.3 授权记录

- `AuthorizationRecord` 增加 `requirement_version`；`record()` 未填时从台账补齐；台账不存在 → 抛错（不建无绑定记录）；
- `reuse()` 要求 `r.requirement_version = u.version` 且要求 active、记录未撤销/未过期、decision=allow；
- `authorization_record_from_outcome` 写入 `requirement.version`；
- 修正/撤回/替换即撤销对应记录；历史行保留（revoked_at 标记），不删除用户历史。

### 9.2 每个用户 turn 开始（所有模式，不只 restricted）

```python
from agent.security.requirements import RequirementBinding
from agent.security.resolution import RequirementResolutionUnavailable

try:
    candidates = ctx.requirements.candidates()          # 有限候选
    resolution = await ctx.requirement_resolver.resolve(
        message=user_text, message_id=message_id, turn_id=turn_id, candidates=candidates,
    )
    applied = ctx.requirements.apply_resolution(
        resolution, message_id=message_id, turn_id=turn_id, topic_id=topic_id,
        message=user_text,                                 # 真实用户原话（不让模型改写 requirement.text）
    )
    requirement = applied.requirement                      # new/amend 后 active；withdraw 时为被撤回要求
    binding = (
        RequirementBinding(requirement.requirement_id, requirement.version)
        if requirement is not None and requirement.status == "active" else None
    )
    resolution_status = "resolved"
    resolution_limits = applied.limits
except RequirementResolutionUnavailable as exc:
    ctx.requirements.record_resolution_failure(
        error=str(exc), message_id=message_id, turn_id=turn_id,
        model=..., prompt_version=..., latency_ms=...,
    )
    # 契约 §3：按新要求继续，并标记 unresolved；授权审查请求携带 unavailable
    new_requirement = ctx.requirements.record_user_message(
        text=user_text, message_id=message_id, turn_id=turn_id, topic_id=topic_id,
    )
    binding = RequirementBinding(new_requirement.requirement_id, new_requirement.version)
    resolution_status = "unavailable"
    resolution_limits = ()
# 把 binding 放进 context.py 的 RequirementBinding contextvar（Lead 新增）
```

### 9.3 Engine 侧（Lead 改）

- 删除 `_current_requirement()` / `requirements.current()` 作为授权依据；从 `AuthContext.requirement`（RequirementBinding）取；
  缺失或 `validate_binding` 失败 → 需人工确认（APPROVE），**不回退"最近一条"**。
- 构造 `ReviewRequest` 时：
  - `requirement=requirements.by_id(binding.requirement_id)`（active + version 与 binding 一致）；
  - `corrections=requirements.corrections_for(id)`；
  - `requirement_resolution_status / resolution_limits` 来自本 turn 解析结果；
  - `operation` 带 R9-G 绑定字段：对象身份/来源、程序身份/argv/cwd/脚本摘要、
    `spec_digest/content_digest/precondition_digest/delete_mode/conditions`（后端核实值，不采信模型字段）。
- ALLOW → `authorization_record_from_outcome(outcome, request=request)` + `authorization_records.record(record)`
  （自动带 requirement_version；也可手工构造 AuthorizationRecord，record() 会从台账补版本）。
- CONFIRM → APPROVE；DENY → DENY；`ReviewUnavailable` → APPROVE（人工审批），不自动允许、不切模式。
- 执行前重核对：`validate_binding(binding)` + `reuse`（版本已由 SQL 校验）；要求已修正/撤回 → 不可执行。
- 子智能体/后台/审批恢复共享父级 RequirementBinding（context.py contextvar），不得改绑。
- 永久删除：模型 ALLOW 不能替代明确人工确认（契约 §5，W2/Lead）。

## 10. 与冻结契约的偏差 / 补充（均为向后兼容的追加）

1. **`ResolutionOutcome.target_version`**：契约 §3 要求"后端核对身份/版本/状态"，但 dataclass 清单未列版本字段；
   增加可选字段（默认 None，amend/withdraw 必填），用于拒绝基于过期候选的修改。
2. **`apply_resolution` 额外可选参数 `message/topic_id/latency_ms`**：契约只列 message_id/turn_id；
   增加 message 是为了让 requirement.text 保存**真实用户原话**（避免模型 corrections 改写原话），
   latency_ms 用于审计耗时；不传时行为保持契约签名兼容。
3. **`validate_resolution` 增加可选 `allowed_objects`**：契约签名仅 candidates；
   用于核对"limits 对象来自候选/后端可解析对象"。未提供清单时只做结构校验（限制只收紧、不产生授权），
   真实执行前仍会核对对象——此边界在报告与代码中写明。
4. **`ReviewOperation` 新增绑定字段**（spec_digest/content_digest/precondition_digest/delete_mode/conditions）：
   契约 §1.4/§7 要求审查围绕真实拟执行操作绑定这些事实；默认空，全部进入 fingerprint。
5. **`ReviewRequest` 新增 `requirement_resolution_status/resolution_limits`**：契约 §3 要求审查请求带解析状态；
   结构化 limits 来自要求解析，仅作为审查上下文展示（不产生授权）。
6. **`AuthorizationRecord.requirement_version`**：迁移 57 已有列；dataclass 增加可选字段（旧记录 None）。
7. **`ReviewAuditLedger` 写 `requirement_version`**：迁移 57 已有列；旧调用不传时从台账读当前版本。
8. **`RequirementLedger.current()` 保留**但明确只读兼容、不得用于授权（契约 §3 允许只读列表用途）。
9. **结构化 limits 持久化限制**：迁移 57 的 `requirement_resolutions` 无 limits/corrections 列；本实现把结构化限制
   **展平为可读文本**写入 `user_requirements.limits`，完整结构化 limits 由 `AppliedResolution` 返回给 turn 上下文。
   若需要跨重启保留结构化 limits 供 engine 逐项核对，需要 Lead 追加迁移列（如
   `requirement_resolutions.limits/corrections` 或 user_requirements.limits_structured`）——本分支未擅自改 schema。
10. **新增异常/辅助**：`RequirementVersionMismatch`、`RequirementBinding`、`AppliedResolution`、
    `record_resolution_failure`、`resolutions_for`（契约外、不改既有签名）。
