一、产品定义与不可破坏的规则

1. 对象定义

Topic：长期内容归属，用户可以反复进入。

Fragment：Topic 内一段连续推进的对话记录，用于保存、摘要、检索和历史接续。

Turn：一次用户交互及其回答、关联执行过程和终态。复用现有轮次身份与管理器。

Anchor：当前有效的对话位置。浏览、检索、模型推测本身不能改写它。

阶段：本次讨论正在完成的工作。作为可重建的辅助信息，首版不建立另一套用户必须管理的对象。

Fragment 不能因为出现一个新问题就立即切分。追问、反驳、修正、补充条件可能共同推进同一阶段。工作阶段转换与容量分块必须区分：同一阶段可以跨多个 Fragment。

2. 强制约束

每个 Topic 最多一个开放、可追加消息的 Fragment；保留迁移 12 已有唯一约束。

同一 Turn 固定绑定一个 Topic 与 Fragment。用户消息、助手回答及关联执行记录必须能追溯到这一绑定。

绑定前确定上下文来源；绑定后不得因为全局 Anchor 改变而移动该轮消息。

尚有未完成写入的 Fragment 不得封存。失败、取消必须释放写入占用，不得依赖最后一条消息角色判断整轮是否结束。

封存后不能追加或搬动原始消息；摘要、向量和索引是可修正、可重试的派生数据。

用户点击历史接续，先保存接续意图；在有实际消息需要执行时落实新片段，不因浏览或点击制造空片段。

浏览 Topic、展开历史、检索记忆均为只读行为。话题预测只能提出建议，不能被片段策略用来自动切换 Topic。

切换 Topic 不自动证明当前阶段结束。可以保留各 Topic 的开放片段；回来时依据接续意图、连续性和容量决定是否分块。

长度是兜底条件，不等于任务完成。因长度而分块时保留同阶段延续关系。

从历史接续恢复的是讨论前提，不回滚已经发生的文件修改或外部工具行为。

三、实施阶段 1：固定轮次归属，安全落实历史接续

1. 设计并实现统一绑定

扩展现有 TurnContext，建立最小必要的持久化记录。至少表达：turn_id、确认后的 topic_id、fragment_id、提交时接受的导航意图及版本、执行终态或可关联终态、写入是否结束。

不要假定已有 Trace 或事件快照天然就是权威业务绑定。确定唯一权威来源及其恢复规则；复用原 turn_id，不新建竞争身份。消息可增加 turn_id 关联，其他执行记录可以通过现有 turn_id 间接关联，不要求把所有记录复制到 messages。

轮前流程：解析本条输入的明确导航意图 → 判断边界 → 在事务中确定归属并写入必要记录 → 基于已确定位置构建上下文 → 执行。明确的导航解析不能误命中否定、引用或假设表达；不要新加仅靠关键词的隐式跳转。

MemoryWriter 改为按显式绑定追加，校验 Topic、Fragment、开放状态和 Turn 的一致性。所有生产写入入口都要接入，包括失败、取消的必要记录和系统主动通知；不能仅改普通助手回答路径。系统通知应有明确来源，但不计作用户轮数、不单独触发语义切分。

移除 persist 阶段依据最新全局 Anchor 搬动已保存用户消息的正常业务路径。轮次完成后推进 Anchor 时使用版本比较，避免旧轮次覆盖较新的导航。

2. 接续意图、有效位置与界面预选分开

保留 TopicNavigationService 作为有效导航的统一入口。增加持久化的已授权接续意图，包含稳定 request_id、来源 Topic/Fragment、版本、状态、落实后的 Fragment，以及必要的提交顺序。

不要复用“模型建议换话题、等待用户确认”的 pending 状态来装载“用户已经选择从历史继续”的意图；二者含义不同。

点击已关闭历史 A：登记可替换的下一次接续选择，界面显示将从 A 继续。点击当前开放片段：视为继续现有位置，不重复建片段。用户在发送前取消或改选时不产生空历史。

接续请求应覆盖 UI 与 Agent 工具两条入口。Agent 执行中调用接续工具，只登记对后续提交消息生效的意图，不改变当前轮绑定，也不改写已经提交的排队消息。工具返回与事件文案必须准确说明生效时机。

3. 队列顺序是强制产品要求

消息提交时捕获导航意图，开始执行时落实具体 Fragment。不要让执行较晚的消息接受提交之后的新导航。

必须实现并验证：C 中提交甲且甲排队 → 选择从 A 继续 → 提交乙。甲仍归原先接续位置，乙从 A 接续。

同一接续意图下连续提交乙、丙时，仅第一次实际需要执行的消息创建接续片段；其余消息继续该路径，容量或阶段边界除外。若首条排队消息在执行前取消，该意图仍可由后续有效消息落实。

如果排队期间其目标路径末端已经封存，应创建该路径末端的普通延续，不重开封存记录，不挪到其他路径，不重新从最初来源重复分支。无论执行顺序如何仍保持每 Topic 最多一个开放片段。

4. 原子交接

在没有活动写入占用的安全边界，以短事务完成：

校验来源和意图版本、检查幂等记录。

必要时封存该 Topic 已有开放片段 C，记录原因，保留未解决状态。

创建 D，写明它直接接续自 A。

固定本轮绑定，并执行与首条消息写入一致的原子安排，避免留下无依据的空片段。

标记请求已落实，保存落实结果，登记封存后的派生任务。

提交后发布必要状态事件；事件发送失败不能使重试重复创建。

不得在事务内 await 模型或网络调用。使用明确的数据库写入协调方式保护共享连接；处理并发、重复 HTTP 请求和工具重试，不能只捕获唯一约束错误后返回“成功”。

区分“请求已落实”与“提示已消费”：首轮失败后复用 D 和来源关系；用户明确重试可建立新的执行尝试，但不能重复创建路径。首轮成功推进后消费提示。传输层同 request_id 的重发与用户明确发起的新一轮必须区分。

四、实施阶段 2：拆开封存与派生任务，建立恢复能力

1. 分开两种结束状态

现有 post_turn 运行时 TurnManager 可能还未发出终态。请明确实现：

写入结束：回答或失败/取消结果已按既定策略落库，不会再追加本轮内容。

轮次整体结束：由既有 TurnManager 按协议发出唯一终态事件。

可在写入结束后释放片段占用；不能为了封块等待一个要在 post_turn 返回后才出现的终态，也不能提前宣布执行成功。取消或异常各出口均应释放占用并保持终态协议正确。

2. 先封存，后生成摘要

拆分当前 close(summary) 语义，采用职责清楚的方法完成封存和派生内容提交。封存时固定消息范围/内容版本、边界原因、封存时间，并登记持久化任务。

任务状态至少能表达 pending、running、completed、retryable failure。支持进程恢复、重复执行幂等、失败退避，避免永不结束的高频重试。

模型调用使用封存后的固定内容；结果落库时校验内容版本，以事务保持摘要、检索索引和任务状态一致。已有摘要版本字段可以复用，只有必要时再增加内容版本或其他字段。

摘要失败不使对话或导航失败；历史原文仍可读取，直接来源的上下文有受预算控制的原文回退。不得把“已关闭但无摘要”当作内容不存在。

滚动摘要也要绑定内容版本或快照，不能让迟到结果覆盖较新内容。实体提炼、知识提炼、向量更新使用稳定来源与幂等标识，失败恢复不能重复制造知识、实体或关系权重。

摘要应表达：本段目标、已形成结果、仍未解决问题、下一步、分块原因。普通讨论或闲聊不强行生成虚构任务；未知信息保持空缺。容量封块不得生成“任务已完成”的错误结论。

3. 恢复边界

持久恢复范围必须包含本次新增的绑定、接续意图、幂等结果和派生任务。确认启动流程如何识别中断轮次并释放写入占用。

不得自动重放可能有外部副作用的工具。进程中断后可以保留 interrupted/failed 状态等待用户显式重试，并给出清楚反馈。不宣称本次实现了所有排队执行的无损自动恢复；若原队列未持久化，说明保留范围和限制。

阶段 2 交付

摘要失败和进程重启可恢复的任务机制，写入完成与轮次终态顺序说明，故障注入测试，原文降级及索引一致性证明。

五、实施阶段 3：正确记录历史关系，并据此组织上下文

1. 数据关系

优先扩展现有 Fragment 与 source_fragment_id，避免新增竞争容器。使 Fragment 数据访问对象能完整暴露关系信息，不让各处靠临时 SQL 猜测。

至少明确表达：

直接前驱或来源。

关系类型：普通延续、历史重新展开，以及旧数据未知。

边界原因：阶段变化、容量、历史接续或其他真实原因。

容量延续是否保持同阶段。

摘要任务状态与必要版本。

来源关系与边界原因分开。普通创建不能只按 Topic 中时间最新片段猜来源；来源必须来自实际绑定路径。校验同 Topic 来源、无自指、无环、失效来源处理。读取祖先时具备深度/预算限制与循环保护。

2. 路径上下文

ContextAssembler 接收明确的本轮 Topic/Fragment/历史意图，查询只读，不再 get_or_create_open。

默认前提按以下层次组织：当前片段近期原文 → 直接来源的必要结果和遗留问题 → 祖先路径上必要摘要 → 其他相关历史参考 → 当前适用的长期知识。

对于 A→B→C 与 A→D，D 不默认继承 B/C 的决定。不要继续把 recent_fragment_summaries(topic_id, limit=2) 作为无条件默认前提。

保留现有预算规划、当前 query 排除、稳定身份去重。必要的不同角色信息不能因粗糙去重丢失：同一片段既有路径继承内容又被检索命中时，统一身份并明确优先级；不得重复注入整段。

其他路径可以作为明确标注的参考，不能伪装为当前已接受结论。长期知识和实体卡也检查来源：特定路径内的决定、假设、方案状态不能经 Knowledge 或 Entity 注入绕过隔离。通用事实可使用，但不能只因为类型名叫“事实”就免除来源与适用性判断。未知来源采取保守标注，不臆造归属。

3. 来源与提示消费分开

不再以 source_fragment_id 非空或存在 Focus 来判断历史提示是否永久显示。来源永久保留；提示在首轮有效推进后消费；失败和取消保留接续含义，但重试不重复创建。

同一段原始历史的“选择待接续”“接续已创建但未成功推进”“正在沿该来源继续”在业务状态上可区分。界面只展示用户需要的信息。

4. 旧数据迁移

只追加新迁移，不改历史迁移。保留 Fragment、消息身份和内容，不自动重切历史。

迁移 12 已把部分重复开放片段的 closed_at 设为 created_at；不能把该时间当作真实讨论结束时间，也不能仅凭相同时间反推迁移处理身份。

可确认的旧 source_fragment_id 保留并校验；不能确认的普通延续标记 unknown。针对未知历史采用清晰的兼容回退并说明限制，不能宣称旧数据全部具备精确路径隔离。对缺少摘要/索引的旧封存数据提供幂等补齐机制，不猜测缺失的讨论内容。

阶段 3 交付

来源关系读写、路径上下文、知识/实体来源处理、提示消费，以及新旧混合数据测试。给出 A/B/C/D fixture 的实际上下文检查结果。

六、实施阶段 4：引入阶段切分与容量兜底

1. 独立边界策略

新增或抽出 FragmentBoundaryPolicy，保持纯判断职责，不直接创建 Fragment、修改 Anchor 或调用导航。返回结构化决策：continue/split/uncertain、原因、生效轮次边界、证据类型、策略版本和必要置信信息。

不要让 should_close 同时承担阶段理解、模型调用和数据库变更。FragmentManager 负责执行已确认决策，TurnOrchestrator 负责时序。

轮前只能使用当前用户输入与此前已经完成的上下文；不能等待本轮回答才决定本轮原始消息归属。轮后以完整 Turn 更新阶段状态和语义表示。首版不自动搬动既有消息纠正较早边界。

2. 规则

显式历史接续：按已授权意图落实，不依赖模型评分。

达到容量目标：在完整轮次边界分块，保留同阶段延续。

明确进入新的交付工作：结合已完成结果、当前指令和上下文确认阶段转换。

同一方案的追问、反驳、修正、补充限制：通常继续。

短回复：结合上一轮提出的具体下一步；“好，就这样”可更新阶段状态，不能单独生成空片段。

单次插话：不足以证明阶段变化。持续偏移可以提高候选信号。

否定、引用、假设中的“开始写代码”等表达：不能当作真实指令。

时间间隔、切换 Topic、语义相似度下降：不能单独证明阶段结束。

无明确目标的普通对话：正常运行，保守切分，不强迫任务阶段分类。

3. 容量

让现有 max_tokens 真正参与策略，明确统计覆盖的保存内容、估算方式、与上下文预算的差别。沿用并兼容 fragment.max_turns 及其旧配置迁移，但把轮数定位为兜底而非唯一阶段定义。

用户轮数依据真实 Turn 绑定统计；系统通知和工具消息不计轮。失败/取消的用户尝试有明确计数政策：实际已写入的用户尝试计入容量，但不假装获得成功回答。传输重试不得重复计数。

单轮可以超过片段容量目标，保留完整后再封存；不要拆轮，不截断原文。片段记录上限不取代已有模型上下文预算和输出限制。上一片段刚因容量关闭时，下一轮同时触发阶段变化，只创建实际需要的一段，不能制造中间空片段。

4. Embedding 信号

复用现有 ONNX/远程嵌入基础能力、缓存和降级机制，不直接把 Selector 最终排序分数当作切分概率。

输入信号至少考虑当前输入与最近完整轮次、当前阶段目标、Topic 代表性内容的关系。语义很接近仍可能发生工作阶段变化；短句低信息量不能当作语义离群值。

阶段目标表示与近期滚动表示分开，避免目标随滚动中心无限漂移。长助手回答不应淹没用户意图；为输入构造和上下文长度制定确定性策略并测试。

向量缓存包含 backend/model、维度、内容版本及表示构造版本等必要身份；不同模型空间不能混比。后端切换或失败时正确失效/重建，BM25/规则降级不用向量阈值。

预算与失败行为：设置短超时或明确可控调用预算，远程故障不能卡住发消息；不可用时以显式操作、可靠规则及容量继续运行。不要给出没有实测依据的准确率。

5. 上线策略与评测

实现 off/shadow/enabled 或同等可回退模式。明确区分确定性边界和待校准语义边界：显式导航、容量和经过测试的高置信阶段规则可以实际生效；Embedding/不确定阶段判断默认先观察记录。

建立人工标注格式的离线评测集，至少包含下面验收矩阵里的阶段案例及独立变体。将规则调试样本与保留验证样本分开，报告误切、漏切、边界延迟、调用成本与降级表现。短回复或有争议的边界允许标为 uncertain，不强迫唯一答案。

不得仅凭自己生成的小样本声称生产准确率。没有足够证据时完整交付观察模式和启用能力，保持不确定策略默认不实际切分，并在报告中说明；不能因此省略策略实现或评测。

切分日志保留必要的原因、版本和匿名标识，遵守现有脱敏约定，不新增完整私人对话或密钥日志。

阶段 4 交付

可运行策略、实际容量兜底、Embedding 辅助、离线评测及观察/启用配置。明确最终默认启用了哪些边界，哪些仍只记录建议。
