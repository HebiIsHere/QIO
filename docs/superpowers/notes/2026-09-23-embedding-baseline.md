# 内置嵌入模型的离线基线（2026-09-23）

## 为什么做这件事

起因是一次「Jev 能不能替代内置嵌入模型」的调研（结论：不能，两者输出形态不同）。
但调研过程中发现一个更基础的问题：`backend/src/agent/eval/` 下的三套离线评测里，
**没有任何一套跑过真实的内置模型**。

- `retrieval_eval` 一直在用 `Selector()` 的默认后端，也就是关键词检索；
- `anchor_eval` 同样；
- `topic_eval` 只在用例自带 `backend: fake_embedding` 标记时套一个确定性假模型；
- `scripts/models/onnx_ab.py` 只有 8 条手写例子，比的还是 fp32 与 int8 两个档位。

所以「现在的模型得几分」一直是个空白，讨论换模型时没有起点。本次把真实模型接进
话题判定与检索两套评测，跑出这个起点。

## 怎么跑

```bash
cd backend
uv run --frozen python -m agent.eval.run                          # 默认路径，不需要模型
uv run --frozen python -m agent.eval.run --embedding onnx         # 用内置模型跑
uv run --frozen python -m agent.eval.run --embedding onnx --out evals/baseline_onnx.json
```

- `--embedding onnx` 时**每个用例新建一个后端实例**：后端内部会按话题 id / 文档 id
  缓存向量，复用实例会把上一个用例的向量带进下一个用例（话题 id 在不同用例里会重复）。
- 评测用内存数据库，不碰用户的 `app.db`。
- 模型缺失时自动退回默认路径，并在结果的 `_run.notes` 里说明找过哪里。
- `--baseline` 只能用于默认路径：`baseline.json` 被 `tests/test_eval_regression.py` 守着，
  不能被模型跑的随机性覆盖。
- 锚点延续评测**本次没有接模型**：它守着一个「不实现距离偏置」的已有决策，改它的输入
  会让那份决策失效，属于另一件事。

本次运行的模型身份（向量身份串，换档位即失效重算）：

```
onnx:bge-small-zh-v1.5:fp32:69a0b846f4f1
```

## 逐用例明细

话题判定：两条路径只在**一个**用例上结果不同。

| 用例 | 期望 | 默认路径 | 内置模型 |
| --- | --- | --- | --- |
| `continue_db`（"继续聊 SQLite 迁移"） | in_topic | in_topic ✅ | new_topic ❌ |
| `embedding_continue` | in_topic | new_topic ❌ | new_topic ❌ |
| 其余 10 条 | — | 一致 | 一致 |

检索：两条路径的第 1 名命中数相同（6/8），但**错的是不同的两条**。

| 用例 | 期望 | 默认路径第 1 名 | 内置模型第 1 名 |
| --- | --- | --- | --- |
| `preference` | `pref_spicy` | 没有召回任何候选 ❌ | `pref_spicy` ✅ |
| `stale_knowledge` | `deploy_current` | `deploy_old` ❌ | `deploy_current` ✅ |
| `person_entity` | `person_xiaolin` | `person_xiaolin` ✅ | `chatter_p1`（"今天开了很久的会"）❌ |
| `cross_topic_recall` | `travel_plan` | `travel_plan` ✅ | `work_note`（"本周要完成接口联调"）❌ |

`person_entity` 与 `cross_topic_recall` 是同一个现象：向量召回把「更新近但不相干」的条目
也带进了候选，而排序里的时效项把候选推到了第一位。这两个用例的正确条目分别有 60 天
和 45 天，被 1 天前的闲聊挤掉。

## 这些数字能说明什么、不能说明什么

能说明：

- 真实模型确实比关键词路径多召回（前 5 名命中 0.875 → 1.00，陈旧知识注入 0.125 → 0）。
- 话题判定上的 `new_topic_threshold = 0.7` 对真实模型偏严：「继续聊 SQLite 迁移」这类
  明确延续的短句会落到阈值以下，被判成新话题。
- 排序权重（相关性/时效/亲和）是在「关键词召回候选很少」的前提下调的；换成向量召回后
  候选变多，时效项的相对影响变大，需要重新校准。

不能说明：

- 用例是当初实现时写的，不是独立标注；`in_topic` 只有 4 条，一个用例就能让准确率
  动 0.25。这些数字是「改动前后对照」，不是生产准确率。
- 锚点延续那套没接模型，本次不对它下任何结论。
- 单机、单盘点、fp32 档位；换模型、换精度、换机器都要重跑。

## 下一步（各自独立，本次都没做）

1. 校准话题判定的阈值：现在 0.7 / 0.3 / 0.55 是按关键词层的量纲偏保守定的。
2. 校准检索排序权重：候选来源从关键词换成向量后，相关性/时效/亲和的比例需要重新算。
3. 扩用例集：现在的规模（12 / 8）只够发现方向性问题。
4. 需要时再评估「在向量召回之上加一层重排」——那是另一个议题（例如 Jev 类判定模型），
   与本文的基线无关。
