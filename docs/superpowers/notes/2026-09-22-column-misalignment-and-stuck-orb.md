# 输入区错位 + 入口球被压住（2026-09-22）

用户报的是两个现象，实测是同一类问题的两条路径：

1. 「不同窗口大小下 UI 严重错位」；
2. 「星球没办法进行移动」（入口球点不到、也拖不动）。

## 现场测量（安装包默认窗口 1200×800，生产构建）

| 窗口 | 消息列 `.turn` | 输入区 `.composer` | 列偏移 | 右边缘溢出 |
| --- | --- | --- | --- | --- |
| 1200×800 | 116 – 976 | 534 – 1394 | **418px** | **194px** |
| 1000×700 | 24 – 868 | 434 – 1266 | **410px** | **266px** |
| 1440×900 | 290 – 1150 | 290 – 1150 | 0 | 0 |
| 1920×1080 | 530 – 1390 | 530 – 1390 | 0 | 0 |

球被压住的证据（同一批测量，把球拖到右下角后做命中测试）：

| 窗口 | 球中心命中元素 | 再拖 |
| --- | --- | --- |
| 1200×800 | `textarea.qio-input`（输入区） | 位移 0px |
| 1000×700 | `textarea.qio-input` | 位移 0px |
| 1440×900 | `button.dock`（球自己） | 位移 258px |

## 根因

1. **输入区手算偏移**（`Composer.vue`）：900–1400px 区间用
   `left: calc(50% - 66px)` + 860px 宽，漏了「半个列宽」这一项，于是整条气泡从
   正文列里滑出去、右边缘越过视口；窗口越窄越糟（1028px 附近溢出 280px）。
2. **球可以停在别人的底下**（`useFloatingWindow`）：贴靠只避让「已贴靠的浮动组件」。
   输入气泡不是浮动组件（z-index 12、不透明底），球贴到底边就藏在它下面；
   窄窗口里底边被输入区占满后，球改停右上角，又压到设置齿轮底下 —— 同样是点不到。

## 修法

- `tokens.css` 新增 `--column-inset-left/right`（≤1400px 右值 132px = 入口球通道）；
  消息流 `.stream` 的内边距与输入区 `.composer` 的 `left/right` 都读这一对令牌，
  输入区不再手算 `calc(50% - Npx)`（宽屏 860px 列仍由 `max-width` + `margin: auto` 居中）。
- `useFloatingWindow` 新增 `avoidSelectors`：贴靠（含窗口变化、挂载恢复）时把
  `FLOAT_AVOID_SELECTORS`（`.composer`、`.settings-float`）当成障碍；
  旧版本已把球停在输入区底下的用户，启动时会被自动挪出来（否则升级后仍然点不到）。

## 验证

- 单元测试（先红后绿）：`design-guards.test.ts` 的列令牌守卫、`useFloatingWindow.test.ts`
  的「拖到底边不压在输入区上 / 窗口变化后让开 / 挂载恢复自愈 / 窄窗口不落到齿轮底下」。
- 浏览器实测（生产构建，Playwright + 真实后端）：四个尺寸列偏移与右溢出全部为 0，
  球在四种尺寸、窄窗口三档、以及「旧位置卡住」的恢复场景下都 `hitsDock: true` 且可点开。
- 星球页本身可拖动（拖动前后像素差 5–10，静止基线 0），即「星球移不动」不是 3D 交互坏了。

## 追加（同日）：第二个「星球点不动」的成因 —— 进出设置页

用户指出球的死锁更像是「打开或关闭设置页」造成的。复现确认，这是**独立的第二条路径**：

- 星球开着（`phase = ready`，或正在长大）时离开对话页（切设置页 / 路由切换），
  PlanetView 被卸载，但 `planetContinuum` 是**模块级单例**，没有任何路径把阶段收回 idle；
- 回到对话页后 phase 仍是 `ready` → PlanetDock 的 `handedOff` 恒为 true →
  `.dock.handed { opacity: 0; pointer-events: none }`：球看不见、点不到，而且**再也打不开**
  （实测：球心命中 `div.stream`，点击 2.5s 超时）。宽屏下输入区并没有压住球，
  所以这条路径与上面的气泡问题互不覆盖。
- 同一条路径还暴露出一个 setup 期错误：`watch(ballMode, …, { immediate: true })` 读了
  之后才声明的 `closing` / `settling` → `Cannot access 'closing' before initialization`。
  首次加载时 `ballMode=false` 走不到那一行，所以只有「从设置页回来（`ballLive` 已是 true）」
  才触发；错误被 Vue 的错误处理吞掉后，球态分支的后半段（对齐入口、跟随入口拖动、
  刷球态数据）全部不执行 —— 也就是「回来之后小球不再跟着入口走」。

修法（`planetContinuum.ts` + `PlanetView.vue`）：新增 `abandonContinuum()`
（阶段回 idle、清 origin/target、`epoch + 1` 让被打断的转场续行失效、`ballLive → false`
把入口交回 2D 压缩态），在 PlanetView 的 `onUnmounted` 里调用；并把 `closing` / `settling`
的声明提到球态 watcher 之前。

验证（生产构建 + 真实后端，Playwright）：三种时机（长大中 150ms / 尾段 600ms / 完全打开）
离开再回来，球都是 `dock`（非 handed）、opacity 1、可命中，点击后 `.planet-view.layers`
重新出现，页面错误为空。单元测试 4 条（先红后绿）：`planetContinuum` 离场收尾两态、
PlanetView 卸载收干净、球态重挂载仍跟随入口。

## 追加（同日）：第三个成因 —— 收起被打断后，球停在收缩起点的尺度（「球变成一个点」）

用户在开发实例里实测：「星球打开又缩小后消失了」。读他那个标签的实时状态：

| 项 | 值 |
| --- | --- |
| `.planet-view` class | `planet-view entered ball`（球态） |
| 舞台 `--stage-k` | **0.075**（正常球态 ≈ 1.0） |
| `.planet-canvas` 矩形 | **8 × 8 px**（球布局下画布是 108px，被 0.075 乘成了 8px） |
| 入口球 | `dock`，opacity 1，可命中（按钮一直在，只是里面没东西） |

机制：体量收缩的第一步会把舞台摆到「入口半径 ÷ **整窗画布**上的球体半径」（1513 宽的窗口里
正好 ≈ 0.075）。如果这一步之后球态接管了（父级把 `open` 置回 false），而 `.ball` 还没落到
DOM，那么按整窗几何算出来的尺度会留在舞台上；画布下一秒变成 `--ball-size`（108px），
球就被乘成一个**几个像素的点** —— 用户看到的就是「星球消失了」。
球态自己的对齐（`syncBall`）本来会覆盖它，但它可能更早跑过一次（那时画布还是整窗尺寸），
之后再没有任何触发点去纠正。

修法：球态不再无条件立刻对齐，而是先确认「画布已经是球尺寸」——没到位就等下一帧
（上限 4 帧）再对齐一次（`syncBallWhenLaidOut`）。球态的三条入口
（setup 里的球态 watcher、`props.open` 变 false、`onMounted` 的球态分支）都改用它。

验证：

- 单元测试先红后绿：`PlanetView` 里复现「收缩起点 0.16 被留下」的序列，
  断言进入球态后必须回到 ≈1（修复前 0.16，修复后 ≈1）。
- 浏览器浸泡（生产构建 + dev）：两种窗口尺寸 × 5 轮「打开 → 在动画中途/结束后收起」，
  10 轮全部 `k=0.91`、画布 98px、球心与入口**偏差 0px**、无页面错误。
- 用户那个卡住的标签在代码热更新后当场自愈：`k` 从 0.075 回到 1，画布 108px 正对入口。
