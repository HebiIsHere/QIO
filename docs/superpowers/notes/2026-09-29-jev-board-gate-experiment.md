# Jev 能否承担 QIO 互动板的低成本语义 Gate —— 实验报告

**日期：** 2026-09-29　**实验目录：** `C:\Users\zxy\Documents\Front agent\jev-board-gate`
**问题：** Jev 是否能够可靠判断“当前互动板变化是否值得让 QIO 主模型重新理解”。

**结论摘要（先给答案）：** Jev 的**二分类**行为很干净（从未误升级、升级精确率 1.00、三种表达判断一致），
但**三分类里的 WATCH 不可靠**（准确率 0.58–0.78），在完整比较下也**没有比一份不刻意做弱的简单规则
基线提供足够的额外价值**（总准确率 0.818 vs 0.849）。详见 §11。

## 1. Jev 的实际调用方式

| 项 | 值 |
| --- | --- |
| 模型 | `typesafe/jev-1.13`（服务端实际返回 `typesafe/jev-1.13-20260917`） |
| 接口 | OpenRouter decisions：`POST https://openrouter.ai/api/alpha/decisions` |
| 请求体 | `{"model", "state": <Board Representation>, "questions": {"gate": {...}}}` |
| 问题类型 | `choice`，标签空间由我方固定为 `IGNORE / WATCH / ESCALATE` |
| 输出 | `answers.gate = {type, choice, probabilities{IGNORE,WATCH,ESCALATE}, confidence}` |
| 概率是否可用 | 可用。每次判断都完整记录了三个概率与 `confidence`（见 `runs/*/cases.jsonl`） |
| 密钥 | 只从环境变量 / Windows 用户注册表读取，未落盘、未打印 |
| 客户端 | 只读复用 QIO 仓库的 `backend/src/agent/eval/jev_client.py`（未改动 QIO 任何代码） |

实测一次 `choice` 返回样例（输入 584 token）：

```json
{"gate": {"type": "choice", "choice": "ESCALATE",
          "probabilities": {"WATCH": 0.36, "ESCALATE": 0.38, "IGNORE": 0.26},
          "confidence": 0.07}}
```

注意：Jev 自带的 `confidence` 字段可以低到 0.07 而仍然给出标签，因此**不能拿它当校准量**；
本实验用 `max(probabilities)` 作为置信度（§4.4），并单独说明 `confidence` 的表现。

### Jev 在这套实验里被允许多做什么

只做一件事：判断“已结构化的板面变化是否值得让主模型重新理解”。Prompt 明确禁止它推断用户真实意图、
解释变化含义、生成 QIO 行动或板面操作。Ground Truth 的 `reason` 从未进入 Jev 的输入。

## 3. Ground Truth 方法

人工判定，依据三条**只用客观板面元数据**的标准（`card.role` 与 `qio_intent.depends_on`
是板面自身的结构字段，不是语义推断）：

1. 变化触达 **QIO Intent 依赖项**或**结论级对象/关系**（文本实质改变、删除、新增关键关系、
   用户显式接受/拒绝/修改 Intent、关键材料移出显式分组）→ **ESCALATE**
2. 只有布局（区内顺序/位置）、`churn` 计数、与任务无关区域的素材整理 → **IGNORE**
3. 触及相关但既非依赖项也非结论（新增证据、修改中间结论、关系多轮未定型）→ **WATCH**

开发集 / 测试集物理分离；Prompt 与阈值的选择只看开发集，选定后冻结，再在测试集上出最终数字。

## 6. Representation 敏感性

13 个场景 × 3 种表达（时间顺序 / 按对象组织 / 状态差异）= 39 次判断。

| 集合 | 有多表达的场景 | 三种表达判断一致的场景 | 一致率 |
| --- | --- | --- | --- |
| 冻结测试集 | 4 | 4 | **1.00** |
| 开发集 | 9 | 9 | **1.00** |

**Jev 对序列化形式不敏感**，这是它表现最好的一项。但要区分稳定性与正确性：
在“变化很多但全是布局”（探针 8）和“等价 delta 换顺序”（探针 9）两类场景里，
Jev 三种表达**一致地答错**（8: 3/6 错，9: 3/4 错）。问题不在表达，在判断本身。

## 7. 与简单规则 Baseline 的比较（关键一节）

基线规则只用输入里客观存在的字段（`src/board_gate/rules_arm.py`，约 40 行，无模型）：
文本是否改动、显式关系是否增删、分组成员是否变化、是否触及 `qio_intent.depends_on`、
被改对象是否是结论卡（`role == conclusion`）、其余是否只是布局与 `churn`。

完整语料（n=126）对比：

| 指标 | Jev B（校准） | 简单规则 | 谁更好 |
| --- | --- | --- | --- |
| Accuracy | 0.8175 | **0.8492** | 规则 +3.2pp |
| ESCALATE Recall | **0.8936** | 0.8723 | Jev +2.1pp（= 1 例） |
| ESCALATE Precision | 0.8235 | **0.8542** | 规则 +3.1pp |
| False Escalation Rate | **0.0000** | 0.0233 | Jev（差 1 例） |
| False Negative Rate | **0.1064** | 0.1277 | Jev（差 1 例） |
| WATCH Accuracy | 0.6389 | **0.8056** | 规则 +16.7pp |
| 成本 / 延迟 | $0.0765 / 千次，554 ms | $0，~0 ms | 规则 |

分场景看，差距集中在 C 类（WATCH）：Jev 准确率 0.583，规则 0.833；D 类（长时间跨度）
规则 1.00，Jev 0.789。

**在“输入已经结构化到包含 `role` 与 `depends_on`”的前提下，Jev 没有提供足够价值。**
它在两个尾部指标（不误升级、少漏报）上各好 1 例，这在 n=126 上属于噪声；在总准确率和
WATCH 上明显更差，而且每次判断要多花 554 ms 与 $0.0000765。冻结测试集上两者只差 1 例，
方向还刚好相反（Jev 0.929 vs 规则 0.893）——进一步说明**两者无法区分**。

必须说明的前提：这条规则之所以强，是因为 Board Representation 已经把 `role`（结论/中间结论）
和 `intent.depends_on` 直接给了它。如果这两项在真实系统里需要靠语义推断才能得到，
规则就会退回到“变化多就升级”的粗糙形态，Jev 的相对位置会明显改善。这是本结论最脆弱的假设。

**最刺眼的发现：强模型在做这个判断时完全不使用 WATCH。** 28 条里它给了 19 个 ESCALATE、
9 个 IGNORE，一个 WATCH 都没有——9 条真实 WATCH 案例全部被判成 ESCALATE。
它有最高的召回（1.0），但精确率因此掉到 0.526，代价是每次要等 12 秒、贵 30 倍。

双方在 28 条中有 10 条判断不一致，几乎全部集中在 WATCH 案例（强模型升级、Jev 保留观察）。
这组数据的意义不是“Jev 比强模型聪明”，而是：

1. **“需要一个便宜的 Gate”这个前提成立** —— 直接把主模型放在板面变化的前面，既慢又贵，
   而且三分类能力并没有因此变好；
2. 但**满足这个前提的不止 Jev 一个**（见 §7）。

另需记录一个过程性失败：第一版强模型调用（`max_tokens=512`）有 10/28 条返回空内容
（推理 token 吃满输出预算），且解析会把推理过程中的标签误当结论，当时得出的准确率是 0.429。
把 `max_tokens` 提到 2500、改为从末行取标签后才是 0.679。**只看第一版会得出错误的“强模型很差”结论。**

## 10. Jev 的能力边界

**适合：**

- 单调二分类 `ESCALATE / DO_NOT_ESCALATE`：精确率 1.00、误升级率 0.00（完整语料与冻结测试集一致）。
- 结论被改写 / 被删除（探针 3 错误率 0，含“只加一个否定词就反转结论”）。
- 长时间跨度之后发生的显式结构变化（D 类 ESCALATE 召回 1.0）。
- 表达形式不敏感（13/13 场景三种表达一致）。

**不适合：**

- **WATCH 这一档**。C 类准确率 0.583，WATCH 准确率 0.58–0.78；错误双向发生
  （布局→WATCH 17 例、中间结论→ESCALATE 8 例、WATCH→IGNORE 2 例）。
- **“什么都不用做”的判断**。纯布局 / 拖动 / churn 的 IGNORE 场景错误率 47.6%，
  这是它最大的系统性缺陷，也是与规则基线差距的主要来源。
- **结构性位移**（移出分组、移出区域）：4 例全部漏报。
- **用户显式接受 Intent**：判成 IGNORE，且置信度 0.70。

| 说明里的追问 | 回答 |
| --- | --- |
| 是否只能做二分类 Gate？ | 按当前证据，**是**。三分类的 WATCH 不可靠。 |
| 是否足以支持 WATCH？ | **不足以**。要么把 WATCH 交给规则/主模型，要么取消这一档。 |
| 能否处理轻量跨轮状态？ | 证据不足。探针 4 上 7 例全对但规模太小；真正带上 `previous_gate_context` 的 Prompt C 反而更差（acc 0.633 / recall 0.730 / FER 0.147），说明“给历史”与“会用历史”是两回事。 |
| 哪些情况必须直接交给主模型？ | 分组成员变化、区域级位移、用户对 Intent 的显式接受/拒绝/修改——这四类 Jev 都出现过漏报。 |

## 11. 最终结论

**主选结论：Jev 与简单规则相比没有足够价值。**

支撑证据：

1. 完整 126 条上，40 行规则基线的总准确率更高（0.849 vs 0.818）、WATCH 准确率高 16.7pp、
   精确率更高，而成本与延迟都是零。Jev 占优的两项（误升级、漏报）各只差**一例**，
   在 n=126 上不可区分。
2. Jev 唯一稳定且系统性的优势是“从不误升级”（FER 恒为 0）与三种表达判断一致；
   这两点不足以抵消它在 WATCH 与 IGNORE 上的大幅劣势。
3. 冻结测试集上两者只差一例，方向还相反（Jev 0.929 vs 规则 0.893），
   95% Wilson 区间宽达 ±0.15——**测试集本身无法支撑“Jev 更好”的说法**。

**最接近的备选结论（第二顺位）：Jev 可用，但仅适合更窄的二分类 Gate。**
若 QIO 最终只要“该不该叫醒主模型”这一个开关（明确放弃 WATCH 中间态），Jev 的表现是合格的：
精确率 1.00、误升级 0.00、升级召回 0.894，每次 554 ms / $0.0000765。改为这一条的触发条件是任一：

- Board Representation 不再直接提供 `role` 与 `intent.depends_on`（此时简单规则会显著退化）；
- 需要开放语义（而非字段判定）的能力，例如判断一条新证据是否挑战了现有结论；
- 未来“误升级”的代价远高于“漏报”（例如主模型调用极贵），此时 FER=0 的价值被放大。

**明确不成立的结论：**

- 不能说“Jev 非常适合成为 Board Gate”——WATCH 与 IGNORE 的错误率不允许。
- 不能说“Jev 漏报过多”——升级召回 0.894、漏报率 0.106，与规则持平，不是主要问题。
- 不能说“当前 Board Representation 不足以判断 Jev”——三种表达下判断完全一致。
