## Task 2：查证成功后按原提交归组（batch-owner）
**Files:** `frontend/src/stores/interactive.ts`（confirmAcceptanceAfterUnclear / refreshAfterSubmit / recordNewIntents / SubmitRefreshContext / deferred 类型）、`frontend/src/stores/__tests__/q46-r8-submit-ownership.test.ts`（或新建 q46-r10 用例文件更合适时可加，但优先扩展既有）。
**行为:**
1. `confirmAcceptanceAfterUnclear(ownerBoardId, baseline?)`：submit 内调用时传入**发起提交时冻结的 intentsBefore**；页面重载恢复（restorePendingSubmission）没有基线时传 null。
2. 查证成功后的刷新上下文带 `submissionId = acceptance.submissionId`：owner 当前时 `refreshAfterSubmit(owner, baseline ?? intentIdSet(), lookupBatchKey, {submissionId})`；owner 不在当前时 `deferredRefreshAfterSubmit` 同时保存 baseline 与 submissionId（不能再写死空基线）。
3. `recordNewIntents(before, batchKey, submissionId?)`：有 submissionId 时只把「服务端明确归属本次提交（intent.submissionId === submissionId）」的意图记入本批；无归属字段的意图只在 baseline 非空（可信增量）时按增量保留。旧任务不得被写进本次批次的本地映射。
4. 后端只受理一次：查证路径不得重复 POST（沿用既有身份查证）。
**测试（红在 _q46-r10-baseline）:** B 提交回执丢失 → 在 A 查证成功 → 切回 B：B 的旧任务保持原批次（不进入本次批次），本次新任务归入本次提交；submitBoard 只调用 1 次；recordIntentBatch 只收到新任务与本次 batchKey。

## Task 3：撤回提示跟随原板与最终结果（cancel-retry-ui）
**Files:** `frontend/src/components/interactive/v2/ImpactConfirmLayer.vue`、`frontend/src/stores/interactive.ts`（settleCancelRecovery / retryCancelRecovery 及迟到失败路径）、`q46-r8-select-cancel.test.ts`、`ImpactConfirmLayer.test.ts`。
**行为:**
1. 组件点「重新核对」时冻结 `ownerBoardId = store.boardId`、`opSeq = store.cancelRecovery?.opSeq`；结果回来只更新这次操作：`outcome.boardId = ownerBoardId`，当前板不是 owner 时不显示（A 不出现 B 的提示），切回 B 才显示；opSeq 已被新撤回替换时丢弃旧结果。
2. 结果以 store 事实为准：同一次撤回 `active === false`（已确认）时，即使本次 retry 返回失败，也显示已取消，不重新显示等待/失败。
3. store：迟到失败只影响对应 opSeq 且不得把已确认（active=false）的撤回重新打开；`retryCancelRecovery()` 在请求失败但该 op 已被同板采纳读取确认时返回 ok:true（不谎报废）。
**测试（红在 _q46-r10-baseline）:** ①B 点重试后切 A：A 不出现 B 的提示，回 B 才显示结果；②同一次撤回已确认后旧请求失败：不重新显示等待/失败，retry 返回 ok:true（或至少 state 保持已确认）；另保留 r9 的旧版本/缺版本/切板/同板连续撤回用例。
