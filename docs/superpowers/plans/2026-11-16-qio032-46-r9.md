### Task 1: 桌面全机单实例（shell-lock）
**Files:** 见上（Rust + updater 前端链路 + install_e2e_multi.py）
**Interfaces（实现须提供）:**
- `single_instance::acquire() -> Acquire`，`Acquire::Primary(Guard) | Acquire::Duplicate { same_session: bool }`；锁名与安装路径/账号/会话/提权/版本无关（Global、产品级 v1）。
- `single_instance::signal_activation() -> bool`（同会话把已有实例的激活事件置位；打不开=true 不同会话/未就绪）。
- `single_instance::spawn_activation_listener(app)`：主窗口就绪后处理挂起激活（show_main_window + unminimize + focus）。
- `single_instance::arm_relaunch_handoff()` / `try_wait_for_relaunch_handoff(max_wait)`：更新重启时新进程先等旧进程退出释放锁，再正常启动。
- `qio_arm_relaunch` Tauri 命令（IPC 内部调用，capability 用 core:default 即可）。
**行为:**
1. `main()` 第一行取锁；未取得时**不得**创建 job/写日志探针/删令牌/建窗口/拉后端。同会话 → 登记/触发激活并 exit 0；不同会话 → 可关闭 MessageBox「QIO 已在此电脑运行」并 exit 0。
2. 首个实例在取锁后立即创建激活事件；窗口就绪后监听；手动重置事件保证「首个实例仍在启动时」的激活不丢。
3. 锁持有到进程退出（正常/崩溃由内核释放）；托盘隐藏、更新停/恢复后端期间不释放；更新交接路径见接口。
4. `note_and_prune_instances` 保留为诊断（措辞改为锁已保证单实例），lease/后端端口职责不变。
5. 同会话重复启动第 2 个进程可短命正常退出；判定标准是**没有第二套应用**（无第二窗口/第二后端/第二份运行记录）。
**TDD 证据:** `src/tests_single_instance.rs` 用 `QIO_INSTANCE_PROBE` 环境变量让 qio.exe 只走锁/激活/交接逻辑后退出：① 第一个 primary；② 第二个 duplicate+激活信号；③ 交接：旧实例置 handoff 后延迟退出 → 新实例等待后成为 primary。另加 `cargo test`（受影响的 Tauri 测试）与 `cargo check`。
**验收脚本:** 默认用例：装 A/B → 启动 B（活动）→ 启动 A（被拦截，无第二 shell/backend/lease）→ 卸载非活动 A 不影响 B → 卸载活动 B 按其进程归属关闭并清目录；保留既有按进程归属核验逻辑。

### Task 3: 提交后回读只归发起板（async-owner，与 Task 4 同一负责人顺序执行）
**Files:** `interactive.ts`（submit 区 / refreshAfterSubmit / retrySubmitRefresh / load 延后分支）、`q46-r8-submit-ownership.test.ts`
**行为:**
1. 新增按板刷新代次（Map<boardId, number>）；`refreshAfterSubmit(ownerBoardId, intentsBefore, batchKey)` 入口冻结板面 / 提交身份 / 批次 / 代次。
2. 整板、可见范围、任务清单、新增任务批次全部用同一上下文：每步 await 后校验代次与板面；离开原板时未开始步骤写回原板会话 `deferredRefreshAfterSubmit` 延后；已返回真实失败经 `patchSubmissionFor(owner,...)` 归原板；新代次不接受旧代次写入。
3. 明确检查子读取返回值：`refreshBoardFromServer` 未采纳（false）、`refreshVisibleRange`/任务读取失败对象都视为本次未完成；只有实际采纳的刷新才把状态置 idle。`load()` 消费延后刷新时也走同一入口。
4. `retrySubmitRefresh()` 复用原板会话冻结的上下文；点击后立刻切板不得在 A 写状态、不得对 A 发读取。
**测试（先红后绿）:** B 回读在 A 显示时失败（A idle / B 回 B 后 error）；B 回读在 A 显示时成功（A 不变，B 回 B 后 idle）；B→A→B 后新刷新成功而旧刷新迟到失败（旧代次不覆盖）；B 点重试后立刻切 A。断言请求目标（fetchBoardState/fetchVisibleRange/fetchIntents 的 boardId 参数）、两块板状态、批次归属、submitBoard 只调用一次（后端受理事实在 store 层的等价断言；浏览器/后端层另记）。

### Task 4: 撤回重试只在服务器事实确认后报成功
**Files:** `interactive.ts`（settleCancelRecovery / refreshBoardFromServer 采纳记录 / retryCancelRecovery / 保存回执结算）、`q46-r8-select-cancel.test.ts`
**行为:**
1. `refreshBoardFromServer` 记录**实际采纳**的读取事实 {readSeq, seq}（仅两个采纳分支；旧读取/只合并草稿不记录）。
2. `settleCancelRecovery`：成功必须带有效有限 seq 且达到当次 expectSeq；缺版本/旧版本/响应废弃/操作被替换 → 不结算成功（保持等待或可重试结果）。修正保存回执里 `Number(result.seq)` 可能 NaN 绕过校验的调用。
3. `retryCancelRecovery()` 捕获本次读取起始 readSeq，只有「本次读取被采纳 + readSeq 前进 + seq>=expectSeq + opSeq 匹配」才结算成功并返回 ok:true；否则返回可重试失败并保留「重新核对」入口；不得用界面缓存 knownServerSeq 冒充。
4. 迟到成功/失败只影响对应 opSeq；满足条件只结算一次并清除重试提示。
**测试（先红后绿）:** expectSeq=7/返回6 仍待核对 → 返回7或更高才完成；版本缺失不完成；切板后读取不结算本板；同板连续两次撤回旧成功/旧失败迟到不关新撤回；同时断言 retry 返回值与界面等待状态。
