## 0. 一句话结论

**没有达到发布级别。** 三个独立原因，任何一个单独成立都足以拦住发布：

1. **产不出被应用信任的更新签名**（第 1 节）：本机的 `dist/qio-updater.key` 带口令加密，
   空口令被明确拒绝；口令不在这台机器上。任务书禁止伪造 `.sig` / `latest.json`，
   所以本次交付的是**显式标注的未签名测试产物**，不是发布资产。
2. **安装/卸载的注册表登记路径在本机无法验证**（第 5 节）：本会话给子进程的是受限令牌，
   安装器的 `WriteRegStr` 与卸载器的 `DeleteRegKey` 都是 `ACCESS_DENIED` 且静默失败。
   文件层（装/删/数据保留）验过了，注册表层没有。
3. **GUI 层完全没有驱动**（第 8 节）：Tauri WebView 不开 CDP，本次全部走 HTTP API。
   界面上的步骤必须人工做。

可以放心说出口的部分：**安装包能从当前源码构建出来，装出来的是这一版的后端与模型，
首启能起、能对话、能走完「创建工具 → 写文件 → 跑测试 → 审批 → 注册 → 调用 → 查记录」，
重启后任务/授权/会话/工具都还在，重装与卸载都不动用户数据，且整个过程没有碰坏本机既有的 D:\QIO 安装。**

## 1. A1：更新签名口令实验（结论：本机产不出正式签名产物）

### 做的是什么

不是猜口令，是**实验**。三条独立证据：

```
$ npx tauri signer sign -f "C:\Users\zxy\Documents\Front agent\dist\qio-updater.key" -p "" probe.bin
incorrect updater private key password: Wrong password for that key
sig produced: False
```

```
# 结构性证据：把 .key 解开两层看内层布局
file bytes: 348
line[0] len=45: untrusted comment: rsign encrypted secret key     <- 注释里就写着 encrypted
inner secret-key blob bytes: 158
  alg: Ed    blob[0:2] = b'Ed'  blob[2:4] = b'Sc'
```

```
# 对照实验：新生成一把**带口令**的钥匙，看布局是不是同一形状
$ npx tauri signer generate -w probe.key -p probe
probe.key: blob=158 head=4564536342322fa9dace1ec8f4fe2cf4   <- 长度与开头 `Ed`+`Sc` 完全一致
probe.key.pub: blob=42 head=4564528bfd43c27d8c333af44a2317bf
```

### 结论

* **这把私钥是口令加密的**，空口令（以及"不给 -p"）都被拒；口令本机不存在
  → **本机产不出正式签名的更新产物**。这是设计限制，不是缺陷。
* 顺带核对了配对关系：`dist/qio-updater.key.pub` 与 `tauri.conf.json` 内嵌公钥
  都是 `key id = 5af7e96c8e24bf8b`（`Ed`/`RWT...`，逐字节一致）——**公钥这一侧是对得上的**；
  `dist/QIO_0.1.10_x64-setup.exe.sig` 的 key id 也是 `5af7e96c8e24bf8b`。
* **私钥与公钥是否成对，本次无法证明**：私钥内层是加密结构，keynum 字段位置被 KDF 参数占用，
  我无法在不解密的情况下读出它的 key id。拿到口令后必须补这一枪（`tauri signer sign` 出的签名
  key id 必须等于 `5af7e96c8e24bf8b`，`release_gate.py` 已经在查这一条）。
* 任务书明确禁止手工伪造 `.sig` / `latest.json.signature` 让闸门变绿 —— 本轮**没有**那样做。
  产物改用显式标记的未签名通道：`scripts/build_installer.ps1 -UnsignedTestArtifact`
  （名字强制带 `-UNSIGNED-TEST`，不写 `.sig`，不更新 `latest.json`）。

| 需要的东西 | 谁有 | 用在哪 |

## 2. 上一轮「静默安装装不上」的三个假设：逐条证伪

Lead 给了 H1（升级分支忽略 /D=）、H2（参数形式）、H3（不可见窗口/UAC）。我先**读到了上一次构建
真正用过的 NSIS 脚本**（`frontend/src-tauri/target/release/nsis/x64/installer.nsi`，942 行），
再用自己编译的最小安装器做对照实验 —— 不是靠猜。

### 已核实的事实

* `INSTALLMODE = "currentUser"`（installer.nsi:39）→ `RequestExecutionLevel user`
  → **不弹 UAC**。H3 的 UAC 假设不成立。
* `.onInit` 只在 `$INSTDIR` **仍等于占位符**时才写默认目录并调用 `RestorePreviousInstallLocation`
  （installer.nsi:489）→ **传了 /D= 就不会被既有安装的 InstallLocation 覆盖**。H1 不成立。
* 既有安装是 **0.1.9**（`HKCU\...\Uninstall\QIO` DisplayVersion），本次是 **0.1.10**
  → 走的是"升级"分支；该分支上默认选中的单选项正是**"卸载旧版再装"**（installer.nsi:236-239、327-332），
  一旦执行就会调用 `"D:\QIO\uninstall.exe" ... _?=D:\QIO`（installer.nsi:349-354）。
  这是本轮最需要小心的地方。

### 对照实验（makensis 现场编译）

```
$ makensis /V2 probe2.nsi       # Page custom CustomPage CustomLeave + Page instfiles，Section 里写日志
$ probe2.exe /S /D=C:\...\.e2e-work\probe2-out
exit: 0
LOG: EVT=Section INSTDIR=[C:\...\.e2e-work\probe2-out]
installed.txt: True
```

日志里**只有 Section 那一行**：`.onInit` 的日志与 `CustomPage`/`CustomLeave` 的日志都没有出现
（后者在 Section 之前，如果被调用必然留痕）。同一形状又用**含空格**的路径复测了一次，结果相同。

### 结论（三条假设的判定）

| 假设 | 判定 | 依据 |
| --- | --- | --- |
| H1 升级分支忽略 /D= | **证伪** | `.onInit` 用"$INSTDIR 是否还是占位符"来判断有没有传 /D=；实测 /D= 生效 |
| H2 参数形式 | **部分成立，但不是根因** | /D= 必须最后一个、**不能带引号**；含空格路径用"裸值命令行"形式实测可用 |
| H3 不可见窗口/UAC | **证伪** | `RequestExecutionLevel user`，无需提权；静默模式下 `CheckIfAppIsRunning` 直接 `IfSilent kill`，不弹窗 |

**静默模式下 `Page custom` 的回调根本不会被调用** —— 这同时解释了上一轮的两个现象：
既没有生成安装目录（我以为的"跑完了"其实没有），也没有"升级→卸载旧版"分支被执行。
上一轮失败最可能的原因是**调用形式**（`Start-Process -ArgumentList` 数组把 `/D=` 处理得和裸命令行不同），
而**不是**安装器逻辑。本轮改用裸命令行形式（`scripts/install_e2e.py::install_cmdline`），
`/S /D=<路径>` 一次装成，实测 exit=0。

### 影响：这条结论是安全的基石

因为"升级/重装页在静默模式下不执行"，所以**只要用静默安装，就不会去卸载既有安装**。
我没有停在这里讲道理，而是做成了可执行的实验放进 E2E：**诱饵实验**（`install_e2e.py` 的 A-009/A-010）——
把注册表里的"既有安装"临时指向一个诱饵目录（里面放一个会写日志的假 uninstall.exe），
再跑真实的安装器，然后看假卸载器有没有被执行。整个 E2E 期间注册表都停在诱饵上，
**D:\QIO 从来不是安装器的目标**；结束时还原注册表并逐文件比对 D:\QIO 的 sha256。

## 3. 构建：能出包，但要先钉住 TEMP

```
$ npm run tauri build -- --bundles nsis --config tauri-unsigned.json
    Finished `release` profile [optimized] target(s) in 5m 55s
    Running makensis to produce ...\bundle\nsis\QIO_0.1.10_x64-setup.exe
113471006  QIO_0.1.10_x64-setup.exe
```

**踩到的坑（已写进脚本头部注释与 `-TempDir` 参数）**：把 `TEMP` 指到 D: 盘上的临时目录时，
vite 会在最后一步炸：

```
[vite:esbuild-transpile] remove D:\qio-e2e-tmp\esbuild-dfaa06...: Access is denied.
beforeBuildCommand `npm run build` failed with exit code 1
```

同一台机器、同一份源码，把 `TEMP` 换成**检出内 C: 盘的 `.build-tmp`** 后 `npm run build` 立刻成功。
所以"可写的 TEMP"还不够：**TEMP 要在 C: 盘上**。`build_installer.ps1` 现在自己钉 `-TempDir`（默认
`<检出>\.build-tmp`），避免下一个人再撞一次。

## 4. 沙箱事实（决定了本轮能验到哪一层）

本会话给**子进程**的是受限令牌（AppContainer 形状）。PowerShell 自己不受限，但它启动的任何东西受限：

| 操作 | PowerShell 自己 | 它的子进程（python / 安装器 / 后端子进程） |
| --- | --- | --- |
| 写检出内的文件 | ✅ | ✅ |
| 写检出外的文件（`C:\Users\zxy\...`、`D:\...`） | ✅ | ❌ `WinError 5` / `Errno 13` |
| 写注册表（`HKCU\Software\...`） | ✅ | ❌ `WinError 5` |

实测（同一把 key、同一个用户，只差"谁在写"）：

```
PS REG OK
PY REG DENIED Software\qio-e2e-probe :: PermissionError [WinError 5] 拒绝访问。
```

这条事实有两个直接后果：

1. **E2E 的工作目录必须放在检出内**（脚本默认 `<检出>\.e2e-work`）。这也是我最后放弃
   `C:\Users\zxy\qio-e2e` 的原因 —— 不是权限没配好，是沙箱在拦。
2. **装出来的后端在启动阶段会崩**，因为启动自检要把数据库基线写进注册表：

```
File "agent\storage\db_identity.py", line 415, in check_integrity
File "agent\storage\db_identity.py", line 300, in _write_baseline
File "agent\storage\db_identity.py", line 108, in write
PermissionError: [WinError 5] 拒绝访问。
[PYI-115212:ERROR] Failed to execute script 'main' due to unhandled exception!
```

   **这是环境限制，不是产品缺陷**（在真实用户会话里注册表可写）。E2E 用产品自带的开关
   `QIO_DISABLE_DB_CHECK=1`（`db_identity.py:139` 的注释写明给测试/隔离环境用）绕开它，
   并在结果里**显式记了一条 WARN（A-032）**：代价是"数据库身份自检"这条启动路径本次没有覆盖。

## 5. 安装 E2E：怎么跑的、验到了什么

### 怎么跑

```
$ python scripts\install_e2e.py --installer <...>\QIO_0.1.10_x64-setup.exe
```

脚本自己按顺序做：指纹 → 备份（注册表 / 快捷方式 / D:\QIO 逐文件 sha256）→ 诱饵实验 →
安装 → 目录清单 → 内置模型核对 → **启动安装目录里的 qio-backend.exe**（白名单构造 env、不继承开发变量）
→ `/api/health` → 假厂商 + 凭据 → 一轮真实 turn → 工具开发全链 → 调用 + 记录 →
重启恢复 → 重装 → 卸载 → 还原机器状态。每步的**原始命令与原始输出**都落在
`.e2e-work\evidence\NNN-*.txt`，机器可读结果在 `.e2e-work\summary.json`。

### 诚实标注：这不是"干净 Windows 用户环境"

本机不能新建用户。可达成的等价条件，以及**它们各自差在哪**：

* ✅ 独立安装目录（不碰 `D:\QIO`）
* ✅ 全新空数据目录（`QIO_DATA_DIR` 指向空目录）
* ✅ 启动进程**不继承**开发用环境变量：env 是按白名单重建的，`QIO_DEV_INSECURE` /
  `QIO_ENABLE_TEST_EVENTS` / `PYTHONPATH` / `VIRTUAL_ENV` 都不在（`.e2e-work\evidence\010-backend-env.txt` 可查）
* ⚠️ 但注入了三个宿主控制变量：`QIO_DATA_DIR` / `QIO_PORT` / `QIO_SESSION_TOKEN`
  （真实应用由 Tauri 壳注入同样这三个），以及上面那个 `QIO_DISABLE_DB_CHECK=1`
* ❌ 没有独立 Windows 用户 → 注册表 HKCU、凭据管理器、快捷方式都是当前用户的。
  注册表那部分还因为沙箱而**根本没写进去**（见第 4 节）。

### 结果

见 `summary.json`。逐条编号的含义：A-0xx 安装/模型、A-03x 后端启动、A-04x 凭据、
A-05x 对话、A-06x 工具链、A-07x 重启恢复、A-08x 重装、A-09x 卸载、A-1xx 机器状态还原。

1. 双击安装包走**图形安装向导**（选目录页、完成页、"运行应用"勾选）；

## 6. 发现的问题

### 6.1 产品缺陷（都不是本轮能改的，报给 Lead 定归属）

## 8. 当前限制（写准，别当成"没做"或"已做"）

1. **不是干净 Windows 用户环境**：没有独立用户；注册表 HKCU / 凭据管理器 / 快捷方式都是当前用户的。
2. **启动时注入 `QIO_DISABLE_DB_CHECK=1`**（产品自带开关）：代价是"数据库身份自检"这条启动路径
   本次**没有覆盖**；不用它，装出来的后端在本沙箱里会在启动阶段崩（第 4 节的 traceback）。
3. **安装/卸载的注册表登记路径没有验证**：本会话子进程是受限令牌，安装器的 `WriteRegStr` 与
   卸载器的 `DeleteRegKey` 都 `ACCESS_DENIED` 且静默失败（A-092 记 WARN）。也就是说：
   "装完能在控制面板看到 QIO / 卸完消失"这件事，本轮**没有**验过。
4. **GUI 一层完全没有驱动**：Tauri WebView 不开 CDP，全部走 HTTP API（第 5 节列了必须人工的 6 步）。
5. **"重启"是后端起停，不是整个应用重启**：Tauri 壳没有参与，壳侧的状态与 sidecar 生命周期没验。
6. ~~**第三方依赖安装没有覆盖**~~（**第四阶段已补，见第 16 节**）：这一轮 E2E 里的工具是纯
   标准库；"声明第三方依赖后的安装链路"后来由 `scripts/install_dep_e2e.py` 在本机真跑过
   （six，真实装进 ToolEnv 并真的调用了工具）。注意：这只推翻第 6 条本身 ——
   "安装版要不要求用户机器上有 Python"另见第 16 节的新结论。
7. **应用内更新（updater）完全没有验证**：需要一份**正式签名**的产物与一个真实的更新源，
   本机两个条件都不具备。
8. **卸载的"删除应用数据"复选框路径没验**：静默卸载跳过确认页，复选框状态恒为 0；
   验到的是"不删数据"，没验"删数据"。

一句话：**装得上、跑得通、数据留得住、既有安装没被碰坏；但产不出被应用信任的更新签名，
安装/卸载的注册表登记没验过，界面层一步没走。**

4. 人工过一遍第 5 节列出的界面步骤与第 8 节第 7 条的更新链路。

# 第三阶段补充（2026-10-03）：卸载契约、发布闸门与"文件锁"事实

工作树 `qio-p3-b`（分支 `wt/p3-b`）。这一节只写**新增的实测**，前面各节的结论不变。

## 10. 卸载残留：`HKCU\Software\qio\QIO`（已修）

### 复现与定位

重新构建后读**本次生成**的 `frontend/src-tauri/target/release/nsis/x64/installer.nsi`：

```
  660: WriteRegStr SHCTX "${MANUPRODUCTKEY}" "" $INSTDIR        ; 安装位置写在这里
  508: Call RestorePreviousInstallLocation                      ; 下一次安装会读它
  863: Function RestorePreviousInstallLocation                  ; 读 MANUPRODUCTKEY
  819: DeleteRegKey SHCTX "${UNINSTKEY}"                        ; 普通卸载只删控制面板登记
  836: ${If} $DeleteAppDataCheckboxState = 1                    ; ← 只有勾了"删除应用数据"
  839: DeleteRegKey SHCTX "${MANUPRODUCTKEY}"                   ;   才清安装位置
  843: DeleteRegValue HKCU "${MANUPRODUCTKEY}" "Installer Language"
```

结论：**普通卸载会留下安装位置记录**，下一次安装（`.onInit` → `RestorePreviousInstallLocation`）
会把默认安装目录指到一个**已经被删掉的路径**。

### 修法：NSIS 钩子，而不是 fork 整个模板

新增 `frontend/src-tauri/nsis/installer-hooks.nsh`，用官方扩展点挂进去：

```json
"bundle": { "windows": { "nsis": { "installerHooks": "nsis/installer-hooks.nsh" } } }
```

为什么不 fork 模板：模板是 Tauri 生成的 900+ 行，fork 一份等于把 Tauri 的每次升级都变成人工合并；
钩子是官方支持的扩展点，升级不会炸。代价是钩子文件必须随仓库一起走（已经入库）。

钩子里只做**安装信息**的清理：

```nsis
!macro NSIS_HOOK_POSTUNINSTALL
  ClearErrors
  DeleteRegValue SHCTX "Software\qio\QIO" ""                    ; 安装位置（默认值）
  DeleteRegValue SHCTX "Software\qio\QIO" "Installer Language"  ; 安装向导语言
  DeleteRegKey /ifempty SHCTX "Software\qio\QIO"                ; 键空了才删
  DeleteRegKey /ifempty SHCTX "Software\qio"
!macroend
```

**安装信息 vs 用户数据的边界**（查过 `HKCU\Software\qio\QIO` 里到底有什么）：
这个键下同时住着后端写的 `DbBaseline`（`agent/storage/db_identity.py` 的 REGISTRY_VALUE，
数据库身份基线，属于**用户状态**）。所以只用 `DeleteRegValue` + `DeleteRegKey /ifempty`，
**绝不**整键 `DeleteRegKey` —— 否则等于顺手改了产品的数据保留策略。
数据目录（`%APPDATA%\com.qio.app`）完全不碰，保留与否仍只由"删除应用数据"复选框决定。

顺带核实：外壳（`frontend/src-tauri/src/main.rs`）的 `reg` 用法只有**系统代理**
（`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`），
它不读安装位置 —— 所以清掉这个值不会影响运行中的应用。

### 证据

生成脚本里钩子确实挂上了（构建期实测）：

```
   31: !include "...\frontend\src-tauri\nsis\installer-hooks.nsh"
  756: !ifmacrodef NSIS_HOOK_PREUNINSTALL
  757: !insertmacro NSIS_HOOK_PREUNINSTALL
  852: !ifmacrodef NSIS_HOOK_POSTUNINSTALL
  853: !insertmacro NSIS_HOOK_POSTUNINSTALL
```

宏体真的展开成预期语句（`makensis /PPO` 预处理，不是靠"应该会"）：

```
  6: ClearErrors
  7: DeleteRegValue SHCTX "Software\qio\QIO" ""
  8: DeleteRegValue SHCTX "Software\qio\QIO" "Installer Language"
  9: DeleteRegKey /ifempty SHCTX "Software\qio\QIO"
 10: DeleteRegKey /ifempty SHCTX "Software\qio"
```

钩子文件必须是 **UTF-8 带 BOM**（与 Tauri 自己生成的 `English.nsh` / `installer.nsi` 一致）：
NSIS 对无 BOM 的源码按系统 ANSI 码页解码，中文注释会变乱码、严格校验时直接报
`Bad text encoding`。已实测两者：无 BOM 的探针脚本编译报错，补上 BOM 后编译通过。

## 11. 「端口关 ≠ 文件没被锁」（Agent A 的 CR3，实测依据）

| 事实 | 来源 |
| --- | --- |
| 运行中的 `qio-backend.exe`：**rename 成功**（映像以 FILE_SHARE_DELETE 打开）、**delete 拒绝**（WinError 5）、**overwrite 拒绝**（Errno 13）；进程结束后三者都成功 | Agent A，`scripts/verify_backend_process_model.py --case 6`（冻结产物） |
| onefile 是 launcher + child 两层：**只结束 launcher 会留下孤儿 child**，它继续持有映像、端口也仍然开着 | Agent A 同上；我自己的安装/卸载 E2E 也见到同一形状（`taskkill` 输出 "child process of PID 87984"） |

所以本 E2E 的收尾全部改成**按 PID / 进程树**（`taskkill /F /T /PID <pid>`），
并新增 `A-088` 硬前置：卸载/重装前按**路径**枚举"安装目录里的那个 exe"还有没有进程在跑，
确认干净才继续 —— 否则"卸载残留了什么 / 重装有没有换掉文件"都会被这把锁污染成假结论。
**绝不用 `taskkill /IM qio-backend.exe`**：这台机器上同时有多个 agent 在跑真实后端，按名字杀会误伤。

同一个事实还暴露了安装器侧的一条缝：Tauri 模板的 `CheckIfAppIsRunning` **只查主程序
`qio.exe`，不查 sidecar**。sidecar 还活着时，`Delete "$INSTDIR\qio-backend.exe"` 静默失败、
`RMDir "$INSTDIR"` 也失败 —— 用户看到的是"卸载完了但目录还在、后端还在跑"。
钩子里补上（复用模板自带的同一个宏，静默卸载直接结束、交互卸载问用户）：

```nsis
!macro NSIS_HOOK_PREUNINSTALL
  !insertmacro CheckIfAppIsRunning "qio-backend.exe" "${PRODUCTNAME}"
!macroend
```

**实测**（故意让 sidecar 跑着去卸载，`install_e2e.py --uninstall-with-running-backend`）：

```
[PASS] A-087 卸载前故意让 sidecar 继续运行 :: 运行中的 sidecar pid=[119756, 124336]（不主动停）
[PASS] A-090 卸载后安装目录被清空 :: exit=0 残留：[]
[PASS] A-095 卸载器自己收掉了还在跑的 sidecar :: 卸载后按路径枚举：无残留进程
```

## 12. 发布闸门：按**实际产物**判定，而不是按源码配置推断

修的是上一阶段暴露的盲点：`bundle.config` 只读 `tauri.conf.json`，构建时用 `--config`
关掉 `createUpdaterArtifacts` 它照样报 PASS（真产物没签名）。

新增/改动的检查项：

| 检查项 | 判定依据 |
| --- | --- |
| `uninstall.contract` | **静态契约**（CI 可跑）：钩子必须清安装信息、且不得删用户状态或数据目录；没配钩子直接红 |
| `build.manifest` | 产物旁的 `<installer>.build.json`（构建脚本写出）：核对 installer sha256 / 版本 / commit / config overrides / signing；没有记 WARN |
| `updater.artifacts` | **产物本身**：`.sig` 在不在 + manifest 声明的 signing。未签名测试产物记 **WARN**（明说"不是可发布产物"），未声明却缺签名记 **FAIL** |
| `repo.commit` | 产物要能对到某一版源码 |
| `bundle.config` | 口径收窄成"只看源码配置"，说明里指向 `updater.artifacts` |

新增 **WARN** 状态：查到了、也如实说了，但不构成"不要发布"。历史比较里单列，
不会被读成"新失败"。`main` 与 `--selftest` 共用同一份检查清单（否则自检绿了、真跑查了别的），
自检 8 个用例（缺钩子 / 钩子删用户状态 / manifest 串包 / 未签名产物只记 WARN …），
由 CI 的 `docs consistency` 任务真跑（本次 CI 已绿）。

实测（本机未签名测试产物）：

```
uninstall.contract  PASS  卸载钩子会清安装信息（Software\qio\QIO 的默认值与 Installer Language），
                          且用 /ifempty 保留 DbBaseline；installMode=currentUser（未显式配置，Tauri 默认）
build.manifest      PASS  commit=06a28eab version=0.1.10 built_at=2026-10-02T15:21:31Z
                          signing=unsigned-test overrides={"bundle": {"createUpdaterArtifacts": false}}
updater.artifacts   WARN  实际产物没有更新签名（.sig 不存在），且它被显式标成未签名测试产物
installer.sig       FAIL  缺少 ...UNSIGNED-TEST.exe.sig
latest.json         FAIL  缺少更新清单
发布闸门：2 项不通过 —— 不要发布。
```

**BLOCKED BY SIGNING CREDENTIAL**：这两项红着的原因是本机没有更新签名口令（前文第 1 节已实验证明），
不是流程缺陷。未签名产物保持显式的 `UNSIGNED-TEST` 身份，不伪造 `.sig` / `latest.json`。

## 13. 本阶段新增的环境陷阱（都实测踩到过）

1. **`build_sidecar.ps1` 会掏空共享 venv**：`uv run --frozen --with pyinstaller` 不带 extras 时会把
   环境同步成"默认依赖集"，于是把 dev extra 里的 pytest / pytest-asyncio 从 `.venv` 卸掉。
   之后跑测试以 **150 个 collection error（`No module named 'keyring'`）** 收场，看起来像代码坏了。
   已修：那次 uv 调用补 `--extra dev`（PyInstaller 只跟着 `main.py` 的 import 走，不会把 pytest 打进包里）。
2. **`uv run --frozen pytest` 可能回退到系统 Python 3.10 的 pytest**（不是 venv 里的），
   报出来的错和代码无关。用 `uv run --frozen python -m pytest`。
3. **端口要按分配用**：多个 agent 同时起真实后端时，撞端口会让"健康检查"被**别人的后端**答上来
   （本机实测过一次：我的 E2E 连到了另一个 worktree 的 `qio-backend.exe`）。
   E2E 现在开局就检查端口，并校验"回答这个端口的进程路径 == 安装目录里的 exe"，
   不符直接 FAIL 停跑；假厂商端口自动挑空闲的。
4. **`_MEIxxxx` 不会被自动清**：onefile 每次启动解出约 180 MB 到临时目录，杀进程后仍留在盘上。

## 14. 仍然没验的（不要读成通过）

* **安装/卸载的注册表登记**：本会话子进程是受限令牌，`WriteRegStr` / `DeleteRegKey` 都
  `ACCESS_DENIED` 且静默失败（E2E 里的探针 `A-023/A-092/A-093/A-094` 记 **NOT VERIFIED**）。
  修复本身由 `uninstall.contract` 静态契约在 CI 上守着；**真机上仍应人工跑一次**
  "装 → 看控制面板 → 普通卸载 → 确认 `HKCU\Software\qio\QIO` 只剩 `DbBaseline`（若有）"。
* **"删除应用数据"复选框路径**：静默卸载跳过确认页，复选框状态恒为 0；验到的是"不删数据"。
* **多份 QIO 安装并存**：卸载器按**可执行文件名**找当前用户的 `qio-backend.exe`，
  与模板对 `qio.exe` 的既有行为一致 —— 卸载一份会连带结束另一份的 sidecar。已知限制。
  能不能改成"按安装路径（`$INSTDIR`）判定"？**结论：技术上可能，但不是小改动，因此不做**（2026-10-03 实测取证）：
  1. Tauri 随包带的 `nsis_tauri_utils.dll` 只导出 `FindProcess` / `FindProcessCurrentUser` /
     `KillProcess` / `KillProcessCurrentUser` —— **全部按可执行文件名**，没有 path 参数
     （把 DLL 里的字符串抽出来核过；内部用的是 Toolhelp `Process32FirstW/NextW` 快照）。
  2. NSIS 标准插件目录里**没有 `nsProcess`**（它同样只按名字），核心 NSIS 也没有进程 API。
     要真正按路径判定，只能自己写一个 C++ 插件并把它作为二进制带进仓库 —— 那才是"把 Tauri 升级
     变成人工合并"的那类代价。
  3. 唯一便宜的替代是卸载器里 `nsExec` 调 PowerShell/WMI 按 `ExecutablePath` 找 PID 再 `taskkill /PID`。
     可行，但要往卸载器里塞一个 shell 依赖 + 输出解析 + 错误分支；而且一旦 PowerShell 被策略挡住，
     为了保住"卸载一定能把 sidecar 收掉"这条保证，还得**回退到按名字杀** —— 那这条精化在回退路径上
     一点也没买到东西，只是多了一个失败模式。
  结论（2026-10-03 当时）：保留按名字杀（与模板对 `qio.exe` 的行为一致），把这条写进"当前限制"。
  更合适的修法在别处：让外壳在退出时负责结束 sidecar（异常退出才可能出现孤儿），
  或者上游给 `nsis_tauri_utils` 加一个按路径的函数。

  **⚠️ 这条"不做"已在第四阶段被推翻（2026-10-03 晚）：** 不是去动 `nsis_tauri_utils`，
  而是换成"安装目录里的 `sidecar.lease.json` + `qio-uninstall-helper.exe` 只按 pid 收"
  （契约见 `docs/p4-plan.md` §1）。多安装并存的实测（先失败后通过）见第 15 节。
  **仍然没改**的是模板对 `qio.exe` 的按名字检查：两份**真名**外壳并存时它照样连坐，
  这条限制还在 —— 只是它不再影响 sidecar 的所有权判定。装置偏差与对照实验见第 15 节。
* **应用内更新**：需要正式签名产物 + 真实更新源，仍未验（BLOCKED BY SIGNING CREDENTIAL）。

## 15. 多份 QIO 安装并存：从"已知限制（不修）"改成"按 lease 只收自己的"

### 15.1 结论写清边界

* **改了（这条是第 14 节那个"不做"的推翻）**：卸载不再按映像名杀 sidecar。判定改成
  "读安装目录里的 `sidecar.lease.json`（schema / install_dir / shell / backend 四件套，
  PID + 创建时间 FILETIME + 映像路径三者同时匹配）+ `qio-uninstall-helper.exe` 只按 pid 收"。
  契约见 `docs/p4-plan.md` §1.1/§1.2；判不出归属时**宁可不杀**（exit 3）。
* **没改**：模板 Uninstall 段自带的 `CheckIfAppIsRunning "qio.exe"`
  （生成脚本 `installer.nsi:760` + `utils.nsh:40-47`，只认映像名，静默模式直接
  `KillProcessCurrentUser`）。所以"卸载 A 连坐 B"有**两条**独立路径：
  * **(a)** sidecar 钩子按名字杀 `qio-backend.exe` —— 本轮修的就是这条；
  * **(b)** 模板按名字杀 `qio.exe` → B 的**壳**被杀 → `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
    （`main.rs:511/530`）关掉 job → B 的 sidecar 跟着死。本轮由构建期补丁
    `scripts/patch_nsis_template.py` 处理（是否进了包要看具体产物，不靠推断）。
  驱动 `scripts/install_e2e_multi.py` 的断言**同时**覆盖 (a)(b)：A 卸载后 B 的壳与 B 的
  sidecar 都必须原封不动，谁没做到就是 FAIL —— 不许用"把 B 的壳改名"之类的装置把 (b) 绕过去。

### 15.2 怎么跑

```
python scripts/install_e2e_multi.py --installer <A 的包> [--installer-b <B 的包>] --work-dir <目录>
```

两种口径，结论分开写：

| 口径 | 开关 | 断言方向 |
| --- | --- | --- |
| 新语义（修复后产物） | 默认 | 卸载 A 后：A 的壳/sidecar/lease 全消失、A 目录清空；**B 的壳/sidecar 仍在**（pid+创建时间逐条一致）、B 的 lease 未变、B 的端口仍答 `/api/health`；再卸 B 也干净 |
| 改动前产物（先失败的取证） | `--expect-legacy-name-kill` | 反过来：**B 的 sidecar 被杀掉**才算复现缺陷（记 PASS-by-repro，标题写明"不是产品通过"） |

`install_e2e.py` 的 `coinstall` 阶段只是把这个驱动当子进程跑（一份实现、两个入口）；
`--rename-b-shell` 是**诊断开关**（把 B 的壳改成 `qio-b-shell.exe` 以单独隔离 (a)），
平时不要用它下结论。

### 15.4 本机实测：三个环境陷阱（都是沙箱，不是产品缺陷）

1. **静默安装要一份可写的 TEMP，否则 NSIS 静默 abort**（本机 exit=2）：
   ```
   [FAIL] C-010 静默安装 A :: exit=2 目录存在=False
   ```
   把 `TEMP/TMP` 指到检出内的 `work/tmp` 后，**同一份安装包**：
   ```
   exit=0 elapsed=8.4s
   install exists: True files: 4
   ```
   根因：子进程是受限令牌，写不了用户目录下的 `AppData\Local\Temp`，NSIS 解 `$PLUGINSDIR`
   失败。`install_e2e.py` 的 decoy/reinstall 两处安装、`install_e2e_multi.py` 的安装步骤
   现在都把 TEMP/TMP 钉在检出内（代码注释写明这是沙箱适配）。**真机/CI 的 %TEMP% 本来就可写。**
2. **真外壳在本机起不来**（这条直接决定"lease 由外壳写"在本机能验到哪一层）：
   ```
   [FAIL] A-111 启动后安装目录里出现 sidecar.lease.json :: 外壳在 60.0s 内就退出了（exit=3221226505），没有写出 sidecar.lease.json；壳日志尾部：
   thread 'main' (13656) panicked at src\main.rs:861:10:
   error while building tauri application: PluginInitialization("log", "拒绝访问。 (os error 5)")
   ```
   根因：tauri 的 log 插件要在 `%LOCALAPPDATA%\<identifier>\logs` 下建目录，受限令牌被拒 →
   外壳启动即 panic。把 `LOCALAPPDATA` 指到检出内**没用**（Tauri 走 KnownFolder API，
   不认环境变量）。所以本机 `shelllease` 只能记 **WARN / NOT VERIFIED**（断言里已经按这条
   签名区分：只有匹配 `PluginInitialization("log"` + `os error 5` 才是 WARN，其它起不来仍是 FAIL）。
   **"外壳会写 lease / 退出会删 lease"这条必须由 CI 或真机硬过。**
3. **NSIS 卸载器是"拷到 TEMP 再删"**：主进程先退出，立刻查目录会看到"什么都没删掉"的假残留
   （0.1.11 实测：`models / qio.exe / uninstall.exe` 都还在）。驱动改成"等目录内容连续 5s
   不变"再判定。

## 16. 安装版自带 Python 运行时：从"用户机器上要有 Python 3.11"改成"自带运行时 + 缺它时明确失败"

### 16.1 结论

* **包里现在有自带运行时**：本机构建出的
  `frontend/src-tauri/resources/python-runtime/` 为 **726 个文件 / 33.9 MB**，
  `python.exe` 自报 **3.11.15**（`python -c` 可跑）。
* **后端按 `QIO_PYTHON` → `QIO_BUNDLED_PYTHON_DIR` → py 启动器 → PATH 解析**
  （`backend/src/agent/tools/tool_envs.py::_resolve_base_python`）。所以
  "用户机器上不需要预装 Python"这句话，只有在**包里带了运行时**且**后端认这个变量**两条同时
  成立时才成立 —— 缺一条就退回下面那条明确失败。
* **缺运行时时不假装可用**：仍然给出可行动的明确失败（原始输出见 16.3）。

### 17.4 三条**环境前提**（不是产品缺陷；Lead 要求写清）

这三条都是本机（Windows 桌面 session 1、Medium 完整性，但子进程带沙箱形状的令牌）实测到的，
换一台干净机器/干净用户**不应**复现。**不 workaround 就会得出相反结论**，所以必须写明：

1. **真实 `%TEMP%` 下 PyInstaller onefile 建不出临时目录** → 后端秒退（lease 写下的 backend pid
   1~2 秒后就查不到）。原始输出：`[PYI-13180:ERROR] Could not create temporary directory!`
   *workaround：把外壳（及其 sidecar）的 `TEMP/TMP` 指到 work-dir。*
2. **受限令牌下 `db_identity._write_baseline` 写基线报 `PermissionError [WinError 5]`** → 后端起来
   ~4s 后崩（就是 §4 那条已知限制）。原始输出：`agent\storage\db_identity.py", line 415, in check_integrity
   ... line 108, in write ... PermissionError: [WinError 5] 拒绝访问。`
   *workaround：产品自带的 `QIO_DISABLE_DB_CHECK=1`（代价：数据库身份自检这条启动路径本次没覆盖 ——
   脚本里记了一条 WARN S0-005）。*
3. **后端已经死了时，严格 close 必须拒绝** —— 这是**产品行为正确**，不是卸载器坏了：
   ```
   qio-uninstall-helper --check-only --json
     -> exit 0, {"action":"would_close","reason":"shell_running","backend_identity_ok":false,
                 "backend_alive":false,"shell_identity_ok":true,...}
   qio-uninstall-helper --close-installation --json

### 17.7 第 2 步为什么在这台机器上验不了：窗口寿命 < lease 写出

最终一轮里三件事的**时间线**（0.1s 采样，`.e2e-desktop/run-final8/evidence` 有原始记录）：

| 事件 | 时刻（相对进程创建） |
| --- | --- |
| 主窗口出现（class=`Tauri Window` / title=`QIO` / visible） | t ≈ 0.1 ~ 0.3s |
| **窗口消失**（进程继续活着） | t ≈ 7.6 ~ 9.2s（三轮观察） |
| **lease 文件写出**（shell.pid = 本进程） | t ≈ 8.0 ~ 8.7s |
| 应用自己的启动日志（"启动耗时 … 合计 1142ms"） | 落在 lease 写出那一刻附近 |

结论：**窗口活着的整段时间里，应用还没写出它的归属记录**；等 lease 出来时窗口已经没了。

### 17.8 更正（2026-10-04，Lead）：那些 FAIL 是"被测程序放在带沙箱 ACL 的工作区目录里"造成的假象

Lead 用**同一份二进制、只换目录**做了对照，结论：

| 程序所在目录 | 主窗口 |
| --- | --- |
| `C:\qio-probe`（干净） | 全程存活（25s 采样 49/49） |
| `C:\qio test\app`（带空格） | 全程存活 |
| `C:\Users\zxy\Documents\qio-probe-app` | 全程存活 |
| 桌面 / `D:\` | 全程存活 |
| **`C:\Users\zxy\Documents\Front agent\...`（本会话工作区根之下）** | **1~1.5s 就消失** |

机制：工作区根目录带沙箱 ACL —— `ADMIN\CodexSandboxUsers:(OI)(CI)(M)`、
`Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)`（低完整性、禁止向上写）、
`Everyone:(CI)(DENY)(DC)`（拒绝删除子项）。放在其下的可执行文件继承低完整性标签，
WebView2 的宿主进程起不来（Chromium 沙箱直接崩，事件日志里是 `msedge_elf.dll` + `0x80000003`）。
换 CWD 不影响（exe 在干净目录、CWD 用工作区 → 正常），所以**是 exe 所在目录**。

**因此 §17 里那 4 条 FAIL（`S1-022b` / `S2-000` / `S2-001` / `S2-001b`）不是产品缺陷。**
把同一份构建放到 `C:\qio-verify` 重跑，第 ② 步通过：

```

lease 内容: install_dir= C:\qio-verify
           shell.pid= 41912  backend.pid= 42200  backend.exe= C:\qio-verify\qio-backend.exe
投递 WM_CLOSE 次数 = 1
外壳自己退出 = True  exit = 0
lease 被删除 = True

```

**纪律补充：桌面/E2E 验证必须把被测程序放到工作区之外的干净目录**（如 `C:\qio-verify`），
否则会把工作区沙箱的假象记成产品缺陷。
