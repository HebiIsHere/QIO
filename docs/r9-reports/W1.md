### B. 审批 v2（契约 §5）

- 新建 `storage/approvals.py`（ApprovalStore）：直接使用 Lead 已冻结的迁移 53 列/表（state/operation/instruction_id/instruction_text/purpose/fingerprint/mode_at_request/mode_at_approval/confirmed_stage/revisions/attempt/claimed_at/result/error/resumed_at + approval_audit + approval_history），未新增迁移、未改历史迁移。
  - 状态机：waiting → approved → executing → completed|failed；waiting → rejected|cancelled|expired；executing → interrupted_unverified；approved → invalidated。
  - 默认 600 秒原始期限（从创建时算起；刷新/暂缓/重启不续期）。
  - CAS 决定/确认（expected_revision）；确认阶段必须 1→2→3 连续；原子领取 UPDATE ... WHERE state='approved'（rowcount 校验，重复领取不执行）。
  - 启动恢复：waiting 未过期恢复（owner 已死/无归属则接管）；waiting 过期→expired；approved→重核对后可执行；executing→interrupted_unverified（不自动重放）；旧 request() 落库行按旧事实标 interrupted（见偏差/边界）。
- 改造 `tools/approval.py`：
  - 旧 request() 行为与签名保留（默认寿命 300→600 秒；超时文案改为 10 分钟），供 loop 的「继续/停止」对话框与尚未替换的旧调用方使用。
  - 新增 submit()（持久化 + 立即返回 waiting ticket）、decide()、confirm()、history()、recover()、aclose()、set_engine/set_operations/set_instruction_registry/set_notifier。
  - 后台执行器：重核对（当前模式更严格则 invalidated）→ 原子领取 → 按 kind 调执行器 → 落 completed/failed + approval_history + 事件；执行结果经回调在活动 turn 内注入系统通知（push_notice，不伪装成模型的话）。
  - 旧 /respond 可驱动 v2 审批（approved/rejected 映射 decide）；旧 invalidate_for_task 同时作废 v2 中指向该开发任务的等待项。
  - 批准「本指令内对该范围」时把有界 user_approved grant 写入当前指令（指令结束即失效）；「仅这次」不写 grant。
- 接线 `services/app.py`：AppContext.authorization / instructions / operations / tempfiles；services.register("security", engine)；每轮 InstructionContext 建立/关闭；通知轮 approval_origin=background；tool.invoke 执行器；_internal_data_paths()；aclose() 先停审批执行器。
- `api/server.py`：
  - GET /api/security/mode → {mode,label,legacy_value}；PUT /api/security/mode（必需 user_confirmed=true，只接受新值；引擎 set_mode(user_initiated=True)，否则 PermissionError）。
  - 旧 /api/settings/computer 兼容：GET 返回 normalize 后的新值 + mode_label；PUT 接受新旧值但映射后落库（新值）。
  - 新审批接口：GET /api/approvals/pending、GET /api/approvals/history、POST /api/approvals/{id}/decide、POST /api/approvals/{id}/confirm；旧 /respond 保留；/api/runtime/state 的 approvals/interrupted_approvals 同时返回 v2 项。
  - lifespan 启动恢复：await ctx.approvals.recover() + 临时文件清理。
- `tools/registry.py`：有引擎+持久化审批时工具审批改 deferred（ALLOW 直接执行 / DENY 中文短路 / APPROVE 持久化 tool.invoke 并返回 awaiting_approval 结构化结果）；无引擎的旧装配保持原 request() 行为；已批准执行用 execute(..., approval_id=...) 重跑管线但不重复弹审批。
- `core/loop.py`：旧「继续/停止」审批调用点保留 request()（这是用户必须当场决定的对话框，不是工具操作占住 turn）；新增独立使用 AgentLoop 时的每轮 InstructionContext 兜底（真实 turn 由 AppContext 建立；通知轮不产生 grant）。
- `services/computer.py`：mode 属性兼容旧值/新值映射（旧逻辑行为不变），新增 permission_mode 返回三模式；旧测试断言不变。

## 四、未完成边界 / 兼容与集成说明

1. 旧调用点：cmd_tools/fs_tools/lifecycle/dev_auth/tool_envs/maintenance/topic_tools 仍调用旧 approvals.request()（同步等待）。按 Lead 分工由 W2 替换为「engine.authorize → engine.submit → decide/confirm」；W1 保留旧签名并默认 600s，不破坏现状。
2. request() 与 v2 的恢复边界：旧 request() 行没有 operation/state，进程内等待随进程消失，重启后如实标 interrupted（旧行为）；v2 行（state 非空）按契约恢复。这样既不误标 v2，也不把「旧内存等待」说成可恢复执行。

4. 工具效果声明：registry 约定工具可选实现 effects(arguments) -> list[Effect]；未声明效果的工具保守走审批（不会猜成 ALLOW）。W2 的文件/命令工具应声明真实 effect 以获得 read_only/restricted 的精确判定。
