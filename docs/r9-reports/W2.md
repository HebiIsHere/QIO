## 一、已实现（按交付项 A–F）

### A. 所有真实执行入口统一走授权网关
新增 `agent/tools/security_gate.py`（工具层唯一适配层）与 `agent/tools/security_types.py`
（契约 §2 类型桥接）。工具不自己判权限，只负责「构造 Effect/Target → 调 gateway → 翻译结果」。

- `fs_tools.py`：`fs_read/fs_list/fs_find/fs_info` → READ effect；`fs_write/fs_patch` → WRITE effect
  （写入前重核对文件身份；原子写：同目录临时文件 + `os.replace`，失败保原件）。
  gateway 返回 `approve` 时一律 `submit()` 返回 `pending_approval`（不阻塞、不自行执行）。
- `cmd_tools.py`：`run_program`（EXECUTE，detail 带 argv/shell=False）、`run_shell`（EXECUTE，
  detail shell=True）、`proc_kill`（EXECUTE，detail 带 `managed_by_this_instance`）全部先经网关；
  `approve` 一律提交待审批（`proc.run_program/proc.shell/proc.kill`）。
  `proc_kill` 只对**本实例 Job 归属**的 pid 走自动放行语义（新增 `isolation.is_managed_pid`），其它 pid 按引擎结果审批。
- `runtime_tools.CodeTool`（自建工具真实调用）：每次调用重新判定（EXECUTE + 代码摘要），
  注册不产生任何长期文件/网络授权；`read_only` 直接拒绝；`approve` → `tool.invoke` 待审批。
  提供 `execute_after_approval(arguments)` 作为审批执行器入口。
- `subagent_tool.py`：创建子智能体先经 SUBAGENT effect 判定；需要批准时由**主智能体**提交
  `subagent.create` 待审批（子智能体不自行弹窗，单层）。
- `dev_auth.py` / `dev_tools.py` / `lifecycle.py`：执行 AI 生成代码前经 EXECUTE 判定
  （`read_only` 明确拒绝）；工具注册前经 TOOL_REGISTER 判定。
- `tool_envs.py`：`ensure()` / `ensure_container_image()` 经 INSTALL_DEPS 判定
  （QIO 专用环境内 allow，不再重复弹窗；系统级/需批准时仍走同一个 ApprovalService）。
- 兼容说明：tools 的 `security` 服务为 None 时保留旧 `ComputerSandbox → approvals` 路径，
  **只用于未接线的旧构造点与单测**；生产接线（W1 注入）后由网关决定，不构成权限旁路。
- 未改 `tools/attachment_tools.py`（按 Lead 边界归 W3，读取由 W3 的 resolve_source 负责）；
  `tools/topic_tools.py` 的 `create_topic` 确认保留 legacy request（Lead 允许：非文件权限，
  且使用的是同一个 `ApprovalService` 实例，见审计表）。

### B. 执行层约束（read_only / restricted / unrestricted）
- `isolation.py`：新增 `low_integrity_required_for_mode(mode, authorized_write_scope)`
  （read_only 强制；restricted 且脚本没有授权写范围时强制；unrestricted 不降级），
  `harden(..., mode=, authorized_write_scope=)` 扩展；`IsolationOutcome` 增加
  `low_integrity_required / boundary_ok()`。**要求了但核实不了 → boundary_ok=False，调用方拒绝执行**（不静默降级）。
  Job Object（内存/进程数上限 + KILL_ON_JOB_CLOSE）照旧，并新增本实例管理 pid 记录。
- `sandbox.py`：`SandboxExecutor` 支持 `mode_provider/security/protected_scope_provider/execution_guard`；
  `read_only` 在执行前拒绝任意脚本/自建工具（不启动任何进程）；restricted 无授权写范围时强制 Low IL，
  核实不成 → 结束进程并返回「执行边界暂不可用」；unrestricted 不做模式降级（旧行为）。
- `cmd_tools` 执行层兜底：`read_only` 下 `run_program` 只在「白名单 + shell=False + 参数可证明只读」时放行；
  `run_shell`、可写子命令（如 `git commit`）明确中文拒绝。**无法可靠约束的路径明确拒绝，不静默降级。**
- **重要修复**：原有 Low IL 写入探针 `_low_process_can_write` 给路径加引号，
  经 subprocess list2cmdline 传给 `cmd /c` 必然「文件名语法不正确」→ 降级长期被 fail-safe 跳过。
  改为「相对文件名 + cwd=目录」后，本机真实降级生效（证据见下）。

### C. 事后核验
新增 `agent/tools/execution_guard.py`：执行前对受保护范围（工作区业务文件、内部数据根等，
由调用方提供）记录 size/mtime 快照，执行后比对新增/删除/修改；越界修改 → 结果标记
`category="boundary_violation"`、`ok=False`、错误文案「执行越界…（无法回滚，只能如实上报）」，
并在 `SandboxResult.guard` 附事实。取消路径无法返回结果时只记日志（不改写取消语义，见限制）。

### D. 子智能体
- 创建时按父 `InstructionContext.grants`（未撤销）生成 `AgentScope` 子集（优先使用 W1 的
  `child_scope(purpose=...)`，否则本地按契约说明构造），深度只有一层，超过 `max_depth` 拒绝。
- 子智能体循环在 `agent_scope_context(scope)` 内执行（同时设置 W1 的
  `agent.security.context.agent_scope` 与本地兜底 ContextVar），循环内 effect 均处于该 scope。
- 无法生成父授权子集 / 会扩权时明确拒绝（中文）；用户批准由主智能体提交待审批（单层）。

### E. 内部运行数据三连确认落到边界
- 文件边界：`fs_write/fs_patch` 命中引擎提供的 `internal_data_paths` 时 EffectKind 改为
  `INTERNAL_DATA`，待审批操作 `confirmations_required=3`，返回文案明确「连续确认三次、任一步取消即停止」，
  确认前不执行。
- 脚本边界：`SandboxExecutor.execute` 执行前扫描脚本内容是否**明确出现**内部数据路径；
  命中则拒绝执行并要求先完成三次确认（`internal_data_confirmed=True` 才能继续，由审批执行器传入）。
- 诚实限制：脚本运行时拼路径/间接写无法在执行前可靠识别 → 由 C 的事后核验如实上报
  （read_only/restricted 下 Low IL 另有 OS 层写兜底；unrestricted 无该兜底）。

## 四、旧用例 → 替代用例（Lead 允许的「被用户决定推翻」改写；覆盖不减少）

1. `test_low_integrity_keeps_the_scratch_writable`
   - 旧：目标目录没有标签 ACE 或标签为 Low → 断言 `WRITE-OK`；
   - 新：无标签 ACE 时按父目录完整性继承判断（父进程 Medium ⇒ 目标是 Medium）→ 断言 `WRITE-DENIED`；
     父进程本身是 Low 时才断言 `WRITE-OK`。**环境分支都保留，断言更强。**
2. `test_the_declared_triple_holds_with_a_non_low_parent`
   - 旧：`higher_target = 有显式标签且非 Low` → 无标签时走「写通」分支；
   - 新：无显式标签且父进程 Medium 也视为 higher_target → 真实走拒绝分支，断言
     user/qio 目录写拒绝且文件不存在、scratch 可写。三件套覆盖不减少。
3. `test_the_process_that_runs_tool_code_is_the_one_we_hardened`
   - 旧：工具自检里调用 `os.getppid()`；
   - 新：Low IL 进程在 Windows 上用 Toolhelp 枚举 Medium 进程会 `ERROR_NO_MORE_FILES`，
     故自检不再调用 `os.getppid()`（诊断字段移除），仍断言真实执行 pid 的完整性为 Low 且在 Job 内；
     失败信息改为只显示 pid。**核心断言未减少。**
