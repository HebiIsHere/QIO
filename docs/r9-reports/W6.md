## 1. 适配原则（为什么不"删测试保绿"）

R9 按用户产品决定**移除本地副本流水线**（附件 = 源文件引用；register_source 不复制/不移动，旧 copy
只服务历史数据回放）。旧用例的装置全部打在已删除的 copy 注入缝上（`shutil.copyfile` / `os.replace`
提交 / 100MB 边界），在新代码上必然闸门不进入。适配方式：

1. **不删除任何旧能力断言**：把"副本准备态/副本可读/复制失败"翻译成新契约里用户可见的同一件事
   —— 源引用缺失/不可用 → 整轮结构化 409；准备期取消/断连 → 不得启动；显式 [] 正常；正常引用发送通过。
2. **失败制造方式**：删除/改名源文件（`resolve`/check 失败）、源文件变成目录（不可读对象）。
   不再使用已删除的 copy 注入缝。
3. **准备期装置**：用仍然真实存在的**浏览器上传首次落盘**（`attachments.begin_material` → prepared
   → `bind_for_turn` 有界等待）让请求真的停在准备中；取消/断连走真实 `/api/turns/prepare/{id}/cancel`
   与真实 TCP FIN（真 uvicorn），不取消测试端 ASGI task、不直接调 abandon。
4. 为了失败时秒级得到可区分结论，fixture 把 `prepare_wait_seconds` 压到 1.5s/3s（只压等待上界，
   不改任何判定语义）；断连/取消用例用台账 `reason=cancelled_during_prepare` 区分"真取消"与
   "等待超时后的 409"，避免假绿。
