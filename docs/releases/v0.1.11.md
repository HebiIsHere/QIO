## 这一版最重要的一件事：安装版里的「带依赖的工具」以前根本用不了

QIO 允许 Agent 创建自己的工具，并允许工具声明第三方 Python 依赖。**但在安装版里，这条链一步都走不了**：
后端被冻结成单个 exe 之后，代码仍然拿 `sys.executable` 当 Python 解释器去建专用环境 ——
那其实就是 `qio-backend.exe` 自己；于是它**又启动了一个后端**，然后因为环境里没有 home 目录而崩掉。
你在界面上看到的只是「创建专用环境失败」。

修好之后，整条链在**真实安装产物**上跑通了：依赖审批 → 建环境 → 安装并锁定版本 → 跑测试 → 注册 → 调用 →
**重启后仍然可调用且版本一致** → 删掉环境后**明确告诉你需要重新准备**（不会偷偷用别的环境顶替）→
重建后仍是同一批锁定版本。

**一个前提要说清楚**：安装版需要一个**与后端 ABI 匹配的 Python（3.11）**才能为工具准备依赖环境。
机器上没有时，QIO 会明确告诉你需要装什么（也可以用 `QIO_PYTHON` 指定解释器），而不是给一段看不懂的报错。
这是当前版本的限制。

## 升级过程本身更安全了

- **数据库迁移现在是原子的**。以前升级途中断电或进程被杀，可能留下「一半的表结构 + 还是旧版本号」，
  结果就是**应用再也起不来**（只能人工修库）。现在要么全生效、要么全不生效；旧版本已经留下的半截库也能自愈。
- **卸载会把安装信息清干净**：以前普通卸载会留下安装位置记录，下次安装可能指向一个已经被删掉的目录。
  现在安装位置会被清掉，而**你的数据（对话、记忆、工具、凭据引用）默认保留**。
- **卸载器会先收掉还在跑的后端**。以前如果卸载时后端还活着，安装目录可能删不干净。
- 关闭 QIO 后不会留下属于本实例的后台进程（资源与进程树由 Job Object 托底；
  这一层在 CI 上有专门的进程模型门槛）。

## 界面上的两处改进

- **中断的消息可以恢复**：重启后，那些被接受但没执行完的消息会出现在对话里，显示原文、中断时间和原因，
  可以「继续发送这条」或「忽略」。**不会自动重发**（避免重复调用模型或工具）。
- **一轮为什么等这么久，看得懂了**：助手消息下可以展开耗时分解（排队 / 准备环境 / 上下文 / 记忆检索 / 模型 /
  工具 / 等待确认 / 保存 / 其它），用的是你能看懂的说法，不出现内部阶段名。

## 没有模型可用时的表现

本地嵌入模型不在时，话题判断会退到规则层。以前这一路的门槛是按另一套量纲定的，结果**假新话题高达七成**。
重新按规则层自己的真实量纲标定后：准确率 0.42 → 0.83，假新话题 0.73 → 0.19。
有模型时的判定完全不受影响（逐字段核对过）。

## 安全表述的一处更正（重要）

README 以前写「新建工具默认拿到最小能力：不联网、不碰用户文件」。这句话容易被读成
「工具做不到这些事」，而事实是：

- **网络没有强制隔离**：工具可以出网；
- **文件读取没有隔离**：工具只要知道路径，仍然能读到用户文件与 QIO 数据目录；
- 默认生效的内核级强制只有资源与进程树（Job Object）；写边界（低完整性）**默认关闭**。

正确表述是：**QIO 默认不授予工具网络访问、也不向它提供你的文件，但这不是操作系统级的强制边界。**
README 已按这个口径改，完整能力矩阵与实测证据见 `docs/security/tool-execution-isolation.md`。

## 发布流程本身

- 发布闸门现在**按实际产物判定**（不再只看源码里的配置），并且构建会产出 `build.json` 记录 commit、版本、
  两个哈希、构建期配置覆盖与签名状态 —— 闸门知道自己正在检查什么。
- 安装/卸载的注册表边界现在跑在 CI 上（windows runner 能写注册表，本机不能）。

## 已知限制

- 安装版的第三方依赖工具需要机器上有匹配的 Python（见上）。
- 网络与读取没有强制隔离。
- 界面层的验收（图形向导、界面审批、界面卸载复选框）仍需人工走一遍。
- 应用内更新需要签名产物；本轮已用正式私钥签名。
