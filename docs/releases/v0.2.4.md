# QIO v0.2.4

紧接着 0.2.3 的热修：**修掉「在互动模式点添加图片 / 添加文件，一直说附件保存失败」**。
本版在 0.2.3 基础上只改这一处（外加一条守护测试）；0.2.3 的功能与已知限制继续适用
（见 `docs/releases/v0.2.3.md`）。

## 现象

互动模式点「添加图片」（或「添加文件」）→ 选一张图 → 界面报
「附件保存失败：…；卡片已保留，可在卡片编辑里重新关联」，**每次都失败**，
而且库里连一条附件记录都没有 —— 看起来像"保存不了"，实际是请求根本没发出去。

同一个原因还影响另外三个入口（都走同一条上传路径）：

- 互动模式 卡片编辑里重新关联附件；
- 互动模式 悬浮聊天里的「选择文件」；
- 对话模式里的「选择文件」（`input[type=file]` 那条回退路径）。

**不受影响的**：对话模式里把文件**拖进输入区**或粘贴路径 —— 那条走的是"登记本地路径"，
不经过浏览器上传。

## 原因

互动模式上传附件走 `POST /api/attachments/upload`，请求带
`Content-Type: application/octet-stream` 与 `X-QIO-Name`（带话题时还有 `X-QIO-Topic-Id`）。
这三者都不在 CORS 的"安全"范围里，所以浏览器**先发一次预检（OPTIONS）**；
而后端允许的请求头白名单里没有 `X-QIO-Name` / `X-QIO-Topic-Id`
（只有 `Authorization / Content-Type / X-QIO-Session / X-QIO-Prepare-Id`）
→ 预检被回 `400 Disallowed CORS headers` → 浏览器把 POST 拦下，前端只看到一句异常。

**为什么之前没被发现**：CORS 是浏览器单方面的强制。`curl`、Python 脚本、PowerShell
发同一个请求都不会做预检，永远成功 —— 所以"后端手工测是好的"并不能证明界面能用；
而前端测试把 `fetch` 换成了替身，也照不到 CORS 这一层。同样的事在
`X-QIO-Prepare-Id` 上发生过一次（那次是"带附件发送"被挡），这次是流量更小的上传路径。

## 修法

- 把 `X-QIO-Name`、`X-QIO-Topic-Id` 加进 CORS 允许的请求头白名单（`agent/api/server.py`），
  并在注释里写清"自定义头必须逐个列出、这个坑踩过两次"。
- 新增 `tests/test_attachment_upload_cors_preflight.py`，其中一条是**枚举式守护**：
  扫描前端源码里出现的**每一个** `X-QIO-*` 请求头，逐个拿去发预检 —— 以后再加头却忘了改
  白名单，测试会直接红，而不是等用户在界面上看到「保存失败」。
- 修复前该测试是红的（`400 Disallowed CORS headers`、缺 `x-qio-name`），修复后转绿；
  既有 CORS 契约与认证测试、后端全量测试都通过。安全性未放宽：来源白名单与认证都没动，
  只是允许这两个头随请求出现。

## 已知限制

- 与 0.2.3 相同（含无边框窗口那几条），见 `docs/releases/v0.2.3.md`。
- 本版只修 CORS 这一处；0.2.3 里其它未覆盖项（候选池截断、前端未知 source 渲染等，见
  `docs/status.md` 的 P38）不在本版范围内。
