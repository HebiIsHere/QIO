## §1 冻结契约

### §1.1 回答阶段协议（问题一）

**唯一的角色判据 = 这次模型调用是否带工具**（协议事实；禁止用超时、文案内容、暂未收到工具增量判断）：

- `tools=[...]` = **工作调用**：正文是进度说明 → 过程区（`interim=true`），可多轮调用工具、可并行。
- `tools=[]` = **回答调用**：正文是正式回答 → **从第一个可发布增量起**就以 `interim=false, streaming=true` 直接进入正式回答区，边生成边显示；该调用不可能再产生工具调用，因此回答不会再被后到的工具调用打断或移走。

**何时进入回答阶段**：工作调用结束且**没有返回任何工具调用** → 工作阶段结束，循环发起**一次** `tools=[]` 的回答调用。回答调用结束时再发一条**同一 `delta_id`** 的 `{interim:false, streaming:false, content=累计全文}` 作为收尾校准（**校准不是首次展示来源**）。
当前「工具阶段收尾完全没有正文才补一次」的稀少路径**推广为常规路径**；工作调用没有产生正文时，回答调用本来就是唯一来源。

**为什么不能复用工作调用的正文当回答**：只有等它结束才知道它是不是回答，而那三个被禁的判据（超时 / 文案 / 暂无工具增量）正是唯一能提前猜的东西 —— 结果必然是「先整体搬入」或「缓存整段再播放」。把回答放进一次**发起前就知道角色**的调用，是唯一能边生成边进正文区的做法。

**工具阶段自主能力不变**：工作调用仍然带全套工具、仍然可以多轮/并行；回答调用只在工作阶段已经不再请求工具之后发生一次。

**额外调用成本（如实记录）**：每轮固定多一次纯回答调用（`tools=[]`）；最简单的问答也由 1 次变 2 次。收益是正式回答真正流式、角色不再靠猜。系统提示明确「工作阶段的文字是进度说明；不需要工具时请直接结束工作阶段，系统会给你一次不带工具的调用产出最终回答」，以尽量让工作调用不产出成段答案；若模型仍在工作阶段写了成段文字，它按事实留在过程区（**不搬动、不删除**），回答调用再产出正式回答 —— 这是本方案的已知代价。

**保留不变**：`delta_id` 稳定、累计快照、`(delta_id, seq)` 单调去重、取消/断流/重连/历史恢复、`TURN_END.final_content` 只做校准、不支持流式的 provider 如实 `streaming=false`；**已进入正式回答区的文字永不移动**。

**文档与测试同步**：`docs/architecture.md` §12.1.3、本契约与被取代的表述要一起改；**禁止**把「过程区可见」重新定义成「正式回答区流式」的通过依据。问题一由 Lead 自己收口文档。

### §1.2 附件重试复用（问题二）

**冻结接口**（B 实现服务，C 在 `api/server.py` 接线）：

```python
@dataclass
class BindOutcome:
    bound: list[str]                  # 真正绑到本轮的 attachment_id
    rejected: list[tuple[str, str]]   # (请求的 id, 人话原因)

def bind_for_turn(self, *, turn_id: str, message_id: str | None,
                  attachment_ids: list[str] | None, topic_id: str,
                  retry_of_turn_id: str | None = None) -> BindOutcome:
    """attachment_ids=None 表示字段缺失（旧客户端兜底）；[] 表示显式没有附件。"""
```

- **受理前完成校验与克隆**：请求里每个 id 必须存在、属于**同一话题**、状态允许，并且**要么未绑定，要么绑定在 `retry_of_turn_id` 那一轮**。任何不满足 → 记入 `rejected`。
- **严格语义（冻结）**：`rejected` 非空时，`POST /api/turns` **不入队**，返回结构化失败（409/422，含每个附件的人话原因）；前端保留文本与附件、显示原因、提供「移除这些附件后发送」。**不允许**静默丢弃，也不允许「后端已经开始执行后才发现附件丢失」。
- **克隆复用**：源轮上 `kind=copy` 的附件 → 为新轮**新建一条记录**（新 `attachment_id`），**复用已保存的副本内容**（优先 `os.link` 硬链接，失败退化为复制；**绝不重新依赖用户原文件**），继承 name/size/sha256/kind/display，新增 `source_attachment_id` 指向原行（**追加迁移**，不改历史迁移）。原行归属与历史**不变**，禁止解除「禁止抢走其他轮次附件」的校验。
- `kind=reference` 的克隆**重新检查当前可用性与变化**：缺失/变化如实记为 `missing`/`changed`（带原因），不沿用发送时的旧状态。
- **防偷换**：只接受「属于同一话题 + 未绑定或绑定在 `retry_of_turn_id`」的 id；不得通过任意 id 跨话题取件、抢占附件或改写已有消息归属。
- **响应回执**：受理成功的响应必须带**实际绑定结果**（`bound_attachment_ids` 与 `rejected`），前端以回执为准更新界面：未绑定的附件不得再显示为「已带上」。
- 同一逻辑要覆盖**中断恢复的重发**（`/api/turns/{id}/resend`）：从 journal 重放时同样按上述规则重新归属，不得丢附件。
- 保留：空数组 = 显式没有附件；缺字段 = 旧客户端兜底。

### §1.3 上传失败/取消收敛（问题三）

- **共享终态**：每个上传一个作业对象（队列 + `state ∈ {running, done, failed, cancelled}` + 终态原因 + 工作线程句柄）。接收端、工作线程、取消清理**都观察同一份终态**。
- 接收循环在**每次排队前**检查终态；`_upload_queue_put` 在等待空位时**必须同时观察终态**（事件/条件变量），终态一到达立即结束接收并抛出准确失败；**结束/中止哨兵不得依赖一个已经没有消费者的满队列**（用独立事件通知，或直接以「worker gone」终止接收）。
- **取消能解除工作线程的阻塞读取**；**工作线程失败能解除接收端的排队等待**（两个方向都要通）。
- **收尾**：失败/取消 → 不留临时文件、`prepared` 记录转 `failed`（带人话原因）或清理、**绝不提交 ready**；不留等待中的任务、不占线程池线程。覆盖：写盘失败（目录创建/打开临时文件/写入途中）、权限不足、超限 413、客户端断开、用户取消、服务关闭。
- **保留纪律**：有界内存与字节上限、临时文件 + `os.replace` 成功后才提交、后台文件 I/O、**数据库只在事件循环线程访问**。
- **禁止**：把队列改成无限大；在事件循环线程同步写盘。
