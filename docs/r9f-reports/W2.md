## 2. launch.py 与契约 §3.3 的 API 校验结论

契约冻结的四个类型/入口全部按原样实现（`backend/src/agent/security/launch.py`）：

- `LaunchSpec(kind, program, argv, cwd, shell_cmd, script_source, script_name, timeout)`：字段与契约一致（含默认值）；
- `LaunchPermit(permit_id, spec_digest, authorized, mode, allowed_roots, allowed_operations, network_hosts, internal_data_confirmed, requirement_id, approval_id, source, reason)`：字段与契约一致；`source` 只取 instruction / approval / unrestricted；
- `LaunchResult(ok, returncode, stdout, stderr, category, error, guard, isolation, spec_digest)`：字段与契约一致（category 额外允许 permit_mismatch / boundary_unavailable / boundary_unverified 等，用于明确「不可用」）；
- `ControlledLauncher.launch(spec, permit)`：`async`；在契约签名基础上只增加**向后兼容的可选关键字参数** `enforce_write_scope=False`、`env=None`。

为让工具层复用同一组组件，额外导出（不改契约类型）：
`build_spec_facts`、`compute_spec_digest`、`build_permit`、`recheck_approved_spec`、`write_roots_for`、`normalize_mode_value`，
以及 `ControlledLauncher.prepare / apply_isolation / postflight`（sandbox 复用；见 §4.4）。

**重要：launch.py 不做权限判定。** 能不能执行由 AuthorizationEngine/用户审批决定；launch.py 只保证「决定之后真正启动的仍是决定时的那个东西，且执行边界与决定时一致」。

## 3. 调用链变化图

改动前（问题 A）：

```
RunProgramTool.run ──> security_gate.authorize ──> asyncio.create_subprocess_exec(program, *args)
RunCmdTool.run     ──> security_gate.authorize ──> asyncio.create_subprocess_shell(cmd)
SandboxExecutor._execute_subprocess ──> create_subprocess_exec(worker) + isolation.harden + ExecutionGuard
审批重放: _ApprovedReplayGateway.authorize() ⇒ 无条件 ALLOW ⇒ 同上直接启动
```

改动后：

```
RunProgramTool.run / RunCmdTool.run
  ├─ 只读模式执行层兜底（可证明只读的 argv 才能继续；否则拒绝）
  ├─ security_gate.authorize(effect)            # 唯一权限判定（引擎/审批）
  ├─ 内部数据明确提及 → 提交「连续三次确认」待审批（不直接执行）
  ├─ 构造 LaunchSpec(kind=program|shell, program/argv/cwd/shell_cmd/timeout)
  ├─ 构造 LaunchPermit（mode、allowed_operations=execute|execute_readonly、
  │     allowed_roots=工作区根（只读=空）、内部数据确认状态、审批来源）
  └─ ControlledLauncher.launch(spec, permit)
        ├─ prepare(): permit.authorized / 模式重核对（切只读→失效）/
        │    权限操作标记 / **spec_digest 重算** / 内部数据未确认拒绝 /
        │    网络白名单→明确不可用 / 写范围目录存在性
        ├─ 执行前 ExecutionGuard 快照（受保护范围 = 工作区根 + QIO 内部数据）
        ├─ 真实 spawn（argv 由 spec 解析：程序真实路径 / COMSPEC / 引导脚本）
        ├─ apply_isolation() → isolation.harden：Job Object（KILL_ON_JOB_CLOSE、
        │    内存/活动进程上限）+ 按模式/许可强制的 Low IL；要求但核实不了 → 不启动
        ├─ script 类型：隔离核实后才写「放行信号」，用户脚本副作用不在隔离前发生
        ├─ 超时/取消/输出超限 → 只收本次进程树，语义与旧 _run_child 一致
        ├─ postflight(): 执行后再算 spec_digest + 临时脚本/引导文件内容核对
        └─ 执行后 ExecutionGuard 比对：授权写范围内的改动=authorized_write；
             QIO 自身 db/log（启动前快照里的确切条目）=self_writes（带证据）；
             其余=violations → boundary_violation
  └─ LaunchResult → ToolResult（退出码/超时/启动失败/许可失效语义保持不变）

审批重放：execute_proc_run_program / execute_proc_shell
  ├─ payload 必须与审批单 payload 完全一致（否则 invalidated）
  ├─ recheck_approved_spec(spec, fingerprint, effect, payload)
  │    spec_digest（含程序内容/argv/cwd/脚本内容）、program_sha256、payload_digest、
  │    effect 快照 argv/command/cwd —— 任一不一致 → invalidated、不执行
  ├─ 当前模式切到只读 → invalidated（审批不能绕过只读）
  ├─ build_permit(source="approval", approval_id=ctx.approval_id)
  ├─ RunProgramTool/RunCmdTool(security=_ApprovedReplayGateway(operation=...))
  │    authorize()：核对 effect 与审批记录一致才返回有界 ALLOW；否则 DENY
  └─ ControlledLauncher.launch（同一执行边界）

自建工具：SandboxExecutor._execute_subprocess
  ├─ 构造 worker 的 LaunchSpec(kind=script；program=解释器、argv、cwd=临时目录、
  │    script_source=code+files+entry 规范化 JSON)
  ├─ ControlledLauncher.prepare()（与命令行同一套 spec_digest/内部数据/操作核对）
  ├─ create_subprocess_exec（原有 worker 协议不变）
  ├─ launcher.apply_isolation()（内部仍是 isolation.harden，参数与既有语义一致）
  ├─ 原有 ExecutionGuard + _parse_worker_result（SandboxResult 语义不变）
  └─ launcher.postflight()（执行后再核对 worker/脚本摘要）
```

## 4. 分文件改动

### 4.1 新增 `backend/src/agent/security/launch.py`

- **spec_digest 规范化事实**：程序（解析后真实路径 + 文件身份 + 大小/mtime + 内容 sha256）；
  shell 时是解析后的 COMSPEC/sh 身份；argv、解析后的 cwd、shell 文本、script_source；
  **argv/命令里作为脚本文件出现的参数**（.py/.js/.sh/.ps1/.bat/.cmd… 或无后缀但带 shebang）
  记录内容 sha256（相对路径按 spec.cwd 解析；提交时不存在也记录 exists=false）。
- **执行前后核对**：launch 启动前重算并与 permit 比较；结束后再算一次；script 类型核对临时脚本/引导文件内容。
- **模式/许可重核对**：当前模式切到只读 → 旧许可不启动；许可必须含 execute（只读只能用 execute_readonly 标记且不得带写范围）。
- **内部运行数据**：spec 明确提到内部数据路径且 permit.internal_data_confirmed=False → 拒绝（「连续三次确认」）。
- **网络**：permit 显式声明 network_hosts → 明确「暂不可用」（本机无 WFP/防火墙集成）；未声明 → 结果标注 network_not_isolated。
- **隔离**：isolation.harden（Job Object 默认；Low IL 按模式/许可强制）+ 要求核实不了就不启动（不静默降级）。
  默认**不**对工作区递归打 Low 标签；enforce_write_scope=True 才把 allowed_roots 临时打 Low（执行后恢复 Medium，并留恢复证据）。
- **事后 guard**：只做补充审计；授权写范围内=authorized_changes；QIO 自身 db/log 按启动前快照确切条目=self_writes（证据随结果返回，不整类排除）；其余=violations。
- **收尾**：proc_cleanup.terminate_process_tree 退出验证（清理未确认会如实说）；Job 句柄随调用释放。

### 4.2 `backend/src/agent/tools/cmd_tools.py`

- RunProgramTool/RunCmdTool 的真实启动全部改走 ControlledLauncher.launch；保留：
  永久删除命令名拦截、只读 argv 证明兜底、退出码事实、超时/取消收尾与「清理未确认」语义、输出截断。
- 审批提交指纹补齐：spec_digest + program_sha256 + payload_digest + allowed_roots + internal_data_roots（供重放前重核对）。
- 命令/参数明确提到内部运行数据 → 以 confirmations_required=3 提交待审批，不直接执行。
- 结果通过 facts.launch_boundary 携带 spec_digest / isolation mechanisms / write_scope.pre_enforced / guard.boundary / capability_boundaries（不改模型正文语义）。

### 4.3 `backend/src/agent/tools/approved_operations.py`

- _ApprovedReplayGateway.authorize() **删除无条件 ALLOW**：
  - 当前模式 read_only → DENY（审批不能绕过只读）；
  - 没有审批记录快照 → DENY（无法核对即不放行）；
  - 操作类型 / argv / shell 命令 / 对象·cwd 与审批记录不一致 → DENY（「审批失效」）；
  - 一致时返回**有界** ALLOW（reason 明确「只免去重复询问；执行边界仍生效」）。
- execute_proc_run_program/execute_proc_shell：payload 必须与审批 payload 相同 → 指纹/spec_digest/effect 重核对 → 构造 source=approval 的 permit → 交给工具（工具仍走同一授权入口与受控启动）。
- 附件写回/读取/回收函数未重构（留给 Lead 合并 W3 冲突）。

### 4.4 `backend/src/agent/tools/sandbox.py`

- 自建工具 worker 启动复用 ControlledLauncher.prepare/apply_isolation/postflight（同一 spec 摘要与隔离/事后核对组件）；
  SandboxResult 字段、guard、协议解析、超时/取消语义不变；容器（docker）路径未改（容器自身隔离）。

## 7. 能力边界（必须和结论一起读）

1. **网络没有强制隔离**：本机没有 WFP/防火墙集成。launcher 能做的只是「声明主机白名单时明确暂不可用」+「未声明时如实标注 network_not_isolated」；不能阻止脚本外发。
2. **读没有隔离**：Low IL 不阻止读取当前账户可读内容（包括凭据文件，若 ACL 允许）。
3. **任意程序/shell 的写范围默认不事前强制**：普通命令的 allowed_roots 只用于**事后**分类，结果标注 write_scope_not_pre_enforced / boundary=post_checked_only。事前强制（enforce_write_scope=True）只建议小范围/验证场景使用。
4. **Low IL 写边界有前提**：把 allowed_roots 临时打 Low 标签需要调用方对这些目录有 **WRITE_OWNER**。
   - 本机实测：C:\Users\...\Temp（用户目录，FullControl）可打标签；D:\qio-dev 仓库目录（Authenticated Users 只有 Modify）icacls /setintegritylevel 被拒（Access denied）。
   - 行为：launcher 明确返回 boundary_unavailable（不静默降级、不把「没打上标签」说成有边界）。真机脚本因此把「可打标签的工作目录」放在系统临时目录，证据仍写回 _r9f-evidence/。
   - 生产含义：用户工作区若同样是「继承来的 Modify」ACL，enforce_write_scope 路径只会明确不可用；普通命令走的是「审批 + 事后核验」边界。
5. **解释器内部删除不能强制进回收站**：Low IL 只阻止写更高完整性对象；在**获准写范围内**（Low 标签目录）脚本可以直接 unlink，QIO 不能把删除改道系统回收站。能力边界在结果 capability_boundaries.delete_not_recycled_within_allowed_roots 明确列出。
6. **program/shell 存在极短启动窗口**：isolation.harden 是进程创建后立即施加的追加式钩子，不能声称「启动前就拦住」。script 类型通过「引导脚本等放行信号」消除了用户脚本在隔离前执行的窗口；program/shell 没有 stdin 握手，只能依赖授权 + Job/Low IL 立即施加 + 事后 guard。
7. **事后 guard 只是补充审计**：不能回滚已发生的修改；QIO 自身 db/log 与脚本写入无法区分（按启动前快照里的确切条目归为 self_writes 并留证据，不整类排除）；受保护范围默认只有工作区根 + AppContext 内部数据，工作区外的用户文件不在快照范围（需要 Lead 在集成时提供更完整保护范围）。
8. **argv 脚本文件识别是启发式**：按后缀/shebang 识别「作为参数传入的脚本文件」；通过 -c 内联代码、运行期动态拼接路径、解释器读取的数据文件、脚本 import 的其他模块等不在 digest 内（这些内容变化不会被事前拒绝，只能靠事后 guard 发现副作用）。
9. **POSIX**：isolation 明确 unsupported；launcher 不误拒普通命令，只在结果标注 posix_no_forced_isolation（行为与改动前一致）。
10. **审批/授权记录 vs permit 的字段对接**：W1 的 AuthorizationRecord/审查结果最终由 Lead 在集成层填入 permit（requirement_id 字段已预留）；W2 不在 launcher 里做权限判定或授权缓存。

## 8. 未完成项 / 给 Lead 的集成建议

6. **超时结果不含 stdout/stderr**：与改动前 cmd_tools 语义一致；若模型需要「超时前输出」，可后续在 _collect 里保留部分缓冲。
