## 1. 做了什么

### 1.1 新增 `backend/src/agent/services/file_origins.py`

* 三来源常量：`user_original` / `user_saved_material` / `qio_generated`；
* `FileOriginRecord` 与迁移 55 的 `file_origins` 一一对应（volume/file_id/path/origin/source/attachment_id/created_at/updated_at/missing_at）；
* `FileOriginStore(conn, workspace_root)`：
  - `record_created`：**仅在受控创建成功后**调用；已有用户来源记录不得被改写为 generated（防「已存在用户文件冒充生成物」二次校验）；
  - `record_existing_file`：登记/观测已有用户文件（桌面路径、上传材料、历史行回退），保留用户来源；
  - `lookup`：**身份优先**（volume+file_id），身份读不到才退回同路径（文件缺失/移动后的历史查询）；身份已知但无记录 → 返回 None（外部替换不继承）；
  - `is_generated`；`update_after_replace`：原子替换/写回后迁移身份键并**保留来源**；`mark_missing`：删除/回收后保留事实只标 missing；`update_path`：同身份移动后更新路径；
  - 全部 fail-soft：表缺失/连接异常/DB 错误返回 None，不影响真实文件操作；
  - 持久化到 sqlite（迁移 55），进程重启后同一 DB 可查。
* 进程级统一查询入口（fs 与附件共用同一 store）：`set_default_store` / `default_store`、`set_attachment_origin_provider`（附件行回退：老附件行没有 file_origins 行时按 identity+file_id 核实后回填）、`origin_for_path` / `record_for_path` / `mark_missing_path`；
* 给 approved_operations 的接线 helper（W3 不直接改该文件）：`snapshot_before_write`、`note_authorized_write_path`、`note_recycled_path`。

### 1.2 `tools/fs_tools.py`

* `_FsTool.inject` 增加可选 `origins`（`ServiceRegistry.attach` 若注册了同名服务会自动注入；未注入时用进程默认 store）；
* `fs_write`：授权前查后端来源，`effect.detail["file_origin"]`（新文件创建前为 None）与 `file_exists` 传给授权引擎；**写成功返回后**记账：已有记录 → 身份更新保留来源；写前存在无记录 → `user_original`；写前不存在 → `qio_generated`（真实创建成功后）；
* `fs_patch`：同样把后端核实来源放进 effect.detail；写后保留来源、更新身份；
* `fs_delete`：多目标逐条查来源，`detail["file_origins"]`（逐条）与单目标 `detail["file_origin"]` 传引擎；**成功移入回收站后** `mark_missing`（保留来源事实）；
* 模型传入的 `origin` 字段被忽略（工具只读取 path/content/paths），不进入 effect。

### 1.3 `services/attachments.py`

* 构造时创建 `self.file_origins = FileOriginStore(conn, workspace_dir)`，并设为进程默认 store / 附件行回退 provider（app.py 无需改动即可让 fs 工具查到附件路径）；
* 记账点：
  - `register_source`（桌面/拖放登记）→ `user_original` + attachment_id；
  - `write_material` / `write_material_bytes` / `apply_material_outcome`（上传/剪贴板首次落盘成功）→ `user_saved_material`；
  - `write_back_source`（allow 路径）→ 写回成功后调用 `note_origin_after_write_back`：身份更新、来源保留（用户文件不会变成生成物）；
  - `recycle_material_files`（allow 路径）→ 每个成功项 `mark_missing`（来源事实保留）；
  - `_origin_from_attachment_row`：老附件行回退查询，校验当前文件身份与附件 file_id 一致（外部替换不继承）。

## 2. 记账规则（后端事实，非模型声明）

| 场景 | 来源 | 身份处理 |
| --- | --- | --- |
| fs_write 新建文件成功 | `qio_generated` | 创建后的真实 identity 落库 |
| fs_write / fs_patch 编辑已有生成物 | 保留 `qio_generated` | 原子替换后的新 identity 更新到同一行 |
| fs_write / fs_patch 写已存在但无记录的文件 | `user_original`（保守） | 同上；**绝不冒充 generated** |
| 桌面/拖放登记附件 | `user_original` | 登记时 identity + attachment_id |
| 上传/剪贴板首次落盘成功 | `user_saved_material` | 落盘后真实 identity |
| 附件写回源文件成功 | 保留原来源（用户文件仍 user_original） | 原子替换改变身份 → 更新身份键 |
| fs_delete / 附件回收成功 | 保留原来源 | 只写 `missing_at`（重启后历史归属可查） |
| 外部程序替换同名文件 | 不继承旧来源 | 身份不同 → lookup 返回 None；再写按 user_original 保守处理 |
| 文件同卷移动/改名 | 不变 | 身份相同 → 仍可查；`update_path` 更新路径 |

## 4. Lead/W2 接线示例

### 4.1 引擎/Gateway（Lead）

    from agent.services import file_origins as origin_store

    gateway = AuthorizationGateway(
        ...,
        origin_provider=lambda path: origin_store.origin_for_path(path),
        reviewer=...,
    )

* `origin_provider` 必须查 `FileOriginStore`（后端事实），不得读模型传入的 `origin` 字段；
  fs 工具的 `effect.detail["file_origin"]` / `detail["file_origins"]` 只是同一次查询的结果，Gateway 可再核对；
* `FileOriginStore` 由 `AttachmentService` 构造时自动设为进程默认 store；建议 app.py 再把
  `services.register("origins", ctx.attachments.file_origins)`，`fs_tools` 的 `inject` 已包含
  `"origins"`，注册后即为显式注入（未注册也走默认 store，功能等价）。

### 4.2 approved_operations.py（W2 负责；W3 已撤回到基线，只给 helper）

| 函数 | 调用点 | 建议调用 |
| --- | --- | --- |
| `execute_fs_write` | 写前 | `pre_record = file_origins.snapshot_before_write(path)`；`existed_before = Path(path).exists()` |
| `execute_fs_write` | `atomic_write_text` 成功后 | `file_origins.note_authorized_write_path(path, existed_before=existed_before, pre_record=pre_record, source="approved.fs_write")` |
| `execute_fs_patch` | 写前 / 成功后 | 同上（`source="approved.fs_patch"`，`existed_before=True`） |
| `execute_fs_delete` | 每个 `ok=True` 后 | `file_origins.note_recycled_path(path)` |
| `execute_attachment_write_back` | `_write_back_source_now` 成功后 | `service.note_origin_after_write_back(attachment_id, outcome)` |
| `execute_attachment_recycle` | 每个成功项后 | `file_origins.note_recycled_path(path)`（或附件服务可用时 `service.note_origin_after_recycle(path)`） |

不接这些调用的后果（如实）：批准路径创建/写回的文件不会被记账 → 后续 fs 查询按「未知」
保守当 user_original，QIO 自主整理会再次要求审批（不是安全问题，是体验/正确性退化）。
非批准 allow 路径（attachments.write_back_source / recycle_material_files）已在本分支内自行记账。
