## 3. 审查输入如何组装（模型不能选择性提交）

`build_review_payload` 唯一入口，payload 结构（稳定 JSON，审计摘要与模型输入同源）：

```json
{
  "prompt_version": "r9f-auth-review-v1",
  "mode": "restricted",
  "requirement": {"requirement_id": "...", "text": "用户原话", "provenance": {...},
                  "parent_id": null, "status": "active", "limits": ["..."]},
  "corrections": ["用户后续修正原话"],
  "user_limits": ["..."],
  "user_constraints": ["..."],
  "operation": {"kind": "write",
                "objects": [{"kind": "path", "value": "D:/...", "identity_key": "...", "file_origin": "user_original"}],
                "program": null, "argv": [], "cwd": null, "script_sha256": null,
                "network_hosts": [], "summary": "后端给出的用途摘要"},
  "related_grants": [...], "prior_decisions": [...], "approvals": [...],
  "untrusted_material": [{"source": "file|web|tool|quote", "label": "...", "content": "..."}]
}
```

边界与裁剪（防止把整段文件/网页塞进"用户要求"区）：

| 字段 | 上限 |
| --- | --- |
| requirement.text | 6000 字符（超出标记 `…（已截断）`） |
| corrections / 条目 | 每段 1000、最多 8 |
| limits / user_constraints | 每条 300、最多 20 |
| operation.objects | 最多 20，value 截断 1000 |
| argv / network_hosts | 最多 32 / 16 |
| 上下文记录（grants/prior/approvals） | 每项 JSON 2000 字符、最多 12 项 |
| untrusted_material | 每项 4000 字符、最多 8 项 |

关键边界：文件/网页/工具结果/引用内容只进 `untrusted_material`（或留在用户原话引号内但不作为操作依据），
不会混入 `requirement.text`；后端也不从模型读取"用户已授权"这类字段。

## 4. 模型调用边界（契约 §3.2）

- 复用用户已配置主模型：生产接线传 `ctx.build_adapter`；每次审查一次普通 `adapter.complete(messages, tools=[])`，**不**新建 Agent、不暴露工具/文件/设置能力。
- 提示词只来自 `agent/prompts.py`；`review.py` 只组装后端核实数据并渲染。
- 默认超时 20 秒（`DEFAULT_TIMEOUT_SECONDS`；调用方可用 `timeout_seconds` 调整，eval 用 45 秒）。超时是硬超时。
- 以下一律抛 `ReviewUnavailable`（调用方必须映射为 APPROVE/DENY，**不得** ALLOW）：
  无适配器（无可用主模型配置）、模型抛异常、超时、返回空、非 JSON、JSON 结构/类型非法、validate_outcome 不通过、
  模式不是 restricted、要求不存在/非 active。
- `model_call` 可选注入（测试/评测抓取原始输出用）；生产不传。
- 可选 `audit=ReviewAuditLedger(conn)`：自动写 `authorization_review_audit`；审计写失败只记 warning，不改变判定。

## 5. `validate_outcome` 校验清单（后端最终把关）

1. 结构与类型：outcome 是 ReviewOutcome、decision 合法、reason 非空、字段类型合法。
2. 请求结构：requirement 有真实 id；operation 是 ReviewOperation；objects 是 ReviewObject；mode == restricted；操作类型在可审查集合内。
3. requirement_id 必须是**当前要求或其父要求**（真实存在），且该要求状态必须 `active`（修正/撤回/替换后不可用）。
4. objects / allowed_operations ⊆ 请求集合：
   - 对象按 kind + 规范化值匹配；身份键/文件来源以**请求（后端核实值）**为准；
   - 模型省略身份/来源可以（后端规范化补回），但给出与请求不同的 identity_key/file_origin、或新对象 → 拒绝；
   - allowed_operations 只能包含本次 operation.kind（write 不能扩成 delete/execute 等）。
5. ALLOW 额外硬条件：
   - 覆盖请求中的**全部**对象（不能只授权一部分）；写/建/删类操作不得空对象 ALLOW；
   - allowed_operations 非空；limits 非空；purpose 非空；
   - 通过确定性兜底（§6）；
   - 返回 canonical ReviewOutcome：objects 用请求对象（顺序/身份/来源来自后端），requirement_id 归一到当前要求。
6. CONFIRM/DENY：reason 非空；若给 objects/allowed_operations，必须是请求子集（用于审批单展示），同样不能扩操作类型。
7. 任何不通过 → `ReviewUnavailable`；不猜测、不修补、不默认允许。

## 6. 确定性兜底（只收紧、不放宽）

即使模型误判为 allow，以下情况也**不会**被后端接受（抛 ReviewUnavailable，接线方按 APPROVE 处理）：

- 用户原话（含 corrections）明确否定本次/同类操作：如"不要修改 X""禁止写入 X""别改这个文件"；
- 疑问句 / 条件句 / 假设：如"如果可以的话""如果测试通过就…""…好吗？"（条件无法由后端核实）；
- 存在引用/不可信材料时，去掉引号内文字后用户原话没有明确要求这次操作（材料里的"允许/请执行/已授权"不构成授权）。

反向豁免（避免误伤合法请求）："别改**其他**内容 / 不要删除**其他**文件 / 别动**其他**部分"属于对**范围外**对象的限制，
不会被当成否定本次操作；第一轮真实模型评估正因这条误伤而发现并修复（见 §10）。

## 7. 缓存键与失效规则

`operation_fingerprint(operation, mode)` = sha256(稳定 JSON)，涵盖：

- mode（模式变化 → 指纹变化）
- operation.kind
- objects：kind + 规范化值（路径 normpath/normcase、service 小写）+ identity_key + file_origin（对象身份变化 → 必须重判）
- program（规范化路径）、argv、cwd、script_sha256、network_hosts（排序去重、小写）

`AuthorizationLedger.reuse` 命中条件（全部满足）：

1. `requirement_id + operation_kind + fingerprint` 精确相等；
2. `decision == "allow"`；
3. `revoked_at IS NULL`，且 `expires_at` 为空或在未来；
4. 对应 `user_requirements.status == "active"`（JOIN 校验）。

失效事件：

| 事件 | 效果 |
| --- | --- |
| 新用户消息（新 requirement） | 新 id，不命中旧记录（天然重判） |
| 修正（add_correction） | 父要求 superseded、父链记录撤销；子要求 active |
| 撤回（withdraw） | 要求及后代 withdrawn、记录撤销 |
| 替换（supersede） | 要求 superseded、记录撤销 |
| 对象身份变化（同路径换文件/移动） | fingerprint 变化，不命中 |
| 新程序 / 新 argv / 新 cwd / 脚本内容变化 | fingerprint 变化，不命中 |
| 新接收方（network_hosts 变化） | fingerprint 变化，不命中 |
| 模式变化 | fingerprint 变化，不命中（无需额外清库） |
| 记录过期/显式 revoke | reuse 不命中 |
| 进程重启 | 全部从 SQLite 重建（无内存唯一副本） |

## 8. 生命周期语义

- `record_user_message`：每条用户消息一条 active 要求，**不自动 supersede** 其它要求；原话原样保存，provenance 记录来源。
  这样"新消息 = 新要求"天然不会复用旧授权；是否延续/替换由调用方显式表达（修正用 add_correction，替换用 supersede）。
- `add_correction`：append 子要求（parent_id 指向被修正要求），父要求 superseded + 父链授权记录撤销；
  limits 继承父要求并追加本次修正原话（契约 limits 定义包含"后续修正"）。
- `withdraw`：要求及全部后代 withdrawn，全部记录撤销；`supersede`：显式替换当前要求并撤销记录。
- 重启：RequirementLedger / AuthorizationLedger 构造只依赖 db 连接，所有状态从库重建（测试覆盖）。

## 9. 审查审计（迁移 55 `authorization_review_audit`）

- `ReviewAuditLedger.record` 记录：requirement_id、request_digest（sha256(payload)）、model、
  prompt_version（当前 `r9f-auth-review-v1`）、outcome（allow/confirm/deny/unavailable）、decision、reason（≤500）、
  latency_ms、error（脱敏后 ≤300）、created_at。
- **不**落模型推理全文、不落材料原文、不落密钥；错误文本经 `trace/redact.py::sanitize_error_text`。
- 是否启用由接线方决定：`ModelAuthorizationReviewer(..., audit=ReviewAuditLedger(conn))`；不传则调用方自行写。

### 10.3 首轮真实评估发现并修复的问题（诚实记录）

首轮证据 `...-141621.json`：`allow_two_files_same_operation`（"别改其他内容"）被判 unavailable，
原因是确定性否定守卫把"别改**其他**内容"误当成否定本次操作。修复：否定词后紧跟"其他/其它/别的/其余/之外/无关"等
视为**范围限制**而非拒绝；补充单测 `test_guard_does_not_treat_scope_limit_as_refusal`；重跑后 0 误授权 / 0 漏授权。

### 10.4 局限（不得夸大）

- 单一模型、单次运行、18 条合成案例；不能代表所有真实用户表达，也不构成模型稳定性统计。
- 模型或提示词版本变化需重跑；证据只对 `r9f-auth-review-v1` + 上述模型有效。
- 预期结果来自人工标注（非模型自评）；案例集 tune/holdout 划分仅为报告分组，本轮没有用 holdout 调提示词。

## 12. Lead 接线最小示例（engine/gateway 接入，本轮不实现）

```python
# 1) AppContext.__init__（Lead 接线位置）
from agent.security.requirements import RequirementLedger, AuthorizationLedger
from agent.security.review import ModelAuthorizationReviewer, ReviewAuditLedger

self.requirements = RequirementLedger(conn)
self.authorization_records = AuthorizationLedger(conn)
self.review_audit = ReviewAuditLedger(conn)
self.reviewer = ModelAuthorizationReviewer(
    adapter_factory=self.build_adapter,          # 复用用户已配置主模型
    timeout_seconds=20.0,
    audit=self.review_audit,                     # 可选：自动写 authorization_review_audit
)

# 2) 每轮用户消息开始（在 InstructionRegistry.begin 附近）
requirement = ctx.requirements.record_user_message(
    text=user_text, message_id=message_id, turn_id=turn_id, topic_id=topic_id
)
# 用户明确修正上一条要求时改用（由 Lead 判定"这是修正"）：
#   requirement = ctx.requirements.add_correction(prev.requirement_id, correction_text, message_id=message_id)

# 3) 受限模式中需要自然语言理解的操作（engine._restricted 返回 REVIEW 信号后由 Gateway 调用）
from agent.security.review import (
    ReviewRequest, ReviewOperation, ReviewObject, ReviewDecision,
    ReviewUnavailable, operation_fingerprint, validate_outcome,
)
from agent.security.requirements import authorization_record_from_outcome

async def decide_by_review(requirement, effect_kind, backend_objects, program, argv, cwd,
                           script_sha256, network_hosts, summary, grants, prior, approvals,
                           constraints, untrusted, mode_value):
    # backend_objects / program / argv / cwd / script_sha256 / network_hosts 必须来自后端核实
    # （file_identity、FileOriginStore、启动解析等），不能采信模型传入的路径/来源/身份。
    operation = ReviewOperation(
        kind=effect_kind, objects=tuple(backend_objects), program=program, argv=tuple(argv),
        cwd=cwd, script_sha256=script_sha256, network_hosts=tuple(network_hosts), summary=summary,
    )
    fingerprint = operation_fingerprint(operation, mode=mode_value)
    cached = ctx.authorization_records.reuse(
        requirement_id=requirement.requirement_id, operation_kind=operation.kind, fingerprint=fingerprint
    )
    if cached is not None:
        return Verdict.ALLOW, cached.reason, cached.record_id       # 同范围复用，不反复审批

    request = ReviewRequest(
        requirement=requirement,
        corrections=ctx.requirements.corrections_for(requirement.requirement_id),
        limits=requirement.limits,
        mode=mode_value,
        operation=operation,
        related_grants=tuple(grants), prior_decisions=tuple(prior), approvals=tuple(approvals),
        user_constraints=tuple(constraints),
        untrusted_material=tuple(untrusted),    # 文件/网页/工具结果内容，只能作为不可信材料
    )
    try:
        outcome = await ctx.reviewer.review(request)
    except ReviewUnavailable as exc:
        # 不可用不能默认允许：返回普通审批（审批单列明对象/操作/依据），不自动切模式
        return Verdict.APPROVE, "暂时无法确认授权范围：" + str(exc) + "；可对明确的具体操作手动审批", None

    if outcome.decision == ReviewDecision.ALLOW:
        record = authorization_record_from_outcome(outcome, request=request)
        ctx.authorization_records.record(record)                   # 有界记录；重启后可重建
        return Verdict.ALLOW, outcome.reason, record.record_id
    if outcome.decision == ReviewDecision.CONFIRM:
        return Verdict.APPROVE, outcome.reason, None               # 转普通用户审批（审批单列对象/操作/依据）
    return Verdict.DENY, outcome.reason, None                      # 用户明确反对/冲突，不转审批
```

接线要点：
- 固定规则（读取、QIO 生成文件、应用受控数据、内部数据三次确认等）由 engine 先判；**只有**需要自然语言理解的
  写/删/执行/外发/系统变更才进入模型审查；read_only / unrestricted 不调用 reviewer。
- `ReviewUnavailable` → APPROVE（人工审批），不自动允许、不自动切模式。
- 审查 ALLOW 后才能 `authorization_record_from_outcome` + `record`；CONFIRM/DENY 不写 allow 记录。
- engine 不要直接持有 async 模型调用（契约 §3.5）；async 在 Gateway 层。

## 13. 与冻结契约的偏差 / 补充（均为向后兼容的追加）

1. **ReviewRequest.untrusted_material（可选，默认空）**：契约 §3.2 dataclass 清单未列，但同节"模型调用规范"明确要求
   "文件/网页/工具结果内容作为 untrusted_material 单独标注"。按可选字段加入，不改变既有字段顺序/构造方式。
2. **ReviewAuditLedger 放在 review.py**：契约未指定审查审计写入归属；实现为可选参数（不传不影响判定），
   表结构沿用迁移 55 的 authorization_review_audit。
3. **确定性兜底**（否定/条件/引用材料）超出契约 validate_outcome 文字清单：只收紧、不放宽（最多把 allow 变成
   ReviewUnavailable→APPROVE），不会把不允许变成允许；"其他/其它/别的/其余/之外/无关"范围限制有豁免。
4. **record_user_message 不自动 supersede**：契约给了显式 supersede/add_correction 入口；由调用方表达"替换/修正"。
   这样新消息天然重判，也不会误伤同一要求内的复用；若 Lead 希望"新消息即替换旧要求"，在 record 后调用 supersede 即可。
5. **附加只读/便捷方法**（chain / corrections_for / records_for_requirement / authorization_record_from_outcome）：
   契约外新增，不改既有签名；用于组装审查输入和复用夹具。
6. 提示词常量命名：`AUTHORIZATION_REVIEW_SCHEMA_VERSION` 同时承担"提示词/输出契约版本号"，
   写入审计 prompt_version；如需单独 `AUTHORIZATION_REVIEW_SCHEMA` 名称，Lead 可加别名（本轮未加）。
