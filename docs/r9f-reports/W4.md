### 1.5 结论与具体改法（数据支撑）

**结论 1（不是 offload 回归）**：修复后的 offload 段本身 p50 19.1ms / max 57.5ms（20 次）；
两个失败用例量的是整轮（本地整轮 0.95–1.5s），其中同步段分散在
`append_message / instance_registry.claim / turn_journal / trace.finish / tiktoken / pydantic /
惰性导入`，单段 10–170ms。CI 上这些段随 runner 变慢并被心跳合并，读数自然升高；而回归签名
（整段 0.2s 召回串行跑在事件循环上 ≈446ms）在本地从未出现。

**结论 2（HEAD vs 对照）**：空载 p50 HEAD 比 R9 集成/基线高 19/21ms（turn-recall）、10/4ms
（turn-predict），max 差 100ms 级；**没有** 446ms 级签名。如实说明：三棵是顺序测量且 HEAD 最先跑
（文件缓存/预热状态不同），这个量级还不能判成回归；要判定需同机交替重复（脚本已支持 `--label`
多轮）。不把它写成“R9-F 引入回归”。

**结论 3（测量方式问题，给出改法）**：`test_a_slow_retrieval_does_not_stall_the_turn_loop`
与 `test_health_probe_stays_responsive_while_slow_prediction_runs` 都把**整轮**的最大 gap 与固定
300ms 比较；整轮里绝大多数同步段与“慢检索有没有被搬走”无关，且共享 runner 的调度地板会漂移
（本地 CPU 压力 p90 已达 304ms）。改法（二选一，均保留检测力）：

```python
# 方案 A（推荐，与同文件 test_slow_retrieval_does_not_block_the_loop 同一口径）：
# 只量刺激段 —— 慢检索/慢推理在不在事件循环上，用这一段的 gap 判定。
async def test_a_slow_retrieval_does_not_stall_the_turn_loop(ctx, topic, monkeypatch):
    slow = _SlowRecall(delay=RECALL_STIMULUS_SECONDS)
    monkeypatch.setattr(ctx.selector, "recall", slow)
    _, gap_ms = await _measure_loop_lag(
        lambda: ctx.heavy.run(ctx.build_injection, "回忆一下之前的偏好",
                              topic_id=topic, short_term=[])
    )
    assert slow.searches >= 1
    budget = loop_stall_budget_ms(RECALL_STIMULUS_SECONDS * 1000)  # 300ms；回归签名=200ms 整段
    assert gap_ms < budget
```

- 回归时（召回被搬回事件循环）这一段 gap ≈ 刺激时长（200ms）且往往成倍；预算 300ms 仍能抓住
  “整段串行”的 446ms 签名，同时不再把轮末 DB/trace/tiktoken 的调度抖动算进来。
- 方案 B（保留整轮口径）：用**刺激窗口 marks** 只统计与召回重叠的 gap（脚本里的 `marks` 已经
  这样做），或对 N 次重复取中位数而不是单次 max —— 都不是“抬高阈值”。
- **不要**把 300ms 直接改大：本地压力对照已证明该数在负载下低于环境地板，改大只会掩盖真实阻塞。
- 另：整轮同步段本身（`append_message` 的 fragment 事务、`instance_registry.claim`、
  `turn_journal`、`trace.finish`、tiktoken、pydantic schema 首建）是**产品侧可优化项**，
  与本次 CI 归因分开记录，供后续任务评估（W4 不改产品代码）。
