## 1. 产品规则（所有工作流共同遵守）

### 1.1 三种模式

* `read_only`：默认允许普通读取；不允许业务修改及无法证明只读的执行；内部维护保留既定三次确认流程。
* `restricted`（默认）：用户明确授权及完成既定目标所需操作按既定规则判断；需要理解授权范围时使用
  模型语义审查；模型不可用时针对具体操作确认。
* `unrestricted`：普通操作不增加常规审批，不调用普通独立授权审查；已知用户禁止、子智能体边界和
  内部维护三次确认仍然有效。

### 1.2 用户限制

* 已知禁止优先于：模式、固定查询、历史授权、模型允许、普通批准、内部维护确认。
* 只有**真实用户修改/解除/撤回要求**才能改变该禁止（撤销/版本/状态必须来自要求台账）。
* 局部限制只影响相关动作和对象；可靠无关的操作继续按当前模式处理；事实不足时提供针对性的
  恢复或澄清，不把局部未知扩大为持续全局拒绝。

### 1.3 其他既定规则

* 普通删除默认进入系统回收站；永久删除遵守既定模式和明确确认规则。
* 审批十分钟过期；重启保持原始截止时间；等待不阻塞其他独立工作。
* 审批绑定具体要求、版本、对象、动作、内容和条件，单次领取执行。
* 子智能体仅获得必要权限；不足先向主智能体申请，主智能体也无权限时再请求用户。
* 应用自身正常的设置、记忆、日志及审批落库不额外要求内部维护三次确认。
* 自然语言含义由模型理解；执行层核对后端建立的结构化事实。

## 2. 共享事实与唯一含义（生产者 / 验证者 / 消费者）

所有入口只能使用下表的事实，不得另建同名但含义不同的判断。

| 事实 | 唯一含义 | 生产者 | 验证者 | 消费者 |
| --- | --- | --- | --- | --- |
| 要求 id/version/status/chain | 一次用户要求及其版本、链路摘要 | `RequirementLedger`（amend/apply_resolution/withdraw） | 台账 CAS（id+version+status+chain_digest）与 `set_structured_limits` 条件写入 | 引擎评估、审批提交/replay、恢复写回 |
| 动作-对象配对 | 本次真实 effect：每个 kind 与它的 targets/detail 一一对应 | 工具/附件/命令适配器构造 `Effect` | 引擎 `assess_limit_conflict` / `ObjectState` 判定 | 审批 payload、recheck、执行器 |
| 用户指定操作路径 | 用户请求里指定的目录项/路径（非解析后目标） | 工具适配器在 effect.detail 记录 `requested_path` | 执行器与最终真实目标逐项比对 | 限制/路径范围/审批绑定/删除语义 |
| 最终执行路径 | 真正执行系统调用的对象路径（链接语义按操作而定） | 执行器在系统调用前确定 | 同一执行器 + recheck（批准后重放） | 实际系统调用、影响集合、审计 |
| 身份比较路径 | 仅用于比较的规范化路径 | `object_state.resolve_path` | 比较函数自身（大小写/分隔符按平台） | 只供对象判定；**不得改写执行目标** |
| 对象身份与生命周期 | 文件身份键 + 创建/生命周期依据 | `file_identity.identity_of` / `compare_bound_identity` | 引擎/执行器重读核对 | 五态判定、审批绑定、内部身份 |
| 读取前内容与摘要 | 执行前一次真实读取得到的正文/摘要（含换行口径） | 工具或执行器的唯一一次读取 | recheck 在核对最新读取权限后重算比对 | 审批 payload、recheck、写入执行器 |
| 拟写入内容与摘要 | 本次准备写入的正文/补丁结果/附件内容 | 工具按请求构造 | 执行器按 payload 写出的真实内容 | 执行器、recheck、审计 |
| 影响集合与完整性 | 本次动作真实影响的对象集合（含目录子对象/参数脚本/读取影响）及是否完整 | 适配器有界枚举/解析 | 引擎/审批执行器逐项核对；不完整不得当完整 | 评估、审批、执行、批量逐项 |
| 当前模式 | 唯一权威模式值 | `AuthorizationEngine.set_mode` | recheck_approved / launch 启动前重读 | 所有判决、审批、UI |
| 委派范围及撤销状态 | 子智能体从父级 grant + 当前有效要求得到的明确子集；可撤销 | 父级 `make_agent_scope`/子任务请求 | 引擎 scope 核对（逐动作逐对象） | 子智能体工具、审批 replay |
| 审批期限/确认阶段/单次执行 | deadline、confirmed_stage、单次领取状态 | `ApprovalService.submit` + 存储层 | `decide`/执行前（过期、阶段、CAS、领取） | 执行器、恢复、重启 |

### 2.1 共享必经步骤

1. 任何真实入口（普通文件读写/删除/回收、程序启动、命令、参数脚本、附件解析与写回、审批提交与恢复、
   子智能体）都必须先构造完整 effect（动作+对象+影响）并调用统一授权入口，再进入内容读取/启动/修改。
2. 适配层只允许：构造 effect、调用统一入口、按结构化结果（verdict/decision_code/object_decisions/
   limit assessment）拒绝或继续；**不得**自行比较名称/路径/摘要/身份或解析 reason 文本决定权限。
3. 读取权限核对必须先于任何正文读取、摘要计算、shebang 内容探测、补丁计算与重新核验。
4. 元数据发现（存在性、身份、大小、mtime）与内容读取分开；拒绝时内容读取次数必须为 0。
5. 身份比较使用**保存的**身份/生命周期事实；当前查找、当前 stat、路径消失、缺失绑定单独都不构成“无关”。
6. `normalize`/`serialize`/`deserialize` 保持纯数据：不查找程序、不采集身份、不隐式补建绑定、不静默合并不同对象。

## 3. 逐项要求

每条要求都必须先有基线复现（红）与修复后（绿）的真实流程证据；拒绝用例配相邻正常放行用例，
允许用例配内容变化/对象变化/越界用例。

### A. 要求继承、绑定恢复与限制保存

* **A1 普通补充不得重新绑定旧禁止**：保存 runner 禁止（身份读取失败，候选 A），PATH 后来指向 B；
  用户只补充“把报告标题改成 X”时，amend 必须**原样继承**旧绑定、未解决状态、失败原因、候选及来源，
  不得重新查找并绑定继承限制，不得把限制转移到 B。区分“本次新增限制 / 明确修改对象 / 原样继承”。
  审查 `record_user_message`、`set_structured_limits`、`add_correction`、`apply_resolution` 及间接入口。
* **A2 缺失历史身份的候选不得宣称已验证**：保存候选只有 A 的路径；旧对象保留硬链接、A 被另一文件替换；
  恢复流程不得仅凭“A 当前存在且身份可读”声称已验证并绑定 A 的新对象，从而解除对旧对象的阻止。
  历史依据不足时保持未解决，保留 known limits、候选与来源；通过专用语义恢复或用户澄清确定限制含义，
  后端核验对象事实；写回继续核对版本、状态、链摘要与采纳事实。旧对象硬链接保护不得丢失。
* **A3 不同对象的同名限制不得被去重丢失**：同名、同动作、分别绑定不同程序的两条限制保存后必须都保留；
  第二条程序仍受限制。去重需考虑绑定对象/身份/生命周期/来源含义；规范化/序列化/继承/合并/恢复不得
  静默丢失不同对象；精确解除其中一个对象时保留其他对象；历史含义不足时澄清而不是静默删除或扩大。

### B. 纠正对象判断过严（保留 MATCH/UNRELATED/UNBOUND/INVALID/UNKNOWN 五态）

* **B1 未绑定的局部程序读取限制不得拒绝普通文件读取**：保存“禁止某程序读取”的限制后在三种模式下读取
  普通 `report.txt` 都必须按当前模式正常处理（普通读取默认允许），不得因该未解决限制持续拒绝无关文件。
  H13 实现口径（软件概念限制的范围规则）：仅当限制对象是 `program_name`、无有效绑定且无任何
  `binding_candidates`、本次 operation=read、候选是具体文件路径，并且当前名称解析不指向该候选时，
  判 UNRELATED（新增注册 basis，必须带上述对象事实）；execute/write/create/delete 与入口名候选仍
  失败关闭；显式 program 路径限制仍走 `_path_core` 保护。**残留边界**：未识别程序文件本体被按路径
  读取时无法保护，需通过专用澄清/绑定解决——报告中如实列明，不用其他禁止换取该边界。
* **B2 限制对象删除后不得持续拒绝无关对象**：保存“禁止读取 A”，B 原本可读；A 被删除后 B 仍必须按当前
  模式可读。不得把“限制路径身份不可读/消失”扩大成全局拒绝；同时不得放宽对旧对象硬链接/别名的保护。
  实现口径：要求保存时在精确对象条目上记录 `identity/birth_key/exists/observed_at/source`（纯数据、
  首次形成条目时采集一次）；object_state 用保存身份比较（不同→UNRELATED，生命周期不同→UNRELATED，
  缺字段→UNKNOWN/需澄清），不使用当前路径/查找推断历史对象。
* **B3 同名入口解析到独立对象时按对象事实判断**：禁止绑定到 A，当前查找指向独立程序 B 时，B 的绝对路径
  允许执行，同名入口也必须按“解析到与绑定对象不同的真实对象”处理（可靠不同对象继续），不得只因
  入口名相同就判 INVALID。若同名入口仍解析到绑定路径且身份变化，则仍属绑定失效（失败关闭）。
* 区分路径范围限制、具体对象限制、软件概念限制；历史表达无法可靠区分时做一次针对性澄清并按要求版本
  保存结果；可靠不同对象按当前模式继续；当前查找失败/路径消失/缺失绑定单独不能证明无关。
  保留旧对象硬链接保护与绑定失效核对。

### C. 读取必须先获准，再采集内容

* **C1 RunProgramTool**：最终拒绝执行前不得读取被禁止文件来计算摘要。所有元数据发现与正文读取分离；
  正文/摘要/shebang 内容探测/补丁计算/重新核验前先核对最新读取权限；拒绝时正文读取次数为 0。
* **C2 附件写回**：附件存在明确读取禁止时，写回流程不得读取原文件；普通写回批准不得解除读取禁止
  （写批准 ≠ 读批准）。写回操作事实必须包含必要的读取影响。
* 覆盖普通文件、程序本体、参数脚本、附件解析、写回、回收、直接允许、模型等待、人工批准恢复及重启恢复；
  内部维护确认前不读受保护正文；确认后仍受最新用户限制约束。本轮只处理 QIO 自身可控的读取，
  不扩大为对子进程任意运行时行为的隔离承诺。
* 不得通过取消摘要、忽略内容变化或省略前置核对解决。

### D. 内容绑定与影响完整性

* **D1 摘要缓存不得掩盖内容变化**：缓存不能仅以路径/大小/mtime 证明内容未变；采用可靠内容快照及
  文件变化依据维护缓存；工具、审查、直接执行、审批恢复和执行前核对采用一致语义；未变化程序正常执行。
* **D2 参数脚本不得被静默遗漏**：超过采集上限后后续脚本变化仍能执行、`python xxx.txt` 内容变化未入绑定，
  都必须修复。按真实启动语义识别入口脚本（解释器 + 参数位置），不能只靠后缀名单或 shebang；
  达到采集上限时明确记录未覆盖影响，不能宣称完整；给出完整采集/流式处理/可执行分解方案，避免普遍拒绝
  正常大任务。
* **D3 递归删除命令必须携带真实子对象影响**：禁止删除目录内指定文件时，递归删除该目录的命令必须命中该
  文件并拒绝（或按规则确认）；复用目录完整性、对象身份、用户限制及内部对象检查；普通文件工具与命令入口
  不能对同一删除影响得出相反结论；影响不完整时不得按完整方案执行，也不得用永久删除绕过回收/确认政策。

### E. 内部维护三次确认必须统一强制（§8）

已复现：通过附件写回内部日志只需一次确认即修改；受限模式下模型允许可使同内容内部文件替换直接完成
（文件身份改变但无人工确认）。要求：

1. 后端根据**真实影响对象**确定最低确认次数，不信任调用方填写的次数。
2. 内部维护不能由普通模型 ALLOW 完成。
3. 提交、批准、恢复和最终执行均核对实际确认阶段。
4. 历史或错误的一次确认记录不得被当成已完成三次。
5. 单项、批量及“内部对象不是首项”的批量采用同一规则。
6. 三次确认不能覆盖用户禁止或扩大子智能体权限。
7. 不增加第四次确认，不影响应用正常受控写入。

### F. 附件执行一致性与批量恢复

* **E1 不得检查旧路径、实际写入新路径**：审批等待期间附件引用改到禁止目录中的同一对象硬链接时，
  最终真实目标（含路径、用途、范围）必须参与最新限制、路径范围和审批绑定核对；身份一致不代表路径、
  用途和范围仍一致。
* **E2 正常写回/回收不得被误判为内容变化**：分别表达并核对身份、读取前内容、拟写入内容；直接允许与
  审批恢复使用同一规则；文件未变化时正常完成；真实变化仍使旧方案失效。新内容摘要不得拿去与磁盘旧内容
  比较；回收流程不得把身份字段当内容摘要。
* **E3 一个子项失效不得导致全部失效**：批量写回只核对共同条件（要求 active/版本/期限/模式/确认基础等），
  每项使用自己的真实效果、对象、内容、限制和确认要求；共同要求撤回或期限失效时停止整批；
  单项失效只影响对应项，保留独立有效项的执行和真实结果。

### G. 路径比较不得改变实际操作语义（§10）

请求回收符号链接时，必须删除/回收用户指定的目录项（链接本身），不得先解析成原文件后移动原文件。
用于身份比较的规范化路径不得擅自改写系统操作目标；读取、写入和删除分别确定链接及目标的真实影响；
覆盖普通文件、符号链接、目录链接、失效链接及目标受限场景；保留内部数据和真实对象保护，不通过取消
链接核验解决。

### H. 子智能体权限必须同时防止扩大和无故缩小（§11）

* **F1** 只有写权限的子智能体仍能读取 → 读取也必须检查操作权限。
* **F2** 授权撤销后仍能读取 → 读取检查撤销状态。
* **F3** 空文件授权的子范围在 unrestricted 模式下仍能读内部日志 → 内部数据/固定规则/unrestricted
  不能绕过子范围。
* **F4** 已授予运行删除程序及删除指定文件，却被拒绝 → 逐动作逐对象核对，不得无故缩小。
* **F5** 只授予对应路径的执行权限，反而能够删除文件 → 复合操作不能用某个动作的授权覆盖其他动作。
* **F6** 主智能体经模型审查取得的有效授权没有形成可委派范围，正常子任务被拒绝 → 主智能体依据当前有效
  要求、模式及核实授权形成完成子任务所需的明确子集；保留对象、版本、内容、条件和用途边界，
  不把一次许可扩大成长期通配授权；不足先向主智能体申请，主智能体也无权限时再请求用户；
  请求/授予/重试/撤销使用结构化状态，不能只返回一句错误文字；避免父级已有权限却重复要求用户批准。

### I. 模式变化按当前规则判断（§12）

批量操作已批准后从 restricted 切换到 unrestricted，不得仅因模式字符串不同而整体失效。
模式变化触发当前规则核对：放宽后仍符合要求、对象、内容和委派范围的操作不应重复审批；
收紧后当前规则不允许的未执行操作仍需停止；不得沿用不适用于当前模式的旧结论，也不得扩大用户禁止。
