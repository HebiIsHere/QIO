## 2. 三项会导致文字错位或未保存的问题

### 2.1 发送失败不能把原文恢复到另一个话题（契约 §10.1）
- **触发：** 在话题 A 输入并发送 → 受理未返回时切到 B → A 的请求失败。
- **改动：** 点击发送时 `session.sendAttribution()` 记录**原话题 + 原文 + 当时草稿版本**，
  `send()` 消费这份归属发请求；失败事实记进会话层（`failedSend`/`failedSendError`），
  ChatDock 与 Composer **不再各自把原文写回输入框**，恢复只由会话层的 `retryFailedSend()` 判断
  （当前就在原话题且输入框为空才放回；否则只回报原因）。原话题已有更新文字时走 `swapFailedSendText()`，两份都保留。
- **可见结果：** A 失败时人已在 B —— B 的输入框、草稿、发送状态一个字都不变；回到 A 可继续编辑或点「放回输入框」取回失败原文，**不自动重发**。
- **证据：** `d4ChatDraftRace.verify.test.ts` 时序 1/2/4/5 全过（旧基线必失败，见 §5）。

### 2.2 成功的旧回执不能删除后来写的新草稿（§10.2）
- **触发：** A 发送第一条 → 切 B → 回 A 写第二条并保存 → 切 B → 第一条受理成功。
- **改动：** `settleSend(at, accepted)` 只在「键相同**且**存储里的版本没有被更新草稿取代」时才删；
  输入框是否为空不再参与判断。
- **可见结果：** A 的第二条草稿保留；别的话题的草稿不受影响；重复回执不重复清理。
- **证据：** 时序 3 的三条（同话题、A→B→A、A→B→A 不清 B）全过。

### 2.3 慢保存失败后卡片新草稿不能永久停在 saving（§10.3）
- **触发：** 第一版正在保存时输入第二版 → 第二版防抖到点 → 旧请求失败。
- **改动：** `flushDrafts()` 不再「等旧请求后直接 return」；请求结束后重新检查未保存的新版本，
  **只有更新版本**才自动再试一次（有界，最多 8 轮），同一版本失败就明确标 error 并保留重试入口。
- **可见结果：** 第二版真的会再发一次请求（或明确失败可重试），不会出现「没有请求、没有计时、却一直显示保存中」。
- **证据：** `d4CardDraftRace.verify.test.ts` 时序 6/7 全过。

## 3. 空草稿与离开页面的恢复

- **空草稿是有效编辑状态（§10.4）：** 新增 `hasCardDraft` / `cardDraftText` / `clearDraft`；
  `BoardCard.startEdit()` 改成按「记录是否存在」判断（原来的 `draftFor(key) || card.content` 会把空草稿当没有草稿）；
  确认编辑后清记录（不是写空串），所以不会留下会盖住新正式内容的空记录；删除卡片时草稿按对象清理。
- **本机恢复副本（§10.5）：** 输入时**同步**写 `draftStorageKey("card", "local-<id>")`（不等防抖、不等网络）；
  重新打开时只有它**比服务端更新**才用它，并把该键标成未保存重新排一次保存；
  保存成功/确认/删除后按对象清理。**明确不把 `pagehide` 里的异步请求当作关闭恢复的证据。**
- **实测（场景 16，3/3）：** 删空正文 → 708ms 内服务端出现空草稿 → 取消 → 重新编辑输入框仍是空的 → 正式正文未变。

## 4. 布局与手势

- **几何模式改变必须落实面板切换（§10.6）：** 宽窗口两面板展开 → 缩到 480px 时**只显示最近打开的那个**
  （实测：聊天关闭、批量保留），并出现常驻切换条「空间不足，只展开一个面板（内容都还在）」+「看对话 / 看审批列表」；
  放大回 1200px 不自动弹出第二个。挂载、缩放、工具栏高度变化都按最新几何执行（不再用上一轮的 `cramped` 值决定）。
- **手势固定（§10.7）：** 删除「选择 / 框选 / 连线」三个常驻模式入口与 store 的 `boardMode`；
  规则固定为「空白拖动＝平移、空格＋拖动＝框选、连接点拖线＝建立关系」；工具栏改为「操作说明」（默认收起）。
- **实测（场景 17，5/5）：** 见上；另回归确认纯单击重叠卡片不成组、默认组名仍是「默认组名」。

## 5. 界面收敛（§10.8）

- 提交区常态只有：`本次可见：材料 X 项 · 注释 Y 条`、简短提交状态（`未提交 · 3 项改动`）、`详情`、`提交给 QIO`；
  完整排除清单、改动列表、保存与提交边界说明都在「详情」里；**删除了上一轮压缩子组件文字的 `:deep()` 补丁**。
- 聊天常驻一句「文字发送不会提交板面」，完整范围说明进可打开的「说明」；聊天外层保持透明，
  消息/用户消息/过程说明各自带轻底色（`:deep` 限定在互动聊天内，普通对话页外观不变）。
- `IntentPreviewCard` 的备用阴影改用 `--shadow-2`；互动板作用域已无硬编码色值。
- **实测：** 工具栏 1440/1024/800 = **51 / 80 / 80 px**（目标 ≤96px，改前一轮是 60/84/84）、
  两面板相交 **0 px²**、提交按钮可点、连接点命中、无横向溢出。

## 8. 已知限制与未验证项

1. **关闭重开未验证：** 探针浏览器每次调用新建实例、`localStorage` 跨调用不保留
   （同一次运行内 `reload` 正常）。因此「关掉浏览器再打开」的草稿恢复**没有实机证据**；
   `pagehide` 里发普通异步请求也不被当作证据。本机恢复副本的写入/恢复/清理由组件级与实机刷新路径覆盖。
2. **强制结束与崩溃未验证：** 只覆盖正常离开（编辑器取消、页面刷新、隐藏）。
3. **话题切换实机受限：** 实例只有一个话题，跨话题竞态主要靠会话层/组件级用例（18 条）覆盖。
4. **真实 QIO 未接入：** `delivery.delivered` 恒为 false，界面如实显示；发送失败与存储失败是模拟。
5. **负载敏感用例（不是本轮回归）：** `eventBufferOverflow.verify.test.ts` 的性能预算用例
   在**并发**跑验收脚本、多个 dev server 同时运行时超时（67s / 58s），把它单独跑 **4/4 通过（13.4s）**，
   机器安静时全量 `npx vitest run` **117 文件 / 1251 用例全绿**；没有降低门槛、没有删测试，
   按「负载敏感的稳定性现象」记录（与本轮改动无关：它在上一轮就出现过同样表现）。
6. **480px 与 800×600 分开：** 480px 属于浏览器窄窗口边界（本轮专门验证切换路径），
   800×600 仍是桌面最小窗口，两者结论不混用。

## 9. 边界

- 本轮**没有**开发真实 QIO 板面理解、附件系统或新的任务执行机制；没有合并两条开发线；没有合入 `main`。
- 保存与编辑不调用 QIO；聊天只发文字与正常会话上下文、不附带未提交板面；板面提交独立；
  未勾选注释及其关系不进 QIO 可见范围；成功提交才取消勾选、失败保留（场景 6/8 回归）。
