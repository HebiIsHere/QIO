# 生成工具执行隔离：威胁模型与分阶段方案

状态：第一阶段已落地（诚实边界 + 授权身份绑定）；**强制隔离未实现**，本文写清为什么、
以及分阶段怎么做到可验证。

责任范围：本文只谈「AI 生成的工具代码在哪跑、被什么挡住」。审批流程本身见
`backend/src/agent/tools/dev_auth.py` 与 `backend/src/agent/tools/lifecycle.py`；
执行器实现见 `backend/src/agent/tools/sandbox.py`。

---

## 1. 一句话结论

**当前 Windows 产品环境下的默认执行路径没有强制隔离。** 生成代码运行在**同一用户权限**
的独立子进程里：有一次性临时工作目录、超时、输出截断、环境变量白名单、不注入凭据，
这些是**降险措施，不是安全边界**。一个谎报能力的工具仍然能读写这个用户能读写的任何东西。

因此本文的目标不是「把文案改得好看」，而是：

1. 让**系统自己也承认**这件事（机器可读的隔离等级、授权身份、没有保护的面）；
2. 给出 Windows 上真正可行的强制隔离候选，以及每个方案要付的代价；
3. 把「能验证的第一阶段」与「需要架构变更的后续阶段」分开，不要用一次重写赌上产品。

## 2. 威胁模型

### 2.1 保护对象（用户资产）

| 资产 | 说明 | 默认（受限子进程）下的实际状态 |
| --- | --- | --- |
| 用户文件 | 家目录、桌面、文档、其它盘符 | **可读可写**（同用户权限） |
| 网络 | 出网、内网横向、本机端口 | **不受限**（没有按域名/端口拦截） |
| 凭据 | QIO 凭据库里的 Key（keyring 保护） | 不注入子进程；但用户自己的凭据文件（.env、key 文件）**可读** |
| 任意进程 | 再拉起别的程序、常驻、打死别的进程 | **可以做** |
| 环境 | 环境变量、进程列表、注册表（同用户） | 环境变量已裁剪；其余**可读** |
| QIO 数据目录 | 工作区、trace、记忆、工具输出库 | **可读写**（同用户） |

### 2.2 对手模型

* **对手 = AI 生成的工具代码本身**，包括：
  * 能力申报与实际行为不一致的代码（声明 PURE、实际联网/读写文件）；
  * 依赖被投毒、或被提示注入诱导写出的代码；
  * 通过子进程、动态加载、网络把影响扩散出去的代码。
* **对手不具备**：管理员权限、内核漏洞利用、硬件攻击。这些不在本轮范围内。
* **用户批准过的东西不算越权**：用户显式批准的 TRUSTED 能力（例如联网）按批准执行；
  本文关心的是「批准之外的能力是否真的被挡住」。

### 2.3 信任边界

```
后端进程（可信，持有凭据/数据库）
   │  审批（用户确认执行边界）
   ▼
执行器（SandboxExecutor）
   ├─ docker 分支：容器是**边界**（--network none、--read-only、pids-limit…）—— 仅当守护进程可用
   └─ 受限子进程分支：**没有边界**，只有降险（临时目录 / 超时 / 输出上限 / 环境白名单 / 不注入凭据）
```

**关键事实（已实测，2026-10-02）**：本机 `SandboxExecutor().executor == "auto"`、
`effective_executor() == "subprocess"`，而旧的 `default_policy_for()` 默认把
`isolation` 写成 `container` —— 策略自己声称了一个不存在的容器。第一阶段把这个字段
改成由**真实执行器**推导（`isolation_for_executor`），并让指纹跟着环境变。

## 3. 候选强制隔离方案（Windows 产品环境）

评估口径：**是否真的挡住 2.1 里的资产**、是否能在用户机器上默认可用、实现与维护成本、
能否被自动化验证。

| 方案 | 挡住什么 | 挡不住什么 | 本机可行性 | 结论 |
| --- | --- | --- | --- | --- |
| **Docker / 容器** | 文件系统（只挂载项目目录）、网络（--network none 默认）、进程（pids-limit）、环境 | 需要用户装 Docker Desktop 且守护进程在跑；镜像分发与磁盘占用 | 本机**未安装**（守护进程不存在）；ubuntu CI 上可用 | **保留为「有就用」的一等路径**；不能作为默认保证 |
| **Windows ACL**（给临时目录设拒写/拒读 ACE） | 其它目录的**写入**（仅当子进程不是所有者时） | 子进程与父进程同一 SID，**所有者可以改回 ACL**；读权限本来就有 | 可行但无意义 | **不作为边界**；只用于「工作目录物理隔离」的加固 |
| **restricted token**（`CreateRestrictedToken` + `CreateProcessAsUser`） | 去掉管理组、禁用 SID、限制完整性级别 | 需要原生启动器；Python `subprocess` 无法直接传递受限令牌；行为差异大（某些 API 直接失败） | 需要新写原生组件 | **第二阶段候选**（成本高、收益真实） |
| **AppContainer**（`CreateAppContainerProfile` + SECURITY_CAPABILITIES） | 文件系统（除显式授权目录）、网络（默认无 capability 即无网络）、注册表 | 需要原生启动器；容器内要能被 Python 启动；打包后仍要能定位解释器 | 需要新写原生组件 | **首选第二阶段目标**：Windows 上真正的强制边界 |
| **Job object** | 进程树回收、CPU/内存/进程数上限 | 文件系统、网络、凭据——**都不是安全边界** | 已部分具备（超时杀进程树） | 继续用于**资源限制**，不冒充隔离 |
| **专用低权限用户** | 文件系统（跨用户 ACL 真正生效）、部分系统资源 | 需要创建用户/凭据管理；用户机器上提权操作不可接受 | 不现实 | **不作为产品路径** |
| **文件系统 staging + 一次性目录** | 工具拿不到「工作区之外」的**默认路径**；调用之间不残留 | 恶意代码可以直接写绝对路径到任意位置 | 已实现 | **已落地**，但只是降险 |

**结论**：本机（以及大量用户机器）没有 Docker，也没有便宜的 OS 级边界；
唯一真正可行的 Windows 强制隔离是 **AppContainer 或受限令牌 + 原生启动器**，
那是一次架构变更（新组件 + 打包 + 真机验收），**本轮不做仓促重写**。

## 4. 分阶段实现

### 阶段 0（本轮已落地，可验证）

目标：**系统说的和实际做的一致**，并且授权绑定的就是真实执行环境。

* `tools/policy.py` 新增 `isolation_for_executor` / `isolation_label` /
  `unprotected_surfaces`：隔离等级、用户可见说法、没有保护的面只有一个来源。
* `default_policy_for(definition, executor=...)` 按真实执行器推导隔离等级，
  因此**执行环境进指纹**：容器没了 / 换回受限子进程 → 旧授权不再算数，必须重新确认。
* 执行审批（`tools/dev_auth.py`）逐字段绑定身份：任务、能力策略指纹、执行环境、
  目录范围、网络范围、凭据范围、被测内容摘要；并**明确列出没有保护的面**。
* 授权生命周期只有三种（本次执行 / 当前开发任务 / 长期授权），没有「不撤销就永久有效」。
* 「受限子进程」不允许被叫成「安全沙箱」——由 `isolation_label` 与测试锁住。

验收方式：`backend/tests/test_tool_policy.py`（隔离等级/说法/没有保护的面）与
`backend/tests/test_dev_test_authorization.py`（审批说明与授权身份）里的边界断言；
两者都不依赖 Docker、不联网，容器分支用显式 `executor="docker"` 覆盖。

### 阶段 1（下一步，仍然是降险，不冒充隔离）

* **默认拒绝**：没有容器时，任何「需要隔离的能力」（联网/绝对路径/进程）一律拒绝执行，
  或要求用户显式批准为 TRUSTED（现状已具备，需要补齐端到端用例覆盖）。
* **工作目录与 QIO 数据目录物理分离**：执行前把项目复制进一次性目录，执行后销毁；
  QIO 数据目录不作为任何子进程的 CWD 或 `sys.path` 项。
* **凭据永不进入子进程**：环境白名单 + 不落在磁盘上（现状已具备，需要断言覆盖）。
* **可观测**：每次执行记录「真实执行器 + 隔离等级 + 没有保护的面」，
  trace 里能查到（新增输出路径必须过 `trace/redact.py`）。

### 阶段 2（架构变更，需要单独立项）

* 新写一个**原生启动器**（Rust，随 Tauri 壳一起打包），用 AppContainer 或受限令牌
  启动 worker：
  * 只授权一个一次性目录（写）、只读的必要系统路径（Python 运行时）；
  * 默认无网络 capability；
  * 子进程不能再拉起同级进程的能力按需收紧。
* `SandboxExecutor` 新增 `executor="appcontainer"`，**探测不到就不假称可用**，
  并且**升级路径明确**：appcontainer → docker → 受限子进程（逐级降级要用户可见）。
* 验收必须在**真机**上做：让声明 PURE 的工具尝试读用户目录 / 写系统目录 / 连网，
  证明三类都失败；frozen（打包后）再验一次。

### 阶段 3（跨平台收口）

* POSIX 上以容器为默认隔离，CI 里用 ubuntu runner 复现「容器内拒绝越界」的用例；
* Windows 上 AppContainer 与容器二选一，按探测结果决定，并保持同样的诚实文案。

---

## 5. 明确不做 / 不声称的事

* 不把「受限子进程」叫成「安全沙箱」——界面、审批说明、文档一律按 `isolation_label` 说。
* 不在没有强制隔离时声称「数据不会被读出」「不会联网」。
* 不用「用户已批准」来代替隔离：批准的是能力范围，不是「代码一定守规矩」。
* 本轮**不**实现 AppContainer / 受限令牌（需要原生组件、打包与真机验收）。
