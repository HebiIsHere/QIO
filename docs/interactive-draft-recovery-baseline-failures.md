## 2. 独立用例（子智能体 D 编写，基线 `f436ad8` = 基线 + 骨架）

命令：

    cd D:\qio-dev\qio-recover-d\frontend
    npx vitest run d5

     Test Files  6 failed (6)
          Tests  12 failed (12)

失败的 12 条（原样抄录用例名）：

- `d5CardDraftRecovery`：防抖未到就刷新：本机记录必须被发现并恢复出来 / 恢复出来的本机草稿要重新排一次保存 /
  清除最后一份草稿也必须发出同步请求 / 清除后刷新，旧草稿不许复活
- `d5LocalWriteFailure`：本机存储写入失败：编辑处要如实说明，并保留输入内容
- `d5ComposerRecovery`：失败后页面上直接看得见本次真实原因 / 输入框已有新文字时仍要有取回失败原文的入口且两份都保留
- `d5FailedSendRecovery`：刷新（新 store）后仍能知道这次失败并取回原文 /
  `currentTopicId=null` 发送 → 绑定真实话题 → 受理成功：输入框与草稿都要干净
- `d5SubmitFailure`：上一次提交成功、本次请求失败：默认区域必须含本次原因 /
  上一次提交也失败过：默认区域不许拿上一次的旧原因当本次原因
- `d5SwitchBarGeometry`：切换条要给剩下的面板预留真实高度

## 3. 说明

- 以上失败都是**行为性**失败（刷新后文字丢失、清除后服务端仍保留、默认区域缺真实原因、
  窄窗口什么都看不到），不是「新函数不存在」或「选择器改名」。
- 失败制造方式：请求拦截（`fetch` 包装只拦单条路径）与本地存储写入失败注入，均在用例/脚本里明确标注；
  应用自身的处理流程是真实的。
- 真实 QIO 未接入（`delivery.delivered=false`），本轮不涉及模型回复，只涉及草稿与失败处理。
