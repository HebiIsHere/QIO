## 未验证 / 装置限制（如实写）

- **J2 的强制结束前等了 6 秒**：Chromium 的 localStorage 是延迟落盘的，SIGKILL 前若刚写过，记录可能整条丢失
  （实测：不等就杀掉时重开后本机记录为 null）——这是浏览器属性，不是产品保证；因此本场景在强杀前留出落盘时间，
  并把它写进证据，避免把浏览器行为误判成产品缺陷。
- **J5 的「等待期间独立移动必须保留」：未验证。** 真实指针拖动在本装置上没有让卡片移动
  （拖动前后 left 都是 420），因此该子断言不当作通过，也不当作产品缺陷。J5 已确认的只有
  「取消影响确认 → 出现确认框 → 取消后被取消的正文仍在板面上」这条 F1 主路径。
- **J1/J2 的「重开」在最初几次尝试里不可信**：同一 profile 被历史实例用过时，旧实例退出会
  把旧 localStorage 快照写回，导致「已删除的记录又出现」。装置改为**每个场景一个全新 profile**
  后才成立（probe-ls*.mjs 是当时的排查证据）。这一点不影响产品结论，但复核时必须保持同样的用法。
- **R2/R3/R5 的迟到读取、兜底确认**：本轮 E2 只覆盖了 R3 的连续编辑（J3 的正文部分通过）；
  R2（迟到 GET 覆盖已保存新版）与 R5（impact_confirmation_required 兜底补取 checkId）
  的**浏览器级**证据本轮未采集（store/组件层已有既有验证）。标注为未验证。
- **N1 / N4 / N5 的浏览器级证据**：本轮未采集（N1/N4 有后端 ASGI 反例，N1/N5 有 store 级反例）。
- **N6 的 file/code 附加字段**：E2 只验证了 url 卡（网址 + 标题）；文件名/图片名/代码语言
  由组件级反例覆盖。
- 以上未采集项在集成分支复核时补跑同一脚本即可（脚本支持 --scenarios=J1,J2,... 过滤）。

## 与「写 marker 再重开」的区别

J1/J2/J3 都断言的是**本功能自己的事实**：本机草稿记录、服务器草稿、编辑框内容、处理入口可达性；
不是「写一个无关 key 后能读回来」。J1 还额外核对了「关闭前 null → 重开后 null」这条负向事实。
